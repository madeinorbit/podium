Map, Queue, Voice — one scope rule for every attention surface

Podium's promise is multiplying parallel throughput by holding the operator's attention for them. That takes exactly three surfaces, and each one's scope follows from the question it answers. The current confusion (tray vs. sidebar overlap, where the superagent lives, issue vs. repo vs. global scope) dissolves once the surfaces are named and the rule is applied.

Every mature attention-heavy tool converges on the same trio — Linear has sidebar + Inbox, email has folders + inbox, Slack has the channel list + Activity. Podium's version:

THE SCOPE LAW
State surfaces are structured. Decision surfaces are complete. Command surfaces are global with injected context.
A map you can filter is still a map. A queue you filter is no longer an inbox — the moment the operator has to wonder "is this everything?", they fall back to scanning the map, and the queue's entire value is gone. A command line that must be re-scoped before speaking isn't a command line.

02The tray does not overlap the sidebar

They overlap in membership — the same waiting item appears in both — but not in function, and the duplication is the mechanism, not a bug. The sidebar's amber badge says that something waits (ambient, glanceable, spatially stable). The tray card says what and lets you act without navigating (full decision: headline, evidence, buttons). Email never made you choose between the folder tree's unread counts and the inbox; Linear never made you choose between the sidebar and Inbox. The pair is the pattern.

What keeps them from competing is a strict role rule: the map carries signals only (count pill, spinner, unread dot — never buttons, never card content), the queue carries the one actionable rendering. If the sidebar ever grows action buttons, or the tray ever grows status rows, the two really would collide — that's the line to hold, and it's the answer to "drop the tray / make the sidebar more complex": decision cards are transient and churny; embedding them in the sidebar would destroy exactly the fixed-position stability POD-100 requirement #1 demands. The map must not churn; the queue must churn.

03The five options, judged by the law

ASidebar + global tray + global chat in the engraved columnADOPT — IT'S THE LAW APPLIED

This is the POD-113-approved direction, and it's correct on every axis: the tray is complete (trustworthy queue), the chat is one global thread with the [USER VIEW] focus block injected per turn (global voice, contextual answers), the sidebar stays a pure map. Selection influences the tray only as a highlight ring — never membership, never sort.

The backend already implements the voice correctly: THREAD_ID='global' + per-turn focus payload. Your "item-unrelated-but-still-getting-the-context" instinct is this mechanism — it has a name now: global agent, injected context. Stop treating it as unresolved.
BTray-only column; superagent as a spawned tab (like files/artifacts)REJECT — BUT KEEP THE ESCALATION

Moving the superagent into a workspace tab kills its defining property: zero-friction availability. A voice you must spawn and find is a destination, not a command line — and the native pane is issue-scoped, issue-tinted territory; one global tab inside it muddies the context flow that the whole colour system exists to make legible. Worst of all, Discuss ↓ on a tray card would become a navigation instead of a glance-down.

Keep the good half: when a chat becomes work, promote it — the "open in terminal" affordance is exactly this. Tabs are for engagement; the column is for triage. See the escalation ladder (§6).
CTray + chat scoped to the selected issue (the code today)REJECT — QUEUE CAN'T BE SCOPED

"The sidebar catches attention, a click brings you in" sounds right but inverts the flow: once you've selected the issue you are already engaged — the issue page, session view and OfferBar show its needs in full. An issue-scoped tray answers a question nobody asks from that position, and cannot answer the one question a tray exists for: what's next across everything? With it, cross-issue triage degrades to click-scan-click-scan through sidebar badges — the exact loop the product promises to eliminate.

Concretely: delete trayScopeIssues (derive-tray.ts) per the approved POD-113 spec. The current code state is just the un-shipped half of a decision already made.
DRicher sidebar; drop the tray (or the whole column)REJECT — MAP MUST NOT CHURN

Cards need width (action rows, artifact thumbnails, feedback inputs) and they arrive/expire constantly. Hosting them in the sidebar breaks fixed positions, breaks the 52px rail collapse, and leaves the phone with nothing: on mobile the tray-as-overlay is the check-in surface PRODUCT.md promises ("glance at the board, answer an agent's question"). A sidebar can't be that.

ETray scoped to the selected issue's repo (colleague's proposal)REJECT — IMPLICIT FILTERS BREAK TRUST

The steelman: a repo is a natural working-set boundary, especially for a teammate who owns one area. But deriving the filter from selection is the worst of both worlds — the inbox silently changes contents as a side effect of navigation. That violates the same principle POD-113 already settled at smaller scale ("never re-sort on selection") at a bigger one: never re-filter on selection. An inbox whose completeness depends on where you happen to be standing cannot be trusted, and an untrusted inbox is furniture.

If team-scale focus is ever needed: an explicit, visible, user-set filter chip on the tray bar (ALL TASKS ▾ → per-repo), sticky until cleared, never selection-derived. Default remains All. File it for when the second user shows up.

04Offers in "two places" is actually three altitudes — all correct

The uncertainty ("we render offers in 2 places because we don't know where it's best") resolves the same way: it's one item rendered at three altitudes, one job per altitude, acting at any altitude clears all three.

AT THE SOURCE · session view
OfferBar above the composer

In-context: you're already looking at this agent; the decision sits where the evidence is. Full detail.

IN THE QUEUE · tray
The actionable card

The only place to act without navigating. Judged in five seconds, cold — headline, state line, buttons, thumbnails.

ON THE MAP · sidebar
Amber count pill only

Pure signal. Never a button, never content. Clicking the badge may deep-link to the tray card (§7) — it never acts.

05One refinement to the approved design: the composer never leaves

Your unease about the superagent is real, but it's not a placement problem — it's a posture problem. A 460px standing chat pane is a lot of furniture for something used in bursts. The v2 handoff already has the right collapse grammar, with one wrong detail: a collapsed super agent loses its composer (3b). Flip that. The feed is what collapses; the composer is the product's command line and never disappears while the column is open.

Typing or sending expands the feed in place; going idle (or Esc) lets it fall back to triage posture. This is the honest version of "superagent as a tab": the tab is the third rung, reached by promotion, not the default home. Triage altitudes live in the column; engagement lives on the stage.

07Cross-links and clearing — the contract that makes it one system

  • Map → Queue: clicking a sidebar amber badge focuses + flashes the corresponding tray card (don't navigate into the issue — the badge is the queue's doorbell, not the issue's).
  • Queue → Map/Stage: the card's ID square selects the issue; session → opens the agent on the stage. Already specced.
  • One item, one fate: acting anywhere (OfferBar, tray card, chip answer) clears every rendering at once. No per-surface read state.
  • Stillness is the signal everywhere: one arrival morph, then nothing moves until the human does. The motion grammar is already right — it's the scope discipline that makes it legible.

08What this means for the code, today

  • Ship POD-113 as approved: delete trayScopeIssues — the tray renders all live offers/questions/finished, decisions-first, newest-first, ring-only selection effect. The spec text in .design/specs/engraved-column.md §5 already says this; the code is just behind it.
  • Keep the superagent exactly where and how it is (global thread + focus injection). Retire the visible thread-switcher ambition; concierge/btw threads stay backend plumbing.
  • Amend the 3b collapse rule: collapsed super agent = feed hidden, composer kept (§5 above). Add a global focus-composer shortcut.
  • Hold the role rule in review: no actions in the sidebar, no status rows in the tray — ever.

09Decisions for Till

Adopt the scope law as the standing rule?

Map structured · queue complete/global · voice global with injected context. This closes options C and E permanently and becomes review-able doctrine (a line in DESIGN.md).

Composer-always: amend handoff 3b?

Collapsed super agent keeps a one-line composer; the feed is what collapses. Default column posture = triage (tray + composer). Recommended.

Global shortcut for the voice?

One chord (⌘J?) focuses the composer from anywhere, even with the column folded — the folded 44px bar would pop the composer as an overlay. Cheap, and it's where the "global feeling" actually comes from.

Badge → card deep-link?

Sidebar amber badge focuses the tray card instead of selecting the issue. Small wiring, big legibility win. Defer if contentious.
