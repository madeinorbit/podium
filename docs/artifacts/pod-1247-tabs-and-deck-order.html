Podium · how it works

Which tab, which order

What the tab strip shows, which tab opens first, how the flight deck orders tasks and sessions, and what survives a reload — on a mission with sub-tasks and many agents.

1 · Which tabs show

One strip for the whole mission

The strip is keyed by the mission root, not by the task you clicked. Selecting a sub-task keeps the same strip — it never swaps to an empty one. Key: mission:<rootId>.

A tab is there because something opened it

Nothing fills the strip for you. Tabs come from a click in the deck, a reveal, an opened file, or a launch. So a mission with 12 sessions can show 1 tab.

What can stay

On every update, tabs are pruned. A session tab survives if the session still belongs to this mission — its issueId is in the mission, or its folder sits in a mission worktree. A file tab survives if it carries this issue's id, stamped when it was opened.

Order inside the strip

Not sorted. New tabs are appended in the order they were opened; you can drag to reorder. The one italic preview tab is special: the next preview replaces it in the same slot, so glancing through sessions feels like one tab.

2 · Which tab is preselected

Click a task in the deck

It opens one session, chosen in this fixed order:

  1. The task's coordinator session
  2. The only live session, if there is exactly one
  3. The most recently active live session
  4. Nothing opens — a task with no live session leaves the current chat alone

Only live sessions count: archived and exited ones are skipped. The pane you were looking at is deliberately not a preference.

Glance vs. keep

  • Single click → preview tab (italic). It closes when you land on another tab.
  • Double click, or typing into the session → permanent tab.
  • Clicking a session row → that exact session, same glance/keep rule.
  • A departure row → its newest live session, always permanent.

With split panes

Each pane remembers its own active tab. Gestures without a pane land in the focused pane, or in the first one if that pane is hidden.

3 · Flight deck order — tasks

The deck is a tree walked depth-first from the mission root, so a sub-task always renders right under its parent. Top to bottom, the column is:

1Mission root strip
2The root's own sessionsall of them, before any sub-task
3The sub-task treeeach task, then its sessions, then its children
4Proposed taskstheir own tail, outside the tree
5Departuresby issue number, ascending

Sibling tasks

  1. sortKey ascending — the manual drag order, when set
  2. Issue number ascending — oldest first

Work an agent started with no parent is grafted under the session that started it, or under the root — then sorted with the rest.

SurfaceFirst ruleFallback
Flight decksortKey ascendingOldest first
Sidebar work listPinned top, snoozed bottom, then sortKeyNewest first

Neither list reorders while agents work. Urgency is shown on the row, never by moving it.

4 · Flight deck order — sessions

Lead first, then in the order they started

  1. The task's coordinator — the lead heads its own crew
  2. Everyone else by start time, oldest first

Until now there was no order at all: agents came out in the order the local store handed them over, which is session id — a random UUID. Stable, and meaningless.

  • Settled agents stay in place, one shade dimmer — nothing is hidden.
  • The Needs you view is the one thing that shortens the list: it keeps only the sessions that are actually asking.
  • Recency is a different question, and it kept its own job: it picks which tab a click opens.

5 · What comes back after a reload

The layout is saved, per device

The whole workspace map is written to this browser's local storage on every change, under the signed-in user. It is deliberately not synced: a phone should not inherit a desktop's split.

What is restored

  • Every mission's strip, not just the one you were on.
  • Tab order per pane, and which tab was active in each.
  • Splits — the tree, the axis, and the drag sizes.
  • Open files — the buffers now travel with the tabs that name them.

A broken or older-shaped blob restores as empty rather than as a layout nothing can render.

What is released on purpose

The italic preview tab. A glance lasts as long as you are looking at it, and leaving is leaving — so it is dropped on the way to storage, rather than coming back as a kept tab you never chose.

Tabs that name nothing

A session killed elsewhere, or a file opened through a session that is now gone: an id that fails to resolve for 20 seconds is dropped, tab and record together. The delay is there because a session may just be arriving late.
