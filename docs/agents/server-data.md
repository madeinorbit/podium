# Server data

How server code (`apps/server`, `packages/sync`) reads, writes and caches data. Every server change follows this guide. It is the server side of [frontend-data.md](frontend-data.md). The agreed design behind it is `docs/internal/superpowers/specs/2026-10-15-server-data-access-design.md` (POD-6140); the evidence is `docs/internal/pod-6140-research.md`.

POD-6140 removed the server's in-memory copies of tables (the world index, both sync copies, the observation checkpoint map and the issue map; the session map now holds running sessions only). The result is in `docs/measurements/pod-6140-result.md`. New code reads the database and adds no copy.

Machine content is reached through the named machine's daemon; a machine id comes from the caller or its record, never from the server host as a default. `scripts/check-server-host-access.ts` enforces this rule in `bun run test` and CI (`bun run lint:server-host-access`): production server code cannot import local filesystem/process APIs, read OS home/temp/hostname values, use Bun disk/process APIs, or read `hostMachine`/`hostMachineId` outside its reasoned allowlists of installation owners and test infrastructure. An exception must name a file or directory, explain why it needs host access, and remain used; `--probe` demonstrates all five required refusals before the real scan.

## Source of truth

The database is the only source of truth for stored facts. The server never holds a full copy of a table in memory.

Memory may hold only:

| What | Example |
|---|---|
| **Live runtime state** that is not a stored fact. It grows with activity, not with history. | connected daemons, running sessions and their terminals, presence |
| **Declared caches**, under the rules in "Caching" below | none yet; the cache layer is built only when a measurement shows the first real need (POD-6150) |
| **Declared write hints**, under rule 7 of "Caching" below: what a store last wrote, kept only to make its next write cheaper, never read as a fact | `WrittenColumns` for the session upsert (POD-6234) |
| **One-operation memos**: the read scope, which removes repeated lookups inside one operation and is gone when the operation ends | `withReadScope` and `readScopeSlot` in `apps/server/src/store/executor/read-scope.ts` |

**One way to read a fact.** A memory copy cannot see a save that is still in progress, so during a save the code must skip the copy and ask the database; When every read asks the database, the database already shows the save's own unfinished changes, so there is no special case and nothing to keep in step: grants, machines, pending counts and folder owners have read only the database since POD-6155, and issues since POD-6158.

**Boot** loads live runtime state only. It never loads whole tables.

Synced records are built from the model tables. Every synced record kind is declared once in `@podium/model` (`records/declarations.ts`: fields and parts, links, collections); the server's record builders register against those declarations, and a collection rule compiles to SQL with `@podium/sync/collections`. The collection fetch (`POST /sync/collections` and the first download, POD-7085) reads each rule through `CollectionsRepository` (`store/collections.ts`): one prepared statement per shape of a declared rule, every value bound, every shape planned by the query-plan audit. A data migration that rewrites
them must bump every affected kind's `sync_kind.generation` in the same migration, in every
workspace that has a feed: "Kind generations" under [Workspaces](#workspaces) has the statement.
Boot does not repair the sync log. Historical upgrades that require service logic
use the normal write funnel and a durable completion receipt.

**Two migration chains** [POD-6981, design `docs/design/POD-6958-postgres-store-design.md`
§2.7]. SQLite migrates at boot from `apps/server/src/migrations/drizzle/`; Postgres has its
own chain in `apps/server/src/migrations/pg/drizzle/`, starting from one baseline generated
from the Postgres schema twin and never edited by hand. On hosted Postgres migrating is a
deploy step, `podium server migrate --database <url>`; a server only checks the ledger at
boot. The baseline is named after the newest SQLite migration it covers, so **every new
SQLite migration changes the Postgres chain too**:

1. Edit `apps/server/src/migrations/schema.ts` and its twin `migrations/pg/schema.ts`
   (`bun run schema:pg -- --check <table>` shows what the generator would write).
2. `bun run migration:new <name>` writes the SQLite migration and then the Postgres side:
   until the baseline is frozen it regenerates the baseline in place; after the freeze it
   writes a Postgres migration under the same folder name.
3. A migration written by hand with `drizzle-kit generate` (`--custom` for a data
   migration) does not touch the Postgres chain: run `bun run migration:pg-baseline`
   yourself before the freeze, or write the Postgres twin under the same folder name
   after it. `chain-parity.test.ts`, in the lean gate, fails until the chains agree, and
   its message names the command.

Until the first hosted database exists the baseline is regenerated in place. Once a hosted
database has applied it, set `PG_BASELINE_FROZEN` in `apps/server/src/migrations/pg/chain.ts`
in the same commit; from then on regenerating it is not allowed, and every change is a
migration in both chains under the same folder name. The generation bump rule above applies
to both chains.

## Workspaces

One server database holds one or more workspaces, and no statement reads or writes a workspace it was not built for [POD-6959]. A self-hosted install has one workspace, `local` (`SELF_HOSTED_WORKSPACE_ID` in `apps/server/src/self-hosted-workspace.ts`, the only place outside the migrations that spells it). Hosted Podium keeps many workspaces in one Postgres database, named by the `ws_` ids podium-cloud mints. A workspace id is the `WorkspaceId` brand (`packages/model/src/ids/brands.ts`). It is minted with `asWorkspaceId` in three places only: the self-hosted composition, hosted routing and test support. It never comes from a request. The isolation comes from the rules below. There is no row-level security.

**Every table has one class.** `apps/server/src/store/workspace-manifest.ts` lists every table with its class and the reason: `workspace` (every row belongs to one workspace), `identity` (the identity package's tables, unchanged), `install` (one per database: what the installation is, its upgrade marks and own secrets, the janitor lease), `transient` (change capture inside one transaction, engine bookkeeping) or `derived` (search indexes scoped through their source table). A new table gets its line there in the same change, or `store/workspace-manifest.test.ts` fails. `meta` and `server_secrets` hold install keys only. A workspace's own keys (settings, model catalogs, its secrets) live in `workspace_meta` and `workspace_secrets` (`store/settings.ts` and `store/server-secrets.ts` are the pattern).

**Every workspace table leads its keys with `workspace_id`.** The column is `text NOT NULL` with no default. The primary key, every unique constraint and every index start with it, and an `ON CONFLICT` target names it first. Foreign keys are composite, `(workspace_id, issue_id)` → `issues (workspace_id, id)`, declared with `workspaceRef` (`apps/server/src/migrations/branded-ref.ts`), which refuses a key that does not lead with the workspace. So no row can reference a parent in another workspace, on either engine. A workspace is its own key space: two workspaces may hold the same issue id, repository id or machine id, and natural keys are unique per workspace (issue numbers `(workspace_id, repo_id, seq)`, label names, repository prefixes, profile names). The seven AUTOINCREMENT ids stay global numbers with `UNIQUE (workspace_id, id)` beside them. A number that counts per workspace, such as an issue number, is allocated inside the workspace's write transaction, never from a database sequence. `migrations/workspace-keys.test.ts` checks the keys and indexes on both engines' schemas. The rearch audit forbids `tenant_id` anywhere and counts workspace tables without `workspace_id` (expected zero).

**A repository is built for one workspace.** `StoreDatabase` (`apps/server/src/store.ts`) owns the one database: the executor, migrations, lifecycle, the global repositories, `provisionWorkspace(id)` and `workspace(id)`. `database.workspace(id)` returns that workspace's `SessionStore`, every repository of it built from the workspace's `WorkspaceQueries` (`store/executor/sync-drizzle.ts`). The handle carries the workspace, and its bound views fill the `workspaceId` placeholder of every statement, so call sites pass no workspace. A caller value named `workspaceId` is refused (`CallerWorkspaceValueError`). Every workspace shares one prepared statement per definition. Every transaction records a `StoreContext` (`store/executor/executor.ts`): a workspace's, or `GLOBAL_CONTEXT`. A workspace transaction joins only work of its own workspace (`CrossWorkspaceStatementError`), and a global transaction refuses a workspace statement (`WorkspaceStatementInGlobalTransactionError`). `provisionWorkspace` creates the workspace's `sync_feed` row before its first write: on Postgres that row is the workspace's write lock (How queries execute, item 4), and a write in a workspace without one fails.

**Three kinds of definition** (`packages/sync/src/adapters/sqlite/prepared.ts`, typed for the server in `store/executor/sync-drizzle.ts`):

| Kind | What it may touch | Runs on | Who may use it |
|---|---|---|---|
| `prepared`, `preparedFamily` | workspace tables, each constrained to the workspace; install tables too | a `WorkspaceDb` | every repository of a workspace |
| `preparedGlobal` | install tables only: its `t` is typed `GlobalTables`, so `t.issues` does not compile | any store handle | the files `GLOBAL_REPOSITORY_FILES` in `store/workspace-manifest.ts` lists, each with its reason (the provisioning insert in `store/database.ts`, the install keys of `meta` read by the settings, issues and machine-record repositories, the update recovery checkpoint) |
| `preparedAcross` | a `SELECT` over many workspaces | the fleet handle (`fleetDb`) only | a fleet job that finds the workspaces with work, then does the work through each `database.workspace(id)`. It is made with an entry of the allowlist, and nothing writes across workspaces |

A global context may write only `meta`, `server_secrets`, `maintenance_leases` and the provisioning insert of a workspace's `sync_feed` row.

**The cross-workspace allowlist** (`store/cross-workspace-allowlist.ts`) lists every statement that may touch more than one workspace, or a workspace's rows from outside it, with its file, name, reason, the index that serves it and the owning issue. Today it has two entries: the provisioning insert (`provisionWorkspaceFeed`, `INSERT INTO sync_feed … ON CONFLICT (workspace_id) DO NOTHING`, global because the row it inserts is the row the workspace's lock takes) and the janitor's list of workspaces with a feed (`listWorkspacesWithFeed`). A raw `SELECT` outside the definition registry, such as a janitor read, is listed as `raw-read` with its exact SQL. Migrations are raw SQL outside the registry and stay off it. A fleet read that needs a range across workspaces declares its own index, `(due_at, workspace_id)` style, in its entry.

**What checks it.** Each check catches what the others cannot:

- the type rule (`store/workspace-scope.type-test.ts`): a global definition sees only install tables, a workspace definition needs a `WorkspaceDb`, and a caller cannot pass `workspaceId`;
- the source guard (`store/workspace-scope-guard.test.ts`): no table imported from a schema module outside the bindings, the migrations and tests; `preparedGlobal` only in the listed files; `preparedAcross` only with an allowlist entry; `asWorkspaceId(` only where a workspace is minted; no `'local'` workspace literal outside `self-hosted-workspace.ts` and the migrations;
- the scope audit (`store/workspace-scope-audit.test.ts`): it builds every registered definition and every censused raw statement and reads its SQL. Every workspace table a statement touches, in joins, subqueries and CTEs too, must be constrained by a top-level `AND` term `workspace_id = :workspaceId`, or joined to a table that is. A term under `OR` does not count. An insert must take `workspace_id` from the placeholder. A global definition touches no workspace table, and a cross-workspace one is a `SELECT` with an allowlist entry. A definition file carries the marker comment `// workspace-scoped (POD-6959)`, and a file without it fails;
- the two-workspace tests: two workspaces over one database (`openWorkspaceStores`, `test-support/workspace-stores.ts`) seeded with the same ids and natural keys and different content (`test-support/workspace-seeds/`). The group files (`store/*.workspace.test.ts`, `store/conversations/conversations.workspace.test.ts`) check every repository method: a read sees only its own workspace, and a write in one leaves the other's rows exactly as they were. `store/workspace-isolation.test.ts` is driven by the repositories a `SessionStore` builds and by the manifest. It fails by name on a repository it does not exercise and on a workspace table no seed fills in both workspaces. For the feeds, `describeTenantFeed` in `packages/sync/src/adapters/sqlite/sync-repository.suites.ts` proves a write in one workspace never reaches the other's feed. Like every store test they run on both engines (rule 9) unless `apps/server/test-store-engines.json` lists them; several are still `pending` there for Postgres.

**How to scope a repository**, and a new definition in one:

1. Import `inWorkspace`, `sameWorkspace` and `WORKSPACE` from `./executor/sync-drizzle`. Scope the shared predicate helpers first, so one edit covers every definition built on them.
2. `inWorkspace(t.x, …conditions)` is `x.workspace_id = :workspaceId AND …`, one flat `AND`. It takes an undefined condition, and `inWorkspace(t.x)` replaces a bare `.from()`. A join or a correlated subquery uses `sameWorkspace(a, b)`. An uncorrelated `IN` / `NOT IN` subquery gets its own `inWorkspace`. In a raw `sql` fragment write `alias.workspace_id = ${WORKSPACE}` in each scope.
3. Inserts: `workspaceId: WORKSPACE` in `.values()`, in every row of a many-row insert, and never in an upsert's `set` (the audit refuses that). When values and set share one object, spread it: `{ workspaceId: WORKSPACE, ...shared }`.
4. The constructor takes `WorkspaceQueries` and reads `queries.db`. A repository over install tables only takes `GlobalQueries`, uses `preparedGlobal`, and its file goes on `GLOBAL_REPOSITORY_FILES`. A package repository that cannot import the server's types declares a structural port with `db: WorkspaceHandle<…>`, as `SyncQueries` does.
5. A test or helper that builds a repository by hand builds it from `workspaceQueries(base, id)` and opens its transactions through that same runner: a workspace statement inside a global transaction throws.
6. Every full-row read (`select()`, `getTableColumns`, a bare `.returning()`) now carries `workspace_id`. Map it out before a row reaches a wire payload or a record value. Payloads do not change.
7. Add the marker comment, run `store/workspace-scope-audit.test.ts` and read its lines, then cover the file in its group's two-workspace test. Aim one workspace's deletes and updates at ids both workspaces hold: that is the case an unscoped `WHERE` gets wrong. A new repository or workspace table also needs an exercise in `store/workspace-isolation.test.ts` and rows in its group's seed, or that test fails by name.

A Postgres form (`dialectPrepared`) names its workspace the same way, with `t.<table>.workspaceId` from the binding.

**Change capture.** How each engine captures is in rule 9 and How queries execute, item 5. What the workspace adds: every source on a workspace table in `sync/record-sources.ts` declares `workspace_id` as its first key, so the captured row names its workspace on both engines. The drain refuses a captured row of another workspace with `ForeignCaptureError` (`sync/record-source.ts`) instead of appending a change to the wrong feed. The store's `SyncRepository` is built for the same workspace, so the change rows land in that workspace's feed in the same transaction.

**Caches are per workspace.** A cache, write hint, snapshot or memo filled from a workspace table lives on an object built for one workspace (a repository or a service of one `SessionStore`), or has the workspace in its key. Repositories are built per workspace, so their state is per workspace by construction: `WrittenColumns` on `SessionsRepository`, the settings snapshot on `SettingsRepository`, the per-operation loaders. A module-level map or slot filled from workspace rows keys by `(workspaceId, key)`. Member ids, session ids and machine ids are unique only within a workspace, so a key made of one of them alone can collide across workspaces. `store/workspace-caches.test.ts` holds each cache to this with the same key in two workspaces; a new cache gets a case there. The perf principal digests (`modules/perf/principal.ts`) hash `(workspace, principal)` for this reason. One known gap is recorded in that file: the table-write announcer (`store/table-writes.ts`) is the database's, so a write in one workspace makes every workspace's listeners drop and re-read (they hold no payload, so nothing crosses).

**Kind generations.** `sync_kind` is keyed `(workspace_id, kind)`. A data migration or boot repair that rewrites the model rows of some kinds bumps each kind in every workspace that has a feed, in the same migration. It starts at 1 where a workspace had none. `kindGenerationBump(kinds)` in `apps/server/src/sync/kind-tokens.ts` writes the statement, the same text on both engines:

```sql
INSERT INTO sync_kind (workspace_id, kind, generation)
SELECT feed.workspace_id, bumped.kind, 1
FROM sync_feed AS feed, (SELECT 'session' AS kind UNION ALL SELECT 'issueProjection') AS bumped
WHERE true
ON CONFLICT (workspace_id, kind) DO UPDATE SET generation = sync_kind.generation + 1
```

(`WHERE true` settles SQLite's parse of an upsert over a `SELECT`.) A bump that names one workspace, or no workspace, is wrong: on a hosted database it would leave the other workspaces' clients on stale records.

## Rules

Each rule has the reason for it and an example from this repository.

1. **Prepared once.** Every query is defined and prepared once, then reused. It is never rebuilt per call or per transaction.
   - Why: building a query in JavaScript costs far more than running it.
   - Example: preparing sessions-by-id once cut each call from 256.6 µs to 28.8 µs, so about 89% of the call was query building (POD-3854). Every repository query is now a module-level definition that takes its tables from the binding and names its workspace (see [Workspaces](#workspaces)), such as `const sessionById = prepared((db, t) => db.select().from(t.sessions).where(inWorkspace(t.sessions, eq(t.sessions.id, param(t.sessions.id, 'id')))).prepare())` in `apps/server/src/store/sessions.ts` (there through the `sessionsWhere` helper), called as `sessionById(this.db).all({ id })`: the workspace handle `this.db` fills `workspaceId`, so the caller passes only the id (POD-6147, POD-7015).
   - How: the helpers are in `packages/sync/src/adapters/sqlite/prepared.ts`. A comparison value is `param(column, 'name')`, so the column's encoder still applies; a `.values()`/`.set()` entry is `sql.placeholder('name')`. A query whose text varies by call (optional filters, a patch with varying keys, an `IN` list) is a `preparedFamily` keyed by a finite shape, never by a value; an `IN` list is keyed by `inListSize(n)` (0, 1, then powers of two) and padded with `inListValues`, so the number of SQL texts does not grow with list length.
   - Transactions: the store hands every repository ONE drizzle instance over the executor's ambient client, which routes each statement to the current transaction when it runs. A query prepared once is therefore valid inside and outside transactions; never build a per-transaction instance.
2. **No query inside a loop.** Data for a set of rows is loaded with one query per table (`… WHERE id IN (…)`), then joined in the operation.
   - Why: a query per row makes the statement count grow with the data.
   - Two standard tools: drizzle's relational queries (`with`) when an operation loads rows with their children, and a per-operation `dataloader` (the DataLoader pattern, on the read scope) when many call sites each ask for one row by id.
   - Example: `buildProjectionPass` (`apps/server/src/modules/sessions/view.ts:204`, POD-3855) loads issues, grants and queue counts for all sessions in one pass into a `ProjectionPass`. `view.projection-pass.test.ts` pins the same statement count at 5, 50 and 200 sessions.
   - **When the operation knows its set up front**, add a repository method that takes the ids (`getSessions`, `listForResources`, `automations.ownersOf`, `shipping.laneMemberIssueIdsMany`) and call it once before the loop. This is the first choice: it is plain, and the count is visible in the code.
   - **When many call sites each ask for one row by id** (a `mayRead(id)` callback, a resolver walking links), use a per-operation loader: `operationLoader` in `apps/server/src/store/executor/operation-loader.ts`, built on the standard `dataloader` package. Define it once as a field of the repository that owns the rows, expose a `loadX(id)` method, and call `invalidate()` from every write of those rows. Loads asked for in the same tick become one `IN (…)` query (split per 500 keys) per execution context (the root, a span's transaction unit, a post-commit drain: a batch runs in its first caller's context, so it never mixes them, POD-6197), and a row already loaded is reused for the rest of the operation. The operation opens the scope with `withReadScope` (`read-scope.ts`); outside an explicit scope each load is one live read, so nothing is shared by accident. Examples: `SessionsRepository.loadSession` (capability → principal, `apps/server/src/capability-principal.ts`) and `GrantsRepository.loadForResource` (every issue query handler runs in one read scope, `modules/issues/registry.ts`, so the per-row `mayRead` checks of a listing are one grants query). A loop that awaits each `mayRead` in turn batches nothing; ask for the set together (`Promise.all`) first, as `tree` does. A loader is a one-operation memo, never a cache.
   - **When one operation asks the same question in several phases** (an access check before its write span, a projection inside it, a reprojection or publication after it), the loader can memoise for the whole OPERATION: declare it with `perOperation: true` (`operation-loader.ts`). An operation is one daemon frame or one tRPC call; `withOperation` (`apps/server/src/store/executor/operation-scope.ts`) is opened at the daemon-frame dispatch (`gateway/daemon-mux.ts`) and on the base tRPC procedure (`trpc.ts`). It is a lifetime of its own, not a read scope, because read-scope slots assume nothing in their scope writes. Its memos end when the operation's function settles: work it left running (a timer, an unawaited effect) sees no operation and reads afresh, and nothing is shared with the next operation. Such a loader must be EXACT across writes, so its rows are written only through the repository, which calls `invalidate()` after every write and again after every commit of a write (subscribe it to the repository's `CommittedRows`). Every memo hit is checked against that version. Inside a write span that has written those rows, later reads go to a memo on the span's frame, so a savepoint rollback takes them with it. `GrantsRepository.loadForResource`/`loadForResources` are the first user (POD-6189: the session and relay paths read the same session's grants three to five times per operation); `SessionsRepository.loadSession` the second (POD-6210: the access check before a write to a parked session and the restore of that session for the write read its row once). `UsersRepository.earliestAdmin` and `SettingsRepository.getSettingsFor` follow (POD-6218): every session projection without an explicit reader acts as the earliest admin, and the runtime-event paths read that member's settings, so one runtime event asked for the admin about four times and its settings twice; now one statement for the admin's row and one read of each settings table per operation. `UsersRepository.get` (an account by id, every authorization's principal) is a per-operation loader too, and `earliestAdmin` hands it the admin's row. A memo shares a repeated key, never a different one: when a later phase will ask another key, an earlier phase asks for it too, in the same read. The grants loader reads every resource kind in one statement, and `loadForResourcesOfKinds` asks for several kinds at once; a session's access check and its published projection also read the session's own grants, which the publication's visibility pass asks for (POD-6217). Tests: `store/operation-loaders.test.ts` (read-your-writes across the span boundary, rollback, no reuse across operations).
   - **When the operation loads rows together with their children**, use drizzle's relational queries (Relational Query Builder v2 in drizzle-orm 1.0.0-rc.4): declare the relations once with `defineRelations(schema, (r) => ({ … }))`, pass them as `relations` when the drizzle instance is built, and read with `db.query.<table>.findMany({ with: { <children>: true } })`, which loads the parent and its children in one statement. The store does not declare relations yet; the first operation that needs this adds the declarations next to the schema and the `relations` option to the store's drizzle instance, and confirms the generated SQL with the query-plan audit (rule 3) and rule 9 (on SQLite it aggregates the children with JSON functions).
3. **Indexed lookups.** Every column used to look rows up has an index. The planner's statistics are kept current (`PRAGMA optimize` at boot and on a timer).
   - Why: without an index, a lookup reads the whole table; without statistics, the planner guesses.
   - Example: `messages.from_issue` had no index and `listLedger` asked `from_issue = ? OR (to_kind, to_id) = (...)`, so it scanned the whole `messages` table and sorted it in a temporary table. POD-6148 added `idx_messages_from_issue` and wrote the read as a `UNION` of one SELECT per arm, each reading its own index newest first, merged without a sort. `ANALYZE` had never run on the live database (research §3); the store now runs it at boot and `PRAGMA optimize` hourly (`refreshPlannerStatistics` in `apps/server/src/migrations/store-lifecycle.ts`). A table analysed while it held a few rows kept those statistics as it grew, and the planner scanned it as if it were still tiny (POD-6223: the runtime-event drain read all of `podium_events`); each refresh now drops the statistics of every table analysed below `PLANNER_STATISTICS_ROW_FLOOR` rows, so the planner treats it as large and takes its indexes.
   - Mostly-NULL columns: a column that is NULL in most rows (a soft-delete `deleted_at`, `issues.parent_id`) is indexed only over its other rows (`WHERE col IS NOT NULL`). ANALYZE counts each NULL as its own value, so a full index reads as a few rows per key, and `col IS NULL` seeks it and walks every live row (POD-7034: 36 statements on the operator's database). An IN list multiplies the per-key estimate by its length, so at a few hundred keys on such a column the planner prefers a scan; name the index with `INDEXED BY`. The audit plans every query again under a stored copy of the operator's `sqlite_stat1` (`test-support/operator-planner-statistics.ts`, refreshed at each release), each IN-list family at every padded size up to the largest its callers pass, and fails on an `IS NULL` walk, or on a scan or sort that its statement does not have in the modelled picture and no list explains.
   - Derived values: when a lookup needs a value derived from several tables, store it as one column on the row and index it. Keep it with triggers created by the same migration, which also backfills it; never with an application write after each input. Every writer of an input, including dynamic SQL and later migrations, then keeps it in the same transaction, and no operation's statement count changes. The first is `sessions.asks_user` (POD-7104): whether a session waits for the user, from its agent state, its offer and both checkpoints, computed by the view `session_asks_user` and sought by the "asking" collection through `idx_sessions_asking`, a partial index on the column itself, so the literal `asks_user = 1` is an equality seek and needs no `INDEXED BY` (as `idx_sessions_headless`). `collection-sql.ts` reads it in place of the clauses it answers, frozen to the migration's definition, and `store/session-asks-user.test.ts` holds it to the JavaScript rule after every writer.
   - How: `apps/server/src/store/query-plan-audit.test.ts` runs `EXPLAIN QUERY PLAN` on every repository query and fails on a table scan or a temporary B-tree sort that is not explained. It also plans every query under statistics from one-row tables (dropped by the refresh) and from tables at the floor and at a million rows, which must plan no query worse than the defaults: a read ordered by `id` needs an index whose order after its equality columns is `id`, because real statistics prefer the index with more equality columns and then sort (POD-6224: the runtime replay went through `(kind, subject, ts)`, whose `ts` is the agent's clock, and sorted the session's whole history; `(kind, subject, id)` serves it). An OR across different columns defeats an index; write one SELECT per arm. A literal in a partial index's condition must stay a literal in the query (a bound parameter cannot prove the condition), and the query must name the index with `INDEXED BY`: SQLite costs a walk of a partial index as a walk of the whole table, so it prefers any seek on another index (POD-6173, `openChat` in `store/messages.ts`). A key prefix is a range, `key >= prefix AND key < prefixUpperBound(prefix)` (`store/prefix-range.ts`), never `LIKE ?`, which reads every row. A new allowlist entry needs a reason that is bounded by something other than the amount of work. SQL handed straight to a database handle (`db.prepare(sql)`, the sync worker's `iterate(db, sql)`) is no repository query, so the same test censuses it in the server's and the sync package's source (`rawSqlSites` in `test-support/prepared-census.ts`, POD-6227): each raw statement is either planned like a repository query (`RAW_SQL_PLANNED`, with why it is raw) or exempt with a reason (`RAW_SQL_EXEMPT`: the drivers, migrations, the phone replica's own database). New SQL belongs in a repository; a raw statement fails the census until it is listed.
4. **Work in SQL.** Filtering, sorting, joining and counting happen in SQL, never by loading rows into JavaScript and working on them there.
   - Why: rows loaded into JavaScript cost memory and main-thread time for every row, needed or not.
   - Example: "which issue owns this folder" used to build and sort a row for every issue, several times per machine every five seconds, to pick one owner of a directory (POD-5941). Since POD-6155 one indexed query (`IssuesRepository.worktreeOwnerCandidates`) returns only the issues whose worktree could contain the folder, and `modules/issues/folder-owner.ts` ranks those few.
5. **Read only what is needed.** Select the columns that are used. Lists come in pages with a limit and a cursor. Never load a whole table.
   - Why: the cost of a read must follow what the caller needs, not how much data exists.
   - Example: `listLedger` caps its answer with `boundedLimit(q.limit, 200, 500)` (`store/messages.ts`). The RPC listings (`issues.list`, `tree`, `graph`) still load a full repository listing and filter it in memory, with no limit or cursor (research §5); new listings must not copy them.
6. **SQL lives in repositories.** Services ask by intent ("active issues visible to user U, next page") and never compose queries themselves.
   - Why: when all SQL is in one place, it can be prepared, indexed, counted and later moved to another engine without touching services.
   - Example: `MessagesStore.listLedger({ issueId, sessionId, limit })` (`store/messages.ts`) is an intent: "the delivery ledger for this issue or session". The caller does not know which columns or indexes answer it.
7. **Short transactions.** One operation is one short transaction with as few round trips as possible. Nothing inside it waits on the outside world.
   - Why: writes run one at a time, so a long transaction holds up every other write; on a remote database each round trip costs a network trip.
   - Example: `Authority.commit` (`packages/sync/src/authority/authority.ts:227`) authorizes, writes and appends the change in one transaction, and broadcasts only after the commit. On Turso a round trip was about 95 ms, and 371 statements sent one by one took 37 s against 0.22–0.88 s sent together (POD-3251).
8. **Statement counts are pinned.** Tests fix how many statements each operation runs, so the count cannot grow with the amount of data.
   - Why: a query added inside a loop is invisible in review and on small test data; a pinned count fails at once.
   - Example: `apps/server/src/store/prepared-loop-scaling.test.ts` counts query construction and execution at drizzle's prepare step, so a rebuilt query or a per-row query fails the test. `view.projection-pass.test.ts` (rule 2) pins a count across sizes.
   - How: `expectConstantStatements(pin, expected)` in `apps/server/src/test-support/statement-count.ts` runs one operation at a small and a large data size (default 5 and 200 rows), counts every statement at the driver seam (`probeStatements`), and asserts both counts equal `expected`. On failure it lists each query with its count at both sizes and marks the ones that grew. Pin the operation as production composes it, with a `check` that proves it did real work. Prove the pin armed with `expectArmed(pin, expected, plant)`: `plant` spies on something on the operation's path and adds one read per fixture row, and the pin must then fail with growth, so the fixture's size reaches the operation and the operation runs inside the counted window. An operation that opens its own connection (the sync worker) is counted through the pin's `count` hook (`sync-feed.statement-count.test.ts`). A loop you find but cannot fix inside the operation gets a sub-issue of POD-6140 and an `it.skip` naming it. 9. **One query, two engines.** The store runs on SQLite (self-hosted, desktop) and on Postgres (hosted), from the same repositories ([ADR 14](../adr/0014-postgres-store.md)). A definition is written once for both wherever the builder can say it; only where the engines differ does it carry two forms.
   - Why: hosted Podium runs on Postgres and is the primary target; self-hosted stays on SQLite. A query that only one engine can run either breaks hosted or forks the repository.
   - How: a definition is `prepared((db, t) => …)` and takes its tables from `t`, never from `migrations/schema.ts`, so the same text builds on each engine's own drizzle dialect and tables (`bindingFor` in `store/executor/binding.ts`). Prefer the portable form: an `IN (…)` list (`inListOf` + `inListValues`) over `json_each` on a bound list, `onConflictDoUpdate` naming every column over `INSERT OR REPLACE`, `.returning({ id })` over `last_insert_rowid`, an explicit key over `rowid`, a JSON document changed in TypeScript and written whole over `json_set`. Where the engines really differ (a JSON field read, `COLLATE NOCASE`, `julianday`, `json_group_array`, an `INDEXED BY` hint, search), write both forms with `dialectPrepared` (`store/executor/dialect-prepared.ts`), which type-checks that both arms take the same inputs and return the same rows. `store/dialect-census.test.ts` (lean gate) builds every definition on Postgres and flags computed text without `COLLATE "C"` in a compared or ordered position.
   - Values: repositories see the same values on both engines. Postgres stores native types (`timestamptz(3)`, `json`, `boolean`, `bigint`, text `COLLATE "C"`), and the driver converts them back to ISO strings, JSON text and numbers. So a timestamp is written in `toISOString()` form (the Postgres leg's strict mode refuses anything else), JSON compared as text is written `CAST(… AS TEXT)`, and external text has no U+0000.
   - Writes on a source table of a synced record go through `captureWrite` (`sync/capture-pg.ts`): on SQLite it is the builder as it is (the triggers capture), on Postgres the same write with its capture rows in one statement. The write census in `sync/capture-pg.test.ts` refuses any other Postgres write on a source table.
   - Tests: a store test runs on both engines (`bun run test:lane -- server-store-pg` is the Postgres leg) unless `apps/server/test-store-engines.json` lists it as SQLite-only with the reason. A statement pin counts the same on both engines (`expectConstantStatements` takes the engine); a different count is written `{ sqlite, pg }` with its reason. Plans: `store/query-plan-audit.test.ts` on SQLite, `store/query-plan-audit.pg.test.ts` on Postgres.
   - Example: `worktreesOfSessions` in `apps/server/src/store/user-layout.ts` used to match ids with `in (select value from json_each(…))` over a JSON string; a plain `IN (…)` list says the same in SQL both engines run.

## Caching

1. **The default is no cache.** Add a cache only after a fresh measurement shows the need. The order is: build it correct, measure, then fix.
2. **One interface.** Every cache sits behind one interface: get, get many, set, delete by key. The first implementation is an in-process LRU; a Redis implementation can replace it later without touching callers. The cache layer itself (POD-6150) is built when the final measurement shows the first real need, not before.
3. **Declared.** Each cache is registered with:
   - what it holds;
   - its key;
   - an entry limit;
   - the committed table writes that remove its entries.

   A test proves that a write removes the entry.
4. **Removed key by key, after commit.** A write removes only the entries it changed, and only once its transaction has committed. Never throw the whole cache away on a write. (The raw copy of `change_latest` that POD-6156 removed was dropped whole on every append and read again in full on the next visibility check; the visibility anchors now build the model records a batch names by key. POD-6771 also removes the durable copy; current values never come from the log.)
5. **Never read inside a save.** A save always reads the database.
6. **Never a whole-table copy.** There is no exception for small tables: with several users or tenants, "small" is multiplied, and several processes cannot share one in-memory copy.
7. **A write hint is declared like a cache.** A write hint is memory of what a row holds, used only to decide how a write is shaped. It never answers a read and never replaces a value; on a miss the write does the full work. It is registered with what it holds, its key, its entry limit, what forgets it, and the writers it assumes. The one write hint today:

   | | `WrittenColumns` (`apps/server/src/store/written-columns.ts`, POD-6234) |
   |---|---|
   | what it holds | for each session row, the values of its indexed columns as this process last wrote them, or last read them by id with no span open |
   | used for | `SessionsRepository.upsertSession` / `upsertSessions` leave an indexed column out of the ON CONFLICT set when its value is unchanged, so SQLite does not rewrite that index |
   | key | session id |
   | limit | 4,096 committed entries, oldest dropped first; staged entries are cleared at the same bound |
   | what forgets it | a write's rollback (staged until the outermost commit, a dead stage reads as unknown); a write with no span open; a read overtaken by any write, promotion or forget; every other write of `sessions` in the repository (`softDeleteSessions`, `restoreDeletedForIssue`, `detachTombstonesFromIssue`, `detachDanglingIssueReferences`, `purgeSession`), which runs through `WrittenColumns.aside` |
   | on a miss | the row is unknown and the upsert sets every column, which is what it did before the hint |
   | tests | `store/session-upsert-changed-columns.test.ts` (a narrow and a full database stay identical over a corpus of writes), `store/written-columns.test.ts` (each forget rule) |
   | **assumes** | **this process is the only writer of `sessions`.** A write by anything else (another server process on the same database, a later multi-process or Postgres deployment, a hand-run `UPDATE`) is invisible to it, and the next upsert would skip a column that no longer holds what the hint says. Before a second writer exists, disable the hint (every upsert sets every column) or invalidate it across processes. On Postgres, where several server processes may write one database, the store builds it disabled (`WrittenColumns.forDialect`). |

   A new write hint must state the same, and a change that adds a second writer of a table must check this list. The `asks_user` triggers (POD-7104) write `sessions` too, but only `asks_user`, which the hint does not hold.

## How queries execute

1. **Async everywhere.** Every data call is awaited through the store interface (POD-3221). The executor (`store/executor/executor.ts`) owns transactions, savepoints and post-commit work on both engines; the driver (`store/executor/driver.ts`) is the seam where an engine plugs in.
2. **The engine is chosen once, from the store's location** (`storeEngineFor`, `store-database.ts`): a file path is SQLite, a `postgres://` URL is Postgres. The server takes the URL from `PODIUM_DATABASE_URL` (environment only). The store-lifecycle port (`migrations/store-lifecycle.ts`) holds each engine's boot and maintenance steps, so nothing below the store asks which engine it is on.
3. **On SQLite** (`store/executor/bun-driver.ts`): one connection on the server's main thread (`readConcurrency: 0`), so rules 5 and 7 keep each query short, and every write runs one at a time.
4. **On Postgres** (`store/executor/pg-driver.ts`, `pg-types.ts`; POD-6958 design 2.3, 2.4): a pool of connections, reads in parallel, and **one writer per workspace**: a write transaction runs at READ COMMITTED and first locks its workspace's `sync_feed` row, so writes of one workspace run one at a time and different workspaces write in parallel. `BEGIN` and the lock go out with the transaction's first statement, and a write outside any transaction is one pipelined unit (`BEGIN; lock; statement; COMMIT`). Each statement waits for the network, so rule 7 matters more here: about 2.6 ms per round trip on hosted (POD-6992 counts them).
5. **Engine differences that reach query code:**
   - On Postgres a failed statement aborts the whole transaction, and its commit is refused (`PgTransactionAbortedError`). Code that catches an expected failure, such as a unique violation, inside a transaction catches it inside a nested transaction (`createOrJoinTransaction` opens a savepoint when nested) or a batch.
   - On Postgres only `int8` is converted to a number. A `numeric` result comes back as a string: `sum()` over a bigint column and `avg()`, for example. A Postgres arm casts it (`::bigint`, `::float8`) or the fragment declares `.mapWith(Number)`.
   - Change capture: SQLite captures with triggers; Postgres captures in the write statement (`captureWrite`). On both, a transaction that leaves capture rows undrained cannot commit, once the store has attached its capture (`StoreDatabase.attachChangeLog`); before that (the boot, a test store with no change log) nothing a write captured reaches a commit.
   - Write hints that assume one writer process (`WrittenColumns`, see Caching rule 7) are off on Postgres.
