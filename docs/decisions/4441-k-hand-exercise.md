## §5 Expectations (README-only) vs where things actually went

- A: expected rules + visible + order/groups + rows. Wrong about order/groups/rows — `VisibilityChanged` drives them with no code. The README list overstates; only the predicate, the flat check, and the tick-sensitivity bookkeeping (set + tick arm + bootstrap mirror) were needed.
- B: expected greenfield. Wrong — `continuationOf` (boolean) already existed inside `rollup.ts`, used to suppress the review ask. The new work was surfacing the LINE (`continued · <ref>` / `duplicate · <ref>` / `another task`, transcribed 1:1 from `mission.ts:2207`) in a `continuations` side map that rides commits exactly like `ticks`, never entering frozen `SliceRow`.
- C: expected a rollup ancestor walk. Half-wrong — `compute` already aggregates waiting over the visible subtree (the worked example's A-asks-because-B-waits), so the gap was narrower: asks from INVISIBLE formal descendants (legacy `rowWaitingCount` sums "visible children and rolled-up depth alike"). First probe setup failed instructively: an archived child detaches from the formal tree entirely (`parentEdgeOf` returns null for archived/deleted), so its asks are unreachable by construction; a `proposed` child stays edged and invisible — that is the shape that bubbles. Control check: with the walk removed, the probe fails (`asking` false); with it, passes. One incoherence noted, not fixed: root phase can now stay `working` while `asking` is true (legacy aggregates phase over the whole branch too — a follow-up, out of the brief's letter).
- C2: expected ~10 files including `shared/` and the UI. Wrong about both: `SliceRow` sufficed for lane rows (displayRef/title/band/repoKey all have lane analogues) and `HandRow` renders any row id, so no `shared/` and no UI change. Right about the scale: 7 files, +341/−19, the largest change by far. Three exercise-grade inventions with no spec behind them (recorded, not defended): lane displayRef/title (`prefix ?? path tail`, `repoName`), lane rank (`createdAt ''` sorts last in-band), group labels (founder-dependent: lane `repoName` vs issue path tail can differ within one repo group).

## §6 What the exercise surfaced beyond the diffs

1. Latent R3 gap (pre-existing, oracle-caught, fixed inside the C2 diff and marked there). An issue arriving AFTER unbound sessions already resolve at its path never attaches them: `resolveAllUnbound` only moves sessions whose ROOT changed, so same-root arrivals left `resolvedByIssue` stale while the bulk rebuild attached them. Bisected: with the attach loop neutralised, `membersOf` returns `[]`; with it, `['su']`, oracle green. At 1x mount the fix changes zero issue rows (classify: changed=0), so it is strictly a late-arrival correction. Recommend a home for it outside this exercise (it is not C2-specific).
2. My own first C2 epoch signal was wrong in exactly the foot-gun-E shape: it compared lane-ness for equality and went silent on lane→lane moves. The rebuild oracle caught it (incremental had the row, rebuild didn't — then vice versa after the fix... precisely: incremental missed it). Lesson recorded in the diff comment.
3. Asymmetry verdict (the coordinator's question). Verified: `mobx.1x.test.tsx` asserts `rowsCommitted == 1`, `commitsByRow == {i0:1}`, `rowsDerived == 1`, `rollupsDerived == 3`, `indexUpdates == 0` for the phase scenario; `hand.1x.test.tsx` asserts parity only. Equalise by raising the hand arm to MobX's standard — add the exact-count assertions to the hand 1x phase scenario (the arm already performs exactly one row there per its published counts, so the assertion is free). Rationale: commit counts are the comparison's currency and the decision order gates on them; the arm whose native test cannot catch a commit-count regression is held to a lower standard. Do not lower MobX to hand's level. (Note: at unit level both arms assert derivation counts in `hand.test.ts`/`mobx.test.ts` — the gap is specifically the 1x count-harness test.)
4. Methodology caveat for E. The §5.9 expectation ("parity oracle fails on scenario 6") assumes the scenario-6 evict removes a keeper. The 1x corpus evict does not, so the m2 gate is green on the E branch — silent. The expectation needs a corpus-shape qualifier, or scenario 6 needs a keeper-evict variant.
5. F is the coverage hole: every honesty mechanism (never-check, oracle, scans, fence, parity) prices the STORE, none prices the RENDER path. A full-list render does ~1M field reads at live corpus (~15.6 ms Node micro-calc, over the 8 ms scenario-#2 wall by itself) with zero automated signal. Only Chromium walls or the 2x/4x slope can see it.
6. Process notes (own mistakes, for the record). (a) I twice made content-free "edits" that concatenated two lines (store.ts:117, summary.ts ×3, rollup.ts tickOf); all were caught by parse/typecheck and repaired — an argument for reading back every edited region, which I then did. (b) A script-inserted `case` arm landed inside `groups.ts`'s clock body (fallthrough into grace-dirty); caught on re-read before any run. (c) The coordinator's mid-exercise mail found nine uncommitted files; committed immediately after, then per-change. (d) The coordinator's m2-gate reassurance checked out: my classify run shows legacy=3,332 rows, matching the corrected seed count.
