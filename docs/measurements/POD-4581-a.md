## 1. Fence steps at 1x

Instrument: `arms/hand/pool/counts.test.tsx`, "fence steps #1-#4, #8, #8b",
through `runFenceStep` (`harness/src/fence-scenarios.ts`). Each step asserts

`assertCommits` is asserted on #1, #2, #3 and #8. Cells:
`harness/browser/results/hand-pool-counts-1x.json` (git-ignored).

Since POD-4568's G2 (b29ea68ce), the shared fence settles a lazy arm's loads
itself:
- the mount's loads before #1, outside the count;
- each step's own loads inside the step, charged to it, through the arm's
  `settleLoads()`.
It then refuses a step that leaves loads pending or loads a row after its
settle. The hand handle gained `settleLoads()` for this (commit f2d75af10,
`arm.ts`). It flushes the arm's redraws, lands what they queued through
`pool.drainLoads()`, and repeats until a redraw queues nothing, as the MobX
arm's does.

- "Changed" is the row-view oracle's changed set.
- "Drawn" is the rows the list committed or remounted.
- "Reads" counts the distinct rows touched through the fenced tables and
  relations.

### What was fixed

At base, `activityAt` walked the `issue.sessions` bucket through
`relations.many` and read every member's row whenever any member changed.
The walk counts every id it yields, so a change to one member of a
7-session family read 7 sessions. This is the same trap Ma4 found in the
MobX pool.

The fix (commit 567943976, first 479b7338a; `views.ts`, `pool.ts`, `rebuild.ts`):
- **`sessionIds`** is a new part and the one reader of the bucket: the
  member ids, sorted. It re-runs only when the bucket's relation slot moves.
  A draft's title (lowest id first) and the `loading` part read it too, so
  neither walks the bucket any more.
- **`ViewInputs.sessionActivity(id)`** is one member's contribution
  (`sessionActivityOf`, its `lastActiveAt` in ms). In the live pool it is a
  cell per session (`HandPool.sessionActivity`, `sessionCells`) that reads
  that session's row. A cold or absent session reads as null, and its
  arrival re-runs the cell. The cell is disposed when the session leaves the
  pool: a row removal, or a cold session removed from the registry.
- **`activityAt`** re-composes from `self.sessionIds` and each member's
  cached value. A member's change re-runs that member's cell (1 row read)
  and then `activityAt`, which reads no row.
- **The rebuild** passes `sessionActivity` as a plain function over the
  same `sessionActivityOf`. *Correction (POD-4674):* this line used to say
  that this made the correctness gate hold both paths to the same rule. It
  did not. The gate compared only `sliceRowOf(view)`, and `activityAt` is
  not a slice field (POD-4598, H3-F3). The gate now also holds every
  resident issue's whole `RowView` to the rebuild's views at every step. A
  plant that caches member activity in a plain `Map` must fail that check
  on every seed.

This is the harness's shape for roll-ups: "re-compose from cached child
results" (`docs/plans/pod-4441-harness.md`, "Reads per change"). No scenario
is special-cased, and no dependency list is kept. The member cell declares
its input by reading it, like every other cell.

## 2. Correctness gate (L4b), 20 seeds × 300 steps, 1x

`checkArm`, rebuild-only, `oracleEvery: 0`). After every step, the
incremental pool's settled snapshot is compared with
`rebuildFromScratch()`. Every relation of every KNOWN row (cold ones
included) is compared with a from-scratch scan of the feed, and the hot/cold
partition with the feed. At step 299 the full-residency checkpoint runs:
every cold row is loaded, then compared with no input from the pool. The
change sequences are `gen(seed, 300)` over every change kind the L4a
generator draws. The feed is `overlaid`.

The rebuild runs the same `activityAt` rule as the live cells (`directParts`
with a plain `sessionActivity`). *Correction (POD-4674):* this paragraph used
to say that the gate therefore held the cached path to the direct one at
every step. It did not. The rebuild comparison covers only the slice fields,
and `activityAt` is not one of them (POD-4598, H3-F3). So this run did not
check `activityAt` incrementally. The per-step whole-view check that does
check it was added in POD-4674.
