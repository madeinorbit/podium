### What was fixed

At base, `activityAt` walked the `issue.sessions` bucket through
`relations.many` and read every member's row whenever any member changed.
The walk counts every id it yields, so a change to one member of a
7-session family read 7 sessions. This is the same trap Ma4 found in the
MobX pool.

The fix (commit 479b7338a, `views.ts`, `pool.ts`, `rebuild.ts`):
- **`sessionIds`** is a new part and the one reader of the bucket: the
  member ids, sorted. It re-runs only when the bucket's relation slot moves.
  A draft's title (lowest id first) and the `loading` part read it too, so
  neither walks the bucket any more.
- **`ViewInputs.sessionActivity(id)`** is one member's contribution
  (`sessionActivityOf`, its `lastActiveAt` in ms). In the live pool it is a
  cell per session (`HandPool.sessionActivity`, `sessionCells`) that reads
  that session's row. A cold or absent session reads as null, and its
  arrival re-runs the cell. The cell is disposed when the session leaves the
  pool: a row removal, or a cold session removed from the registry.
- **`activityAt`** re-composes from `self.sessionIds` and each member's
  cached value. A member's change re-runs that member's cell (1 row read)
  and then `activityAt`, which reads no row.
- **The rebuild** passes `sessionActivity` as a plain function over the
  same `sessionActivityOf`, so the correctness gate holds both paths to the
  same rule.

This is the harness's shape for roll-ups: "re-compose from cached child
results" (`docs/plans/pod-4441-harness.md`, "Reads per change"). No scenario
is special-cased, and no dependency list is kept. The member cell declares
its input by reading it, like every other cell.

### The plant: a sibling re-read fails #2 on its own

Ma4 found that at the old #2 target (3 members) a whole-family re-read cost
exactly the budget and passed. POD-4635 then moved the #2 target to a family
larger than one level's budget, so the fence can now see the re-read on its
own. `counts.test.tsx`, "a sibling re-read alone fails #2", holds the hand
pool to that. It plants the pre-fix activity, where each member's row is
read again inside `activityAt` over the cached `sessionIds`. The test
asserts:
- that the planted pool reads `{ session: 7 }`, which is the target's whole
  family;
- that the family is larger than the budget of 3;
- that `assertReads` throws `read 7 rows, budget 3`.

The same test runs #1 on the planted pool first, and that step passes.
Green at 479b7338a.
