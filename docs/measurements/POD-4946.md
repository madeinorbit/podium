# POD-4946 — window and native work per change

The actual web window and native SectionList now run the existing work-per-change meter at 1x and 4x. All sixteen scenarios pass the original neighbourhood bound, with parity at both scales and no new allowances. The window no longer rebuilds a per-row geometry cache; unchanged native lanes retain their section objects and data arrays.

## Count method and scope

The web roster keeps the bare, write-idle and write-pending variants and adds a window variant. A harness-only HTMLElement getter stub supplies the real PoolList scroll element with the browser lane's 1600 × 5800 px box. The mount asserts that it draws a non-empty strict subset of the visible list. There is no test prop or test renderer in the product module.

Native mounts the real `mountNative()` SectionList through `mountNativeForCounts`, using the same read fence, work meter, scenario writes, parity oracle and scale bound. Each step also checks the sections supplied by the real mount: equal lane contents keep both the Section object and data array by identity; an entirely unchanged section sequence keeps the outer array. This is the existing react-native-web lane, not phone CPU timing. Plain SectionList internals and React reconciliation are outside the meter, just as dependency internals are outside the web meter.

The parity oracle's cold inputs are primed once outside the measured changes; the renderer itself stays windowed. Counters are distinct row reads, derivation executions and distinct iterated collection elements. For each counter the unchanged rule is `4x − 1x ≤ neighbourhood at 4x`. The neighbourhood comes from the changed rows' families and the lanes they leave or enter. Work inside that neighbourhood may grow: for example a new row's touched lane contains 1,643 rows at 4x. This gate excludes growth with unrelated visible lanes, rather than promising constant-time pool membership maintenance.

## Negative controls

Every new check was made red on flatblock before its restored result was accepted. Each plant used a `cp` backup and `cp` restore, with a committed checkpoint before the run.

- **Original PL2**, `for (const id of group.rowIds) void groups.rankOf(id)` in WindowPlan: the new window variant fails six work verdicts. Stage move elements grow **940 → 2,863**, exceeding its 4x neighbourhood of **24** by **1,899**. New issue, archive, both eviction cases and the heartbeat derivation verdict also fail. Previously this path was not mounted by the count lane.
- **Window geometry/identity plants**: replacing unchanged lane payloads, making every estimate 56 px, and returning every index makes all three window-plan tests red. The real window mount also rejects drawing all 732 rows.
- **Native copied sections**: copying `data` on every update fails the actual mount's unchanged-lane array-identity assertion on stage move.
- **Native PL2**: the same whole-list rank walk makes five element verdicts red. Stage move grows **782 → 2,747**, exceeding its neighbourhood of **24** by **1,941**.
- **Skipped dependency work**: bypassing `virtualizer.getTotalSize()` fails the browser counter assertion with `keys=0 sizes=0 count=742`.
- **Hidden numeric index walk**: an extra loop calls getItemKey for every index but still returns the same 110 drawn items. The clock-free browser probe fails with `fixed window walked offscreen indexes: keys=852 sizes=110 drawn=110`. The product file was restored with cp before the green probe.

## Installed virtualizer cache and choice

Source read: the installed `@tanstack/react-virtual` **3.14.13** and `@tanstack/virtual-core` **3.17.11**, `src/index.ts`, `getMeasurementOptions` / `getMeasurements` at lines 1264–1425. The measurement-options memo depends on count, paddingStart, scrollMargin, getItemKey **identity**, enabled, lanes, laneAssignmentMode and gap. When these change it clears `pendingMin`; `getMeasurements` therefore starts at index zero. In the one-lane fast path it allocates/reuses a Float64Array and a per-index key array, calls getItemKey for every index, looks up cached size or calls estimateSize, and recomputes each start/size pair. This is a geometry-cache rebuild, not a DOM read of every row: this list did not supply measureElement.

Stable callbacks remove identity-triggered rebuilds but do not remove count-triggered rebuilds. estimateSize identity itself is not a measurement-options dependency. With stable getItemKey and unchanged count, same-count moves can leave cached keys and header positions stale in the default start-anchored mode; end-anchoring has separate edge-key invalidation. Real resize invalidation can restart at a changed suffix, but a changed count or key-function identity restarts at zero.

The isolated Chromium probe alternates the actual corpus lanes before and after a new issue, using immutable lane summaries and stable callbacks. Engine writes and pool derivations are outside the timed region. It asserts exact key/size call counts and equal total geometry, discards 20 warm-up samples and reports the next 100 at each scale. It is built with its own Vite entry, so it adds nothing to a measured arm bundle. All browser timings run on flatblock under `bench:flatblock`.

The decision is to remove TanStack virtualization **from this fixed-height list only**. The current contract already fixes rows at 56 px, headers at 40 px and overscan at five. One stable plan retains a segment table, memoizes each lane by id-array identity, changes the touched payloads and following offsets, and resolves pixels/indexes by binary search over lanes. It materializes only the viewport plus overscan and resolves fresh keys after moves and folds. The plan and native section caches are keyed by lane, not by row; no known-row index or peek caller is added. Existing row access, declared unloaded summaries and LOADING/batched-load behavior remain in place.

The 4x dependency rebuild is small in absolute time (**0.3 ms median, 0.6 ms p95**) but still visits every one of its roughly 2,938 indexes. The fixed window visits **110** at both scales. Its median was below Chromium's 0.1 ms timer resolution; zero-valued samples do not establish zero cost.

The timing samples came from the earlier lease-held probe (`1bb22def7`). POD-4950 reported previously queued package lint overlapping that lease, so the wall values are observational, not an isolated latency budget. The final probe (`f1c227201`) wraps the actual fixed-plan key/size callbacks and repeats the exact lookup assertions in `--counts-only` mode, which never reads performance.now or emits timing fields. The restored callbacks were green at both scales. This confirms the bounded index work independently of the clock.

The production browser lane at 4x passed stage-move and rename parity with zero over/under/stray row commits in all eight sample records (one warm-up plus three samples each). A separate smallest affected interaction observed real scroll routing: wheel input moved scrollTop to **10,000** and changed the first drawn id from **i4053** to **i17789**. Returning to the top and folding group **r0** reduced the sizer from **164,328 px** to **154,528 px**.
