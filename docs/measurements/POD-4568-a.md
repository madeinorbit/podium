### What was fixed

At base, #2 read every member session's row whenever any member changed. Two
parts did this:

- `activityAt` took the max `lastActiveAt` over the members' rows.
- The display title read the first member's row eagerly, for every issue,
  draft or not.

The fix (commit "activityAt re-composes from per-session cached values…"):

- A member's contribution is now a computed on the member's model
  (`SessionModel.activityMs`).
- The issue reads its bucket once (`sessionIds`, its own `computedStruct`) and
  re-composes from the members' cached values.
- The title asks for the first member only when the issue is a draft.
- The rebuild runs the same functions directly (`ViewInputs.sessionActivity`),
  so the correctness gate below holds the two paths together.

This is the harness's own shape for roll-ups: "re-compose from cached child
results" (`docs/plans/pod-4441-harness.md`, "Reads per change"). No scenario
is special-cased.

### Finding: #2 cannot catch a sibling re-read on its own

The #2 budget is 3 per level, and `i17` has exactly 3 member sessions.
Re-reading the whole family therefore costs 3 reads and passes. The base
failed only because a second part also read `i17`.

The test "pins the #2 finding" makes this reproducible. It plants a pool that
reads member activity from the rows again, and that pool passes #2 at exactly
`{session: 3}`, which equals the budget. For the fence's claim ("a roll-up
that re-reads a level's siblings … fails") to hold, the #2 target needs a
family larger than one level's budget. This has been reported to the
coordinator.
