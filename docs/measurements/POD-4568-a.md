### What was fixed

At base, #2 read every member session's row whenever any member changed. Two
parts did this:

- `activityAt` took the max `lastActiveAt` over the members' rows.
- The display title read the first member's row eagerly, for every issue,
  draft or not.

The fix (commit "activityAt re-composes from per-session cached values…"):

- A member's contribution is now a computed on the member's model
  (`SessionModel.activityMs`).
- The issue reads its bucket once (`sessionIds`, its own `computedStruct`) and
  re-composes from the members' cached values.
- The title asks for the first member only when the issue is a draft.
- The rebuild runs the same functions directly (`ViewInputs.sessionActivity`),
  so the correctness gate below holds the two paths together.

This is the harness's own shape for roll-ups: "re-compose from cached child
results" (`docs/plans/pod-4441-harness.md`, "Reads per change"). No scenario
is special-cased.

### Finding: #2 cannot catch a sibling re-read on its own

The #2 budget is 3 per level, and `i17` has exactly 3 member sessions.
Re-reading the whole family therefore costs 3 reads and passes. The base
failed only because a second part also read `i17`.

The test "pins the #2 finding" makes this reproducible. It plants a pool that
reads member activity from the rows again, and that pool passes #2 at exactly
`{session: 3}`, which equals the budget. For the fence's claim ("a roll-up
that re-reads a level's siblings … fails") to hold, the #2 target needs a
family larger than one level's budget. This has been reported to the
coordinator.

### F1: bucket upkeep proportional to the change

**Before.** A bucket was a sorted, frozen array. `pendingSet` copied it into
a `Set` and `flush` spread, sorted and froze it on every membership change.
That is O(bucket) per edge, while `indexUpdates` counted it as 1 slot.

**Now** (`relations.ts`). A bucket is an observable `Set` of member ids,
UNORDERED. The action's moves are netted per bucket (member → added, or
deleted), and `flush` applies each touched bucket's net moves once:
- one element per member added or deleted;
- the rest of the bucket is never read;
- moves that cancel out within the action notify nothing.

Any order a reader needs is applied at view time. `sessionIds` sorts its
members, because the draft title's "first member" needs an order. The
maintenance-only `members()` returns a sorted copy (a removed root's
members, a released repo row). `diffRelations` compares buckets sorted.

**The counter.** `stats.counters.bucketElements` counts ELEMENTS TOUCHED:
- each member added to or deleted from a bucket;
- each member moved once when a cold bucket turns resident (`promote`).

`PoolRelations.lastElements` holds the last action's count. `indexUpdates`
keeps its meaning (slots written). The README "Stats" section has the
definitions.

**Proof that it is armed, without the live export.** `relations.test.ts`,
"bucket upkeep is proportional to the change, not to the bucket (M3 F1)",
builds one `repo.issues` bucket and one `worktree.sessions` bucket (a
prefix link) of **4,000** members each. It then applies one insert and one
delete to each, and asserts **exactly 1 element touched per edge**. That is
O(1), so the bound is 1 per edge whatever the bucket's size.
- **Red** on the copy-and-sort code: commit 8869bf15e, which is the counter
  and the test on top of the old `flush`. The run fails with `new issue:
  expected 4001 to be 1`.
- **Green** from the next commit on.

**M3's probe** (`harness/review/m3-shape-probes.test.tsx`). The probe now

### F2: the views resolve relations through the engine

`views.ts` no longer resolves a relation itself:
- `repoTarget` is `inputs.relations.one('issue', id, 'repo')`, and `prefix`
  reads that repo's row.
- `originRef` is `one('issue', id, 'discoveredFrom')`. It is a KNOWN
  origin, which may be cold. `loading` reads it, and `originId` keeps only a
  resident origin, so the cold-origin loading check stays.
- The rebuild runs the same parts over the scan's `one()`. So the gate now
  holds the engine's forward slots to a from-scratch resolution through the
  row views as well.

The part was renamed from `repoRef` to `repoTarget` because
`installFields` refuses a model member named after a row field (`repoId`).
The `relations.ts` header and the README "Idiom" bullet are corrected. The
arm's lint now forbids `views.ts` from importing `relations.ts`
(`no-restricted-imports`). A planted `import { relationRef } from
'./relations'` fails the lint.

**Proof.** `relations.test.ts`, "the row views resolve relations through the
engine (M3 F2)", plants a wrong target into the engine's forward slot:
- **`issue.repo` → another repo.** The view's `displayRef` becomes `XYZ-1`,
  and the pool's snapshot differs from `rebuildSnapshot`, which still says
  `POD-1`.
- **`issue.discoveredFrom` → another issue.** The view's `originTick.id`
  follows the plant, and `diffRelations` reports the slot. `SliceRow` has no
  `originTick`, so the rebuild cannot see this one.

Before the fix, both tests FAIL. That run was in an isolated checkout of
619c99953, with `views.ts` and `models.ts` from 8869bf15e:

```
the view reads the engine: expected 'POD-1' to be 'XYZ-1'
the view reads the engine: expected 'I2' to be 'I1'
```

In other words, the old views never read the engine's slot.

**Side effect on the gate's plants.** F2 made the rebuild catch an issue
whose promotion was skipped. In the first default run after F2, the
promote-skipped plant (per-step checks off) was caught by the per-step
REBUILD, not the checkpoint, on all 3 seeds (seed 1: `row i168:
displayRef: "#169" (expected "POD-169")`). The gate counts that plant only
when the checkpoint catches it, so it went red. The plant now skips
promotion for sessions only. No view reads a session's forward slots, so
the checkpoint stays the only check that can catch it. Default run at
3628a36a1: caught by the checkpoint on 3/3 seeds (`session:s-g10.issue:
live null, scan "i119"`).

`flush` also now adopts a plain twin when it creates the observable bucket
of a resident target. `promote` runs first on every path today, so this
changes nothing observed. Without it, a skipped promote would silently drop
the twin's members.
