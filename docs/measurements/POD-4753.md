# POD-4753 — loading-aware closed reads: measurements

Host flatblock, node lane (`bun run test:file`, the checkout's own `.toolchain`
Bun), MobX 7.0.3. Counts, not timings: box load does not affect them. Corpus
cells from `harness/src/fixture` (`buildCorpus(1|4)`, `buildCorpusCell`), the
lazy MobX pool built by `mobxPoolArm.create` with its load window never
closing on its own.

## 1. The cached MobX `CaughtException` objects (coordinator note, POD-4747 N4)

POD-4747 reported 42,936 (h1a1) and 242,808 (h10a1) `CaughtException`
objects in the MobX arm's heap layer. Measured again in node with a V8 heap
snapshot (`node:v8` `getHeapSnapshot`, objects named `CaughtException`), the
pool bootstrapped over the same cell and every visible row read as a mounted
row reads it:

| Build | h1a1 | h10a1 |
|---|---|---|
| d9a6be7c2 (the build POD-4747 measured) | 42,953 | 242,825 |
| 8b6e5ae47 (this issue's base, after POD-4757) | 18 | 18 |

The 18 are the node process's own (the same with any pool); 42,953 − 18 and
242,825 − 18 are POD-4747's browser counts to within one run.

**What they are.** MobX creates every computed with `value_ = new
CaughtException(null)`, its "not computed yet" marker
(`mobx/src/core/computedvalue.ts:94`, 7.0.3). With error boundaries off
(`configure({ disableErrorBoundaries: true })`) the old build throws nothing
and still holds 42,953 of them. So they were computeds BUILT and never READ,
about 8.8 per known issue: the old startup pass (`syncWorklist` over
`knownIssueIds`) built visibility nodes for every known issue, cold history
included. Not a LOADING signal carried by exceptions, and not a latent fault.
POD-4757's filing reactions (one per issue in memory) already removed them.
