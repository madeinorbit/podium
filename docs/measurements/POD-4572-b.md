### What the misses are (diagnosed, not fixed here: POD-4686)

A CPU profile of the page built with `--minify false` (self time summed per
bundle chunk; the `mobx-*` chunk holds MobX and the pool's code), 10 samples per
scenario at 4x:

- **Stage move** is the one real O(visible) cost in the pool: every stage move
  runs the grouping layout once over the WHOLE visible order (`groups.ts`
  `layout` → `layoutOf`; counters `groupElements` 732 at 1x, 2,928 at 4x), then
  the virtualizer re-measures every item because the item list changed. The
  pool chunk's own time is ~3.6 ms at 1x and ~12 ms at 4x. Commits are already
  exact (no row redraws; the rows below the moved one shift). Making it follow
  the change means an incremental layout (move one id between lanes), a design
  change to Mb2's view-time grouping (Linear also sorts at view time).
- **Click** (selection plus the app's mark-read): the pool chunk's time is
  ~3.4 ms at 1x and ~8 ms at 4x, almost all MobX re-validating the 12–38
  per-node visibility reactions the click marks possibly stale
  (`runReaction_ → shouldCompute → ComputedValue.get`); no reaction involved has
  more than 18 direct dependencies. The count lane's click on an unread row
  re-validates none of them, so the page's state (every visible row resident
  after the first parity snapshot) matters; not found here.
- **Heartbeats and rename**: the pool chunk's own time is under 1 ms at 4x; the
  remaining excess is kernel, React and GC time on a page with a larger heap.
  The heartbeat's 1x p95 miss is 0.2 ms.

Filed as POD-4686 (discovered from this issue) with the profiles' method.

## 5. The console trap (M3 note N3)

- **Browser lane.** The pages are production builds, where MobX's enforcement
  warnings are compiled out (`__MOBX_DEV__` is `NODE_ENV !== 'production'`); a
  throw inside a reaction is still reported, through `console.error`. `run.ts`
  now fails a candidate arm's run on ANY console warning or error. Proven armed:
  `run.ts --arm mobx --console-plant warn` fails with `console warning: [plant]
  console warning`; `--console-plant reaction` fails with `console error: [mobx]
  uncaught error in 'Reaction[Reaction]' Error: [plant] thrown inside a
  reaction`. Every record of the matrices above ran under it.
- **Native lane.** `harness/native/mobx-pool.native.test.tsx` runs under
  `installMobxWarnTrap({ errors: true })` and proves it armed with a planted
  warning and a planted reaction error. Its first catch was real: React's
  "suspended resource finished loading outside act" from the lazily imported
  native list; the test now awaits that module inside an act.

## 6. Fixes found by this run, and whether each added a place to remember

- **A draft's title** (`pool/views.ts` `firstMemberOf`): the legacy names a
  draft after its first member that is not a shell, archived or headless
  (`sessionsForIssueNav(...)[0]`); the pool took its first member of any kind.
  Invisible at 1x and 2x; the 4x browser parity caught `i10142`, `i13682`,
  `i3081`. Test: `pool/worklist/draft-title.test.tsx` (every visible 4x draft's
  title equals the oracle's; a shell-first draft must exist). A/B on flatblock:
  the old rule fails it (`i13682.title: expected 'New Shell session' to be 'New
  Codex session'`), the fix passes. No new place to remember: the rule is in the
  one function the model and the rebuild share. The hand pool has the same rule;
  its lane was mailed.
- **POD-4671's allowance covers its class** (`known-gaps.ts`): the page's rescope
  stages the 2x corpus's rows but not its scans, so at the grown state seven
  issues' worktrees are unscanned (`i4944`, the 2x corpus's own orphan, and
  `i5950`, `i6651`, `i6875`, `i7502`, `i8964`, `i9549`). Reproduced in counts: a
  fresh 2x pool differs from the oracle on `i4944` alone, the rescoped one on
  all seven, each in seat fields only (`s5122` under
  `/repo-000/.worktrees/w00477/sub` links to the repo-root lane: `w00477` is
  never scanned after the rescope). No place to remember in the pool; a test
  exception that dies with POD-4671. The coordinator was told the rescope does
  not re-scan (an L5e harness question).
- **`knownTables` reads lanes and repos from the feed** (`pool/enumerate.ts`),
  the switch its comment assigned to Mb4: the relation check no longer leans on
  the pool's own tables.
