# POD-4705 (Mc3 follow-up): MobX pool lifecycle walls with lazy visibility nodes at 1x

L5e's lifecycle scenarios for the MobX pool arm with lazy IssueNodes
(POD-4705) against the same control, at 1x: cold bootstrap to first painted
list, principal switch over a fresh replica, rescope 2x then back, retained
heap after forced GC. Epic POD-4545; coordinator POD-4286. The question from
POD-4575 (Mc3, `docs/measurements/POD-4575-c3.md`): can MobX meet the
lifecycle budgets when nodes are built only for issues a derivation actually
reads, the way Linear does — or was the O(known issues) construction
intrinsic?

Corpus: `buildCorpus(scale, FIXTURE_SEED)` (L2d live-shaped fixture): 1x 4,867
issues, 4,304 sessions, 468 lanes, 732 visible rows. Feed: `overlaid`.

## 4. The CaughtException addendum (answered, no code change)

Mc3's heap snapshot showed 111,924 `CaughtException` objects (+1.8 MB) at
bootstrap. There is no throw site and no control flow: every MobX
`ComputedValue` is born holding `value_ = new CaughtException(null)` (its
placeholder until first compute), so every never-observed computed retains
one. Counted from outside at 1x (`_getAdministration`, `dependenciesState_`
NOT_TRACKING): **109,173** never-computed IssueNode computeds of 111,924
total (97.5%; remainder ≈ session/group/model placeholders, same
mechanism); per-node never-computed ≈ 22.4 of 32; direct reads of every node
getter throw nothing; `onReactionError` records zero errors across
mount/snapshot/settle. After lazy nodes: 42,934 (−62%). No separate bootstrap
number exists — the placeholders are a direct function of the eager node
count and fall with it.

## 5. What the experiment changed (and what it proved along the way)

`arms/mobx/pool/worklist/visible.ts`: `sync()` split into `ensure()` (named
ids only; updates keep what they hold) and `syncReplace()` (exact closure at
a replace, held outsiders leave). `arms/mobx/pool/pool.ts`: the replace
computes the visible closure in a plain non-reactive pass (`directVisibility`
over unfenced, overlay-aware reads — the control's ~109 ms shape) and nodes
visible/present/keeping rows plus ancestors, nest owners and formal
subtrees; updates ensure named rows plus session/worktree-linked rows gated
by a plain present/keeps/held-parent check (cold explicit-linked rows stay
out — warming covers them; cold lane-linked rows are evaluated, R3 never
warms); removals and clock ticks need no ensure (hide-only, proven). The
write layer (`pool/write/edit.ts`) ensures rows its pending overlays touch,
since only a derivation reads an overlay. `relations.ts` gains a fence-free
forward reader for maintenance.

Four correctness gaps found by the gates, all fixed, all with regression
cover: a reparented held row orphaned its subtree (ancestor walk verifies
the first hop); an R3 lane flip of a cold owner was skipped (lane-linked
cold rows are evaluated); a pending edit's visibility flip had no node
(overlay-touched rows are ensured); a replace dropped held roots (closure
membership includes held rows). Tests updated where eager behavior was
pinned: the lazy plant (`worklist/visible-lazy.test.ts` — eager fails
`4867 < 4867`), the no-op ingest (first-touch convergence), the L1d
precondition (hidden-by-absence), residency bootstrap reads (discipline, not
count). Gates green at the timed SHA: read gate, counts, visible + plants,
pool, scaling, bootstrap, first-paint, residency, models, relations (43),
rollup (7) + rollup gate, groups, write edit/settle/with-edits (3x200),
`gate.test.ts` (3x200), and the MobX truth gate **20x300 in four flatblock
chunks (1-5, 6-10, 11-15, 16-20), all green**.

## 6. Conclusion (decision input)

Lazy nodes move every construction-proportional number by roughly the node
ratio (2,112/4,867 = 43%): bootstrap observables −44%, IssueNode computeds
−57%, reactions −57%, CaughtException placeholders −62%, retained heap
−31%, bootstrap build −12%, switch wall −18%. Steady-state per-change work
is byte-identical. **All three lifecycle budgets still miss**: coldBootstrap
3.52x (budget 1.1x), retained heap 2.69x (budget 1.1x), principalSwitch 2.60x
(budget 2x); only the heap-growth budgets hold. The remainder is the
per-visible-row derivation cost the design keeps (32 computeds + 4 reactions
per node, now for 2,112 rows) plus the relation/table substrate for every
known row and a ~110 ms plain pass that replaced ~180 ms of node building.
Making nodes lazy answers the experiment's question in the negative as
framed: even at 43% construction the budgets do not come within reach, and
the remaining gap is per-kept-row derivation cost plus substrate, not
eager construction. Per §6 rule 19 / the G6 gate reading, the three misses
stay with this mechanism.
