# POD-4576 (Mc4): MobX growth and coexistence on the lazy arm

Did the MobX arm's cost per change stay flat as the data grew from 1x to 4x,
and can it run beside the legacy sidebar on one kernel? Epic POD-4545;
coordinator POD-4286. Baseline is the LAZY arm (POD-4705 landed as
`bebb6e3b9`: bootstrap 669.9 ms / 3.52x, retained heap 60.75 MB / 2.69x,
switch 570.5 ms / 2.60x; per-change counts byte-identical to eager).

Corpus: `buildCorpus(scale, FIXTURE_SEED)` (L2d live-shaped fixture): 1x 4,867
issues, 4,304 sessions, 732 visible rows. Feed: `overlaid`.

## 4. Stage-move attribution (addendum 2)

The pool side is proven O(change) by counts with plants
(`scaling.test.ts` at 1x and 4x, green): filings 1, key-index reads 0,
order elements walked 0 (counted through a proxy on the host seam, so
plain-map walks count too), moved lanes exactly once; the verbatim
whole-order `keys` mutation fails at 1x (731 walked) and 4x (2,927).

CPU profiles at 4x (CDP Profiler, unminified build, 10 prepared stage
moves each; `mc4-scratch/cpu-prof.ts`):

- Timed dispatch only, mobx page (1,112 non-idle hits): MobX
  dependency tracking (`get`/`has`/`bindDependencies`/`reportObserved`/
  `computeValue_`) ~34%, kernel replica row projection
  (`project`/`reconcile`) ~14%, the moved lane's re-sort (`rankSorted`/
  `rankOf`/`headRank`/`filedLabel`/`sortClosedFold`) ~7%,
  React + `PoolList` + virtualizer ~5%, GC ~0% (1 hit).
- Same window, noop page (843 hits): replica `project`/`reconcile` 74%.
- The shared projection grows steeply with the corpus for the SAME
  change: noop 1x → 4x projection hits 27 → 620 (~23x). `reconcile`
  rebuilds the kind's rows array as one linear merge over every
  survivor — O(kind) per change, in the frozen kernel/replica path
  every page pays (the floor's raw 5.5x on stagemove). Not mine to fix;
  filed to the coordinator.

Against the three named candidates: `PoolList`'s whole-`items` rebuild
0.5% (6 hits), `getMeasurements` 1.3% (14 hits), GC ~0%. None
dominates — no fix in the idiom; the mechanism above is the report.
The 4x excess (17.0 ms) is spread across constant-count per-change ops
running on a 3x heap, with the long-task storms §1 shows arriving with
the floor.

## 6. Conclusion (decision input)

- Slopes: click and clock within; heartbeat 1.74, visibleHeartbeat
  3.00, rename 5.08, stagemove 2.88 OVER. Rename's slope is
  near-noise-driven (1x excess 1.2 ms); clock's is ill-conditioned by
  rule (0.1 ms). The budget is not re-read.
- 1x walls: rename, click, clock within; heartbeat (tail), stage move
  and visible heartbeat OVER.
- Counts (the load-independent half) are flat at 1x/2x/4x: same fence
  budgets, no growth on reads, commits or derivations, exact parity.
- Heap: lazy cut ~30% per scale off eager; the remainder is
  per-kept-row derivation objects plus substrate, linear in the corpus.
- Stage move: pool O(change) proven; the 4x excess is shared O(kind)
  projection plus constant-count ops on a 3x heap — no arm-side
  walk left to fix.
- Coexistence: both sides count solo == co-mounted.
