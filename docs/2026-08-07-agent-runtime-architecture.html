Podium · Architecture Proposal · Agent Runtime

Sessions become servers. The terminal becomes an attachment.

An Agent Runtime that runs every harness headless-first behind one driver contract — protocol-native where the harness supports it, user-emulating where it doesn't — with the CLI/TUI demoted to an on-demand attachment, sessions that survive everything, and a topology that extends unchanged to other machines and the cloud.

status proposal for discussion date 2026-08-07 issue POD-1761 prior target-architecture v1/v2 · reattachment-design.md

§1The problem: the TUI is the engine, and everything else is scraped around it

Today a Podium agent session is an interactive CLI in a PTY. The chat view, agent mail, the steward, the superagent, drafts, and state classification are all layered around that terminal by reading its side channels and typing into its input box. The v1/v2 architecture docs deliberately kept this layer ("native substrate, structured intelligence") and it got us to market — but the code now documents its own ceiling:

  • Sending a message is a heuristic. typeText() in apps/server/src/modules/sessions/inbox.ts wraps the body in bracketed paste, waits 90 ms, sends \r, then polls the transcript for 1.6 s and re-sends \r up to twice because we cannot observe whether the TUI accepted the submit. That workaround is promoted to a manifest capability (submitVerification).
  • Reading the input box requires a second terminal. apps/daemon/src/composer-sync.ts runs a headless @xterm/headless VT emulator per flagged session just to scrape the composer, with two-identical-scrapes stability gating. Injection ("phase 4") is still unbuilt.
  • The PTY-as-API is an attack surface. A message body containing ESC[201~ escapes the bracketed paste and executes as keystrokes; sanitizeBody() strips control characters at render time as the only defense.
  • Blocking interactions are invisible or improvised. A permission menu or AskUserQuestion is classified from hooks and screen state; answering one headlessly means typing menu keystrokes. Grok mail delivery sacrifices a denied tool call because there is no blocking Stop hook.
  • Headless is bolted on, not the default. Three headless drivers exist (headless-drivers.ts) but only for superagent threads; a "real" session cannot be driven headless, and a headless thread cannot be attached to.

Meanwhile the product is moving to a world where most agents are background executors — non-native subagents across harnesses, fleet workers, eventually cloud sandboxes. For those, the interactive TUI is pure overhead: it exists so a human could look, at the cost of making every programmatic interaction a screen-scrape. The industry has landed on the opposite shape, and it works with subscriptions where the vendor allows it:

Two pieces of prior art bracket the abstraction space: ACP (Zed's Agent Client Protocol) standardizes exactly the client-facing half — JSON-RPC session updates plus session/request_permission as an agent→client request — and agentapi (Coder) is the degenerate case: an HTTP wrapper around an in-memory terminal emulator for agents with no protocol. Podium needs both ends under one roof, which is precisely what its Declared<T> manifest philosophy was built for.

The inversion, in one sentence: today the interactive process is the session and headless is an emulation; in the target, the headless session object is the session and the interactive terminal is one of several attachments to it.

§2The Agent Runtime: one contract, three driver families

We introduce one abstraction, the Agent Runtime: the machine-local service that owns agent sessions and exposes them to the rest of Podium through a single driver contract. Podium above the runtime (server modules, steward, superagent, mail, UI) speaks only this contract and never knows how a harness is driven. The contract has exactly six primitive groups:

  1. Lifecycle — create, resume, adopt (rebind after restart), stop, hibernate, kill. Same survival table as today (session-teardown.ts).
  2. Turns — send(input) with inputOrigin (human / controller / steward / mail / auto_continue / system) and delivery modes incl. steer (append to an in-flight turn where supported), interrupt().
  3. Interactions — every blocking ask (permission, question, plan approval, elicitation) reified as a durable, addressable PendingInteraction that anything can answer: policy, superagent, a human in the web UI, or an attached CLI. §4.
  4. Observation — one event stream per session (state transitions, transcript items, interactions, process events) under the already-approved causal contract of reattachment-design.md: bootstrap snapshot + cursor-fenced live deltas, provenance-tagged. Two watch levels: coarse (durable-synced, always on) and fine (live-only token deltas while a viewer watches) — §5.
  5. Attach — produce an interactive surface on demand, in whichever mode the driver supports. §5.
  6. Placement — sessions are addressed as (machine, session); handoff/placement stays a server concern, unchanged.

Under the contract sit three driver families. A harness may implement several; a selection policy (auth mode, platform, availability, user preference) picks per session at spawn:

Decision: the terminal family is a permanent tier, not a deprecation path. It is the only subscription-preserving way to run Claude Code, and the only way to run harnesses that never grow a protocol. What changes is its rank: it stops being the definition of a session and becomes one driver behind the same contract, and all its heuristics (submit verification, composer scrape, screen classification) become internals of one driver instead of semantics smeared across server, daemon, and web.

What this buys the dominant workload, stated honestly. For Claude-on-subscription the session mechanics do not change: the TUI process remains the engine, and the scrape/retry machinery survives — inside the driver. The wins for Claude are containment (one driver owns the heuristics instead of five modules), reified interactions (Claude's 15-event hook channel is the richest of any harness, so hook-sourced asks and hook-anchored receipts approach protocol fidelity), and honest receipts (§3). The inversion — the session object replacing the process as the thing Podium holds — is real only for the server and embedded families; this spec claims no more than that.

§3The primitive surface (code-level)

This is the load-bearing section: the complete set of primitives every harness session sits behind, whatever the family. Podium features may touch a session only through this surface — which is why it is built first, in front of today's PTY stack, and why getting it right makes codex-terminal → codex-server a driver swap no feature notices. Home: new package packages/agent-runtime, depending on @podium/harness (manifests), @podium/pty, @podium/transcript; the daemon composes it; the server sees its wire projection, zod-schema'd in @podium/protocol under a new runtime message family.

Five rules govern what belongs here:

  1. A primitive earns its place only if a Podium feature consumes it, and every family can implement it or honestly decline it (Declared<T> — consumers branch and degrade; no silent substitution).
  2. Guarantees are family-invariant; fidelity is declared. send() means the same thing on every driver — what varies is the declared mechanism/confidence, never the semantics.
  3. Every write returns a receipt or a typed refusal. Never fire-and-hope.
  4. Every read is causally enveloped — (observerGeneration, turnEpoch, cursor, provenance) per reattachment-design.md.
  5. Machine-transparent: every primitive relays identically over the daemon WS for local, remote, and cloud machines.

Two tiers, so rule 1 has counter-pressure. The core contract — lifecycle & identity, turns & control, interactions, observation, transcript, attach & lease, export/import — is what a new driver MUST implement or explicitly decline, and is all the conformance suite pins. The extended tier — draft, machine accounting (quota/usage), open-url, title, accent color — are feature seams carried on the same registry that never block a driver: a driver shipping only the core is complete. New primitives default to extended and must argue their way into core; without this tier boundary, the surface audit's own history shows the contract only ever grows.

Accounts are per-machine-per-harness, never per-session. Sessions touch them in exactly two places: SessionSpec.principal selects the account at spawn (and binding records it), and mid-session auth expiry is not a special path — it surfaces as a login interaction plus a turn failure typed auth-expired, answerable and escalatable like everything else. The login-helper mechanics — forwarding agent-opened URLs and OAuth callbacks to the operator's browser (today's browser-open relay) — deliberately stay behind these primitives: they are transport for the login interaction's payload, not surface. A feature never drives a login flow except by answering its interactions.

Session handle — identity & lifecycle

handle.binding: SessionBinding    // podium id, harness resume ref, process/scope identity, workdir, driver id
handle.stop() / hibernate() / kill()       // survival table unchanged; hibernate REFUSES without a resume ref
handle.snapshot(): SessionSnapshot         // one bootstrap snapshot: state + transcript position + open interactions + draft
handle.export(): SessionArchive            // harness-NATIVE files + resume ref + binding metadata; opaque-but-versioned per harness
handle.health(): { alive, memoryBytes, scopeUnit, oomEvents }   // feeds hibernation policy + host metrics

Guarantee: the resume ref is captured as early as the harness allows, and the capability declares when that is late (Codex's lazy rollout files). And the archive guarantee: an archive is sufficient for runtime.import → resume to continue the conversation on any machine with the same harness. export()/import() are byte-faithful to the harness-native store (Claude project JSONL, Codex rollouts, opencode sqlite) — this pair is the basis for cross-machine handoff (what handoff-package.ts builds today), cloud migration, disaster recovery, and scheduled backup (the native files are append-mostly, so incremental export is cheap). It is deliberately distinct from the display transcript below.

The identity triangle: binding = live identity (who and where the process is), snapshot() = observation bootstrap (what the causal contract needs to resume watching), export() = portable archive (what another machine needs to resume the conversation). Three artifacts, three disjoint consumer sets — implementers must not merge them.

Turns & control — the one write path

handle.send(input, { origin, principal, delivery: 'when-ready' | 'queue' | 'interrupt' | 'steer' }): TurnReceipt
  // principal: the ACTING principal (opaque tag) — carried through queueing so the server's
  // drain boundary re-authorizes as the real sender, never as a system default (W3-review F3)
  // TurnInput: text + attachments (refs from stageAttachment) + Declared per-turn overrides (model/effort)
  // 'steer' appends into the open turn — Declared: native on codex (turn/steer); embedded/terminal degrade to
  // 'queue', and the receipt REPORTS the downgrade (deliveredAs) — no silent substitution
handle.stageAttachment(bytes | path): AttachmentRef  // lands the file on the session's machine in the form the harness accepts
handle.interrupt(): void          // REQUESTS a fence; the fence is emitted only on provider confirmation —
                                  // never manufactured (reattachment-design invariants: fences are absorbing, state is never fabricated)
handle.answer(interactionId, answer): void   // idempotent; typed error if expired/already answered

Guarantee: send resolves to exactly one of accepted (turn opened; receipt carries the new turnEpoch and the delivery actually used), queued (durably, with position), refused (typed reason: needs_user, lease held, …), or — terminal family only — unverified: the keystrokes were delivered but acceptance could not be proven inside the verification window. Unverified is the two-generals gap made explicit instead of retried into a lie; callers decide (retry, surface, wait for the transcript echo) with the truth in hand. Terminal receipts are hook-anchored where a causal hook exists — Claude's UserPromptSubmit is the accept signal, exactly as reattachment-design anchors turn epochs to it — and fall back to transcript verification only where no hook channel exists. This single verb subsumes today's typeText / queueText / sendTextWhenReady / interruptText — chat, mail, steward, superagent, and auto-continue all become callers of it with different origin.

Failure semantics

Errors are not a primitive — they are a normalized vocabulary threading through the three channels the surface already has. Every failure is exactly one of:

  • Refusal (synchronous, expected): a typed reply to a verb — send refused needs_user, configure unsupported per Declared, hibernate without a resume ref. The caller handles it; nothing is "wrong."
  • Turn failure: TurnFailed{ reason: rate-limit | auth-expired | context-overflow | provider-error | timeout | interrupted } in the causal stream — a small normalized vocabulary with the harness-specific detail preserved as diagnostic payload (generalizing today's superagent/harness-error.ts mapping to all consumers).
  • Process failure: process events — exited with exit classification, oomKilled, adopted.

One routing rule keeps sessions unstuck: every failure is classified retryable | needs-human | fatal, and needs-human failures materialize as PendingInteractions (auth-expired → a login interaction; context-overflow → a recovery interaction). Transport/runtime failures (machine unreachable, driver crash) are deliberately outside session semantics — the session may be alive and adoptable even while the path to it is down; conflating the two is how ghost sessions happen.

Composites: the procedures layer

The rule for where an operation lives: primitive if it needs driver-private access or varies per harness in semantics; procedure if it is pure composition whose variance is only mechanism/timing. Procedures form a thin layer inside agent-runtime — above drivers, below features:

procedures.interruptAndSend(handle, input)   // generic: interrupt() → await fence → send()
procedures.askAndAwait(handle, input)        // send + await the matching turn-completed
procedures.oneShot(spec, prompt)             // ephemeral spawn → send → await → kill; drivers override with
                                             // native one-shot forms (claude -p, codex exec --ephemeral)
// a driver MAY override a procedure when the harness has a native/atomic form
// or a peculiarity: driver.procedures?.interruptAndSend

Generic implementation by default, declared override when a harness needs one — the same house pattern as the manifests, so peculiarities stay inside the driver that owns them instead of leaking into features. Composites so common they are effectively sends are folded into the surface as delivery modes instead: send(delivery: 'interrupt') is interrupt-and-send, implemented natively per driver (Codex: turn/interrupt + turn/start; terminal: ESC + settle + paste with its timing lore).

Deliberately not in the surface — the things features must stop touching, because they are what makes the current coupling unswappable: raw PTY writes, hook ingest, transcript file paths, abduco socket names, screen/VT state, harness settings files. All of that becomes private to drivers; the frame stream itself appears only inside an AttachEndpoint.

Deliberate omissions, stated so they read as decisions rather than oversights: shell sessions are degenerate terminal-family sessions with every capability declined (no transcript, state, draft, interactions) — same surface, no special case; slash commands have no primitive — they are reachable only through terminal attach, and that stays true until a feature actually needs structured commands; capability degradation (e.g. the Codex hook version gate refusing an unrecognized CLI version) surfaces through inventory diagnostics, not a new channel.

The conformance suite is what makes the swap safe. The surface is pinned by one shared driver-conformance corpus — send accepted/queued/refused/unverified, interaction asked→answered, interrupt requests-then-fences, snapshot→adopt round-trip, event causality under restart — that every driver must pass, in the style of the repo's characterization gates. Crucially, the suite also names, per family, what a driver is permitted to fail or decline: the terminal family may return unverified sends, and its classifier-sourced interactions are at-least-once with best-effort identity. A suite without that list proves nothing about the hardest driver. When codex-server lands it passes the same suite, the selection policy flips, and no server module, view-model, or feature changes — because none of them ever knew more than this surface.

Third-party protocol churn (server family)

The server family's crown jewels ride pre-1.0, vendor-internal protocols — codex app-server has already renamed its approval methods once; opencode's API is still settling. The stance: (1) each server driver pins the harness versions it speaks, in the house pattern of the codex-hooks minor-version gate — refuse loudly with a machine diagnostic, never guess; (2) drivers carry recorded-fixture contract tests per pinned version, so a vendor rename fails in CI, not in a user's fleet; (3) protocol capability handshakes (app-server initialize) are used for negotiation where offered; (4) the terminal driver is a permanent fallback for every harness that has one — a protocol break degrades Codex sessions to the terminal driver instead of stranding them. Stated consequence: phase 5's deletion list is contingent — the Codex scrape stack leaves the default path, not the tree, until the vendor protocol carries a stability guarantee.

Three things are deliberate here:

  • send() returns a receipt, not hope. For server/embedded drivers the receipt is the protocol ack (e.g. Codex turn/started). For the terminal driver the receipt is hook-anchored where a causal hook exists (Claude's UserPromptSubmit) and submitVerification-derived otherwise — and when neither proves acceptance, the receipt says unverified instead of retrying into a lie. Callers stop caring which mechanism proved delivery; they must care that terminal proof can be inconclusive.
  • The event stream reuses the approved causal contract. reattachment-design.md (checkpoints, observer generations, turn epochs, terminal fences, bootstrap-vs-live provenance) was written for the PTY stack but is driver-agnostic. Server drivers get trivially strong cursors (Codex thread id + event seq; opencode session id + event offset) in place of file inode+offset ProviderCursors. One SessionObservationCheckpointV1 shape covers all three families; only the cursor material differs — it is already per-harness.
  • adopt() is first-class. The supervisor restarting must find surviving session processes (abduco masters today, harness server processes tomorrow), rebind by exact identity, emit one bootstrap snapshot, and continue — the reattach flow stops being a PTY special case and becomes the same verb for every family.

The AgentManifest gains one axis instead of growing more flags:

The existing headless/exec manifest axes fold into this over time: a superagent thread becomes an ordinary runtime session with no attach and a dontAsk-style interaction policy, deleting the parallel headless-drivers.ts/durable-headless.ts plumbing once server drivers carry those harnesses.

§4PendingInteraction: nothing blocks invisibly, nothing gets stuck

The single most valuable thing Codex and opencode both did is reify the blocking ask as addressable server state. Podium adopts this as a first-class aggregate, because it is the mechanism that makes fully-headless workers safe:

interface PendingInteraction {
  id: InteractionId
  sessionId: PodiumSessionId
  kind: 'permission' | 'question' | 'plan-approval' | 'elicitation' | 'login' | 'recovery'
  payload: …                     // tool + input for permission; options for question; plan text; url for login
  askedAt: number
  source: 'protocol' | 'sdk-callback' | 'hook' | 'screen-classifier'   // provenance ⇒ confidence
  answerable: 'structured' | 'keystroke-emulated'
  policyVerdict?: 'auto-allowed' | 'auto-denied' | 'escalated'
  expiresAt?: number             // escalation deadline, not auto-deny
}
  • Where they come from. Server family: Codex server→client approval requests and opencode permission.updated events map 1:1. Embedded: canUseTool and AskUserQuestion invocations map 1:1 (the callback parks on the interaction and returns when it is answered). Terminal: synthesized from hooks (PermissionRequest, Stop-with-question verdicts) and the screen classifier — flagged keystroke-emulated, answered by the composer/menu driver.
  • Who answers. In order: a per-session interaction policy (allow-lists, "always" rules, sandbox-aware auto-answers — the orchestration analog of dontAsk); then optional superagent triage; then escalation to a human as a durable, oplog-synced object that renders in the web UI, the Tray, mobile, and any attached CLI simultaneously. Answering from any surface resolves it everywhere.
  • Any lifecycle phase, including STARTING. Resume-time prompts — "session fell out of cache, resume from summary?", trust re-prompts — are kind: 'recovery', asked while the handle is still starting. Policy default for every role profile: resume the full session; summary-resume is chosen only when the harness offers no full path, and is then recorded on the session. Background executors auto-answer these and never stall on startup.
  • Why sessions stop getting stuck. "Stuck" today means a blocking prompt nobody saw. Under this design a blocked session is, by construction, a session with an open PendingInteraction — enumerable (runtime.interactions.list), alertable, escalatable after expiresAt, and answerable without attaching a terminal. The steward's nudge machinery narrows to genuinely idle sessions.

Phase-1 deliverable, called out honestly: the per-kind payload and answer schemas — normalizing Codex approval requests, opencode's once/always/reject, the SDK's canUseTool/AskUserQuestion shapes, and classified terminal menus into one typed vocabulary — are the hard part of this aggregate and are specified in phase 1, not in this doc. And interaction identity on the screen-classifier path is best-effort by nature: a re-rendered menu can mint a duplicate ask, and a keystroke answer cannot prove it acted on the exact menu it classified. source makes that visible; consumers of classifier-sourced interactions must treat asked→answered as at-least-once, never exactly-once.

This also subsumes agent mail's blocking-boundary tricks: mail delivery for server-family drivers is just a send() with delivery steer or queue — no Stop-hook blocking, no sacrificial denied tool call. The Grok workaround survives only inside the Grok terminal driver.

§5The session surface: observation, control, attach

Everything Podium does with a running session happens on one of three planes. The first two are the contract — always on, for every family, no attach involved. Only the third is "attach," and it means exactly one thing: a live terminal. The litmus separating them: attach acquires something side-effectful on the agent's machine (a process, a lease); observing and writing acquire nothing.

Plane 1 — Observation (read; always on)

The runtime holds one standing connection per session to its engine regardless of whether anyone is looking (Codex: the JSON-RPC connection to that session's app-server; opencode: the SSE stream; terminal: transcript tail + hooks; embedded: the SDK's own stream). What varies is the watch level, never the connection:

  • coarse (always): turn started/completed, transcript items as completed, state transitions, interactions, process events — durable-synced through the oplog. These feed the board, recency, notifications, and the steward: the low-cadence keep-everything-up-to-date signals, no viewer required, ever.
  • fine (while watched): token-level message deltas — live-only class, never persisted. When at least one chat view is open on the session, client-core subscribes and the server raises the watch level; the driver maps it to the harness mechanism: Codex literally has the knob (optOutNotificationMethods suppresses item/agentMessage/delta; raising watch enables it), opencode's SSE bus streams deltas regardless and the runtime forwards instead of discarding, terminal/embedded streams already flow. Refcounted; closing the last viewer drops back to coarse.

This is where the durable-synced vs. live-only message classes from the v2 protocol taxonomy land their natural tenant: coarse observation is durable-synced, fine deltas are live-only.

Plane 2 — Control (write; always available)

send() (with its delivery modes), interrupt(), answer() — origin-tagged, receipt-returning, lease-arbitrated. Steward nudges, agent mail, auto-continue, and a human typing into chat are the same verbs with different inputOrigin. Worked example on Codex: type in chat → send() → turn/start → the receipt on turn/started reconciles the optimistic bubble; a mid-turn approval arrives as a server→client request → PendingInteraction → inline card in the same chat → answer() resumes the turn. opencode: identical shape over POST /session/:id/message + SSE + the permission reply endpoint.

The chat view is therefore not a session surface at all: it is Podium's UI over observation(fine) + control. It attaches nothing, spawns nothing, holds no lease, admits unlimited concurrent viewers, and works identically for all three families — which no terminal mode does. If viewing chat required an attach, headless sessions would be broken by definition.

Plane 3 — Attach (a real terminal, on demand)

One user-facing verb; what you get is a live terminal. Internally the endpoint declares its lifecycle coupling to the session — determined by the driver family, never chosen by the user:

The supervisor, reaper, scope hierarchy, and crash handling all branch on this coupling — the distinction exists whether or not it is named, so it is named once, on the endpoint type, and nowhere user-facing: both render as the same "Terminal" tab fed by the same frame stream. (embedded sessions have no terminal endpoint — observation + control are their whole surface; the handover idea is deferred, see below. The names are deliberately not "cli": both hand you a CLI — what differs is whether you are connected to the engine itself or to a client of it.)

Placement — a client-endpoint question only

Engine terminals live where the engine lives, by definition. Placement is a real choice only for client terminals:

  • on-machine, streamed (the default and the only v1 mode). The runtime spawns the TUI client on the agent's machine, hosted exactly like an interactive session today: in a PTY, under abduco, in its own scope. Its frames stream through the existing relay to every surface Podium already has — web, Tauri desktop, mobile, podium attach. No new transport, no new auth surface; typing latency is identical to today's interactive sessions, so nothing regresses.
  • user-local, direct (deferred, evaluate before committing). The TUI process runs on the user's machine and connects over the network (the literal codex --remote ws://…-from-a-laptop shape). Potential input-latency win, but: it doesn't fit the web-wrapped UI at all (desktop is Tauri around web; mobile can't run a harness), it opens a real auth/security surface (exposed sockets, token handling), and the benefit is harness-implementation-dependent. Gate: measure streamed-attach input latency first; build this only if a concrete, felt gap exists — and then only as a power-user CLI path, never a requirement.

Warm attachments

Attach must be instant for the sessions a user is actively bouncing between, so client terminals are parked, not killed: on detach (user navigates away, closes the tab), the TUI client stays alive under abduco and the runtime keeps it warm for an idle TTL (default ~30 min, configurable). Re-attach within the TTL is an abduco reconnect — milliseconds, same mechanism as parked interactive sessions today. The reaper closes attachments past TTL, and under memory pressure attachments are the first thing reclaimed (they are pure convenience; the session engine is untouched). Attachment lifecycle is strictly subordinate to the session: hibernate/stop/kill the session ⇒ its attachments die with it. (Engine terminals need no warming — they are the session, which is what parking already handles today.)

Deferred: tui-handover for embedded sessions. For harnesses with resume-but-no-server (Claude on the embedded driver), the only way to offer the vendor TUI is a serialized handover: pause headless driving at a turn boundary, release the lease, spawn claude --resume <id>, and reverse on detach. This is an ownership transfer with genuinely hard failure modes (crash mid-handover, mail arriving while a human holds the engine), and the judgment call is that it will be buggy in proportion to how rarely it's used. So: not built until proven necessary. Embedded sessions are chat-only; the honest trade is "best headless fidelity, no native TUI," stated in the UI. The contract keeps the endpoint variant reserved so adding it later is additive.

type AttachEndpoint =
  | { kind: 'engine'; stream: TerminalStreamRef }                            // terminal family; existing frames path
  | { kind: 'client'; placement: 'on-machine'; stream: TerminalStreamRef;    // TUI client under abduco, streamed
      warm: { ttlMs: number } }
  // reserved, deferred: { kind: 'client'; placement: 'user-local'; connect: {…} }
  // reserved, deferred: { kind: 'handover'; lease: SessionLease; argv: string[] }
// NOT attach: chat, status signals, mail, steward — those are events()/send() on the session handle

One control lease per session, extending the existing binding/lease machinery (binding-store.ts, observation leases): exactly one driver-controller (the runtime) or one human-controller (an attach in take-over mode) holds it; spectators are unlimited. The lease is what makes "the user attached and started typing" and "the steward tried to nudge" impossible to interleave: controller writes are serialized through the same funnel, and headless drivers refuse send() while a human holds take-over (queueing instead, exactly like queueText today). For server-family sessions the harness serializes turns on its side too; the lease still arbitrates Podium's own writers. This generalizes exclusiveInteractiveResume from a Claude quirk into the actual concurrency model.

CLI surface: podium attach <session|issue> resolves the variant from the family (client for server-family, engine for terminal-family; for an embedded session it says so and points to chat), and --takeover/--peek selects controller vs spectator. Uniform across families and machines — for a remote machine the server relays, as PTY frames already relay today.

§6Process topology: one supervisor per machine, one process tree per session

Two questions were asked directly: one server per machine, or one process = one server? And how do sessions stay alive independently of Podium without dying together?

Decision: exactly one Runtime Supervisor per (machine × instance) — it is the evolved daemon — and one isolated process tree per session under it. The supervisor is control plane only: it launches, adopts, observes, and brokers. It is never the durability boundary and never shares an OOM fate with sessions.

  • Supervisor = daemon. apps/daemon keeps its identity (instance partitioning of ports/state/HOME per multi-instance.md, WS to server, frame-handler registry per the v2 doc). packages/agent-runtime becomes the heart it composes. No new long-running service is introduced — "runtime" is a role of the daemon, which matters operationally (one thing to install per machine, unchanged).
  • Session processes, per family. terminal: the abduco master hosting the CLI (unchanged). server: the harness server process itself (codex app-server on a per-session Unix socket; opencode serve on a loopback port), plus its agent children. embedded: a runtime-owned worker child process running the SDK loop — not in the supervisor's heap, precisely so a runaway embedded session cannot OOM the daemon (today's in-process claude-sdk driver moves out).
  • Attachment processes live beside the session, not inside it. An on-machine client-terminal attachment (§5) is a PTY process under abduco like any interactive session, placed in its own scope sibling to the session's (…-sess-<id>-attach.scope): it can be reclaimed independently, its memory never counts against the agent's budget, and it dies automatically when the session does. Warm-parked attachments are simply these scopes outliving their viewer connection until the TTL/reaper closes them.
  • Local sockets are an attack surface, treated as one. v1 creates one harness-server endpoint per session. Rules: Codex speaks over a per-session unix socket, mode 0600, in the instance state dir — never TCP. opencode binds loopback TCP, so every per-session port requires a per-session random secret via its server-password mechanism — an unauthenticated per-session HTTP server holding a credentialed agent is not acceptable even on loopback, which every local process and user can reach. Correlation secrets ride the spawn env, never argv (the hook-port discipline, unchanged); the multi-user threat model is written down before phase 3 ships; and the conformance suite includes a connect-without-the-secret refusal test.
  • Dedicated process per session — pooling is a driver-internal placement, not a mode. Codex's app-server can host many threads in one process; the contract doesn't care, because a driver already maps sessionId → (endpoint, thread). But pooling changes real guarantees, not just implementation: per-session MemoryMax and OOM/crash isolation only exist when session = process (a cgroup bounds a process tree, not a thread), and one pooled-server crash becomes N simultaneous process.exited events. So: v1 ships dedicated only; pooled placement is a later, opt-in driver config declared in capabilities (per the Declared<T> rule — a pooled session visibly lacks the per-session isolation guarantee) rather than a new mode in the taxonomy.

Reliability: cgroups, not luck

The abduco layer already discovered the right mechanism — systemd-run --user --scope so masters survive daemon redeploys. Generalize it into an explicit hierarchy on Linux:

podium-<instance>.slice
├─ podium-<instance>-daemon.service|scope        # the supervisor
└─ podium-<instance>-sessions.slice
   ├─ podium-<instance>-sess-<id>.scope          # one per session process tree
   │    MemoryHigh= (throttle)  MemoryMax= (kill THIS session only)
   │    TasksMax=  OOMPolicy=continue
   ├─ podium-<instance>-sess-<id>-attach.scope   # warm client-terminal attachments; reclaimed first
   └─ …
  • No collective OOM death. Per-scope MemoryMax means the kernel kills the offending session's cgroup, not the box's biggest process (which today can be the daemon or an innocent neighbor). The supervisor observes the scope's oom-kill event and surfaces it as a first-class process.oomKilled runtime event → session goes exited with a stated reason and a one-click resume (state is on disk; server/embedded sessions resume by ref, terminal sessions via the existing revival path).
  • Living independently of Podium. Sessions must survive: daemon restart (scope outlives it — true today for abduco, extended to harness servers and embedded workers), server restart (daemon reconnect + reattach gates, unchanged), and full Podium uninstall-grade absence (harness-native state on disk — transcripts, thread stores — plus the durable SessionBinding journal in the state dir means a later supervisor can adopt() or at worst resume()). The reattach storm limiter (reattach-gates.ts) already handles the thundering herd.
  • Hibernate / stop / resume. The survival table is unchanged and gets cheaper: for server/embedded drivers, hibernation is "kill the process tree, keep the resume ref" with no terminal-proof gymnastics, because turn state is harness-persisted and there is no screen to prove quiet. The two-pass candidate-signature policy from reattachment-design still gates when; the runtime event stream supplies the required "no open interaction, settled turn, quiet output" evidence directly. Auto-hibernation of idle server-family sessions can therefore be much more aggressive — which is the memory story for hundreds of background executors (Codex's own 30-minute thread unload is prior art).
  • Platform degradation, declared. macOS: no cgroups — isolation degrades to separate process trees + supervisor-enforced soft memory watermarks (poll RSS, hibernate-or-kill worst offender first), launchd keep-alive for the daemon. Windows (ConPTY, no abduco): already durable: 'none'; server-family sessions are actually the first durable Windows story, since a harness server + resume ref does not need a PTY multiplexer at all. Degradation is surfaced in capabilities, per the Declared<T> house rule.
  • abduco's narrowed role. abduco remains load-bearing wherever a real TUI runs: the terminal family's session engines, and on-machine client-TUI attachments (it is what makes them warm-parkable). Vendored source, systemd scoping, alt-screen stripper all stay. It stops being the universal answer: server and embedded session engines need no VT multiplexer because their durability is process + on-disk state, not a screen.

§7Cloud and other machines: same runtime, different placement

Nothing above is machine-local by design, which is the point:

  • Another machine in Podium is already a daemon enrolled via pairing; it becomes a Runtime Supervisor with zero topology change. Placement (handoff/placement.ts) chooses a machine; the runtime contract rides the existing daemon WS; attach relays as PTY frames do today (engine and on-machine client terminals both ride the same frames path). Handoff between machines reuses the existing coordinator; server-family sessions make it easier (resume ref + thread files instead of screen state) and should extend harnessSupportsHandoff beyond claude-code/codex.
  • Cloud is a machine we provision instead of enroll. A cloud sandbox (Firecracker/containers, per provider) boots the same supervisor image with an instance identity, pairs to the hub over the existing peer handshake, and appears as a machine with a cloud capability tag. The provisioning/billing/pool logic is the closed-side orchestrator module behind the PodiumPlugin seam, exactly where the v2 doc parked "cloud sandboxes." Nothing in OSS Podium knows the difference between "Mike's VPS" and "a rented sandbox" beyond that tag.
  • Auth in the cloud follows the driver matrix: Codex workers ride subscription auth.json seeded via the existing cross-machine login catalog / propagation work; Claude cloud workers are embedded-family on API keys (subscription-bound Claude stays on machines where the user's interactive login lives — a product constraint, stated honestly, not an architectural one).
  • Harness-native clouds (Codex cloud, Claude remote-control/web) are explicitly out of scope for v1 of the runtime: they are a possible fourth driver family later ("external"), and the contract has room for it — a driver whose processes we do not own, only observe.

§9Migration: seven phases, each ends with something deleted or measurably safer

  1. Reify interactions on the existing stack. Build modules/interactions + policy engine fed by today's hooks/classifier (source: screen-classifier). No driver work yet. Deleted: the class of invisibly-stuck sessions; steward nudge scope shrinks. This is the highest product value per line and de-risks everything after.
  2. Extract the contract; wrap today as the terminal driver. packages/agent-runtime; daemon session control speaks the contract. Scoped honestly: this is not a zero-behavior-change wrap — roughly 29 call sites (the messages family, steward, superagent tools, automations, revival) move from ready-poll heuristics to receipt semantics, which changes every caller's failure path. So: caller-by-caller migration behind a flag, characterization suites re-baselined as each caller flips, and the boundary manifest amended deliberately (agent-runtime takes the host capability that hook-ingest/composer-sync move under). Deleted: direct daemon-frame coupling in the sessions module.
  3. First server driver: opencode. The pilot: simplest protocol to client (HTTP + OpenAPI + SSE), a clean reified permission API, and low-stakes rollout — and the intended background-executor host for non-Claude/non-Codex models. Its permission.updated events map onto the interactions aggregate from phase 1, proving the contract end to end. Proved: a session driven headless-first with structured interactions and zero screen-scraping.
  4. Process supervision. Slice/scope hierarchy, MemoryHigh/Max, oom events, adoption scan, embedded driver moved to worker children. Deleted: shared-fate OOM; daemon-heap exposure to SDK sessions. Gate: phases 5–7 start only when telemetry from phases 3–4 (driver-family usage share, per-process memory overhead) justifies the fleet-scale bets — §10.3/§10.5 name these as unknowns, so they are measured, not assumed.
  5. Codex server driver + superagent on the runtime. The subscription-carrying driver: ChatGPT auth works headless, approvals flow as structured interactions, steer replaces mail injection. Superagent threads become runtime sessions. Deleted (for Codex-on-server): submit-verification, composer scrape, blocking-hook mail path — from the default path; the terminal fallback retains them per §3's churn stance. Deleted outright: headless-drivers.ts, durable-headless.ts, doubled superagent send paths.
  6. Attach v2. Client-terminal attach (on-machine, streamed, warm-parked) + podium attach; control lease unification. Handover stays deferred per §5. Deleted: exclusiveInteractiveResume as a special case.
  7. Cloud supervisor image behind PodiumPlugin; placement targets cloud machines; aggressive auto-hibernation policies for background fleets. Proved: the acceptance test is "a non-native subagent fleet of 50 Codex executors runs for a week on one box with zero stuck sessions and zero collateral OOM kills."

§10Open decisions (with recommendations)

  1. Wire protocol for the runtime: extend Podium's protocol vs adopt ACP. Recommend: extend Podium's protocol (we need durability classes, oplog sync, and interaction aggregates ACP doesn't model), but keep RuntimeEvent/interaction shapes deliberately ACP-translatable so an ACP driver (Gemini CLI, future harnesses) is a thin adapter and an ACP server facade (exposing Podium sessions to ACP editors like Zed) stays possible.
  2. Where the interaction policy lives. Recommend: server-side (funnel + domain policy in @podium/domain), with a small daemon-side fast path only for latency-critical auto-allows; policy must be one auditable place.
  3. When (if ever) to enable pooled server placement. Decided in §6 that v1 is dedicated-only and pooling is a declared driver capability, not a mode; the open question is whether and when memory data justifies building it — the actual per-process overhead and potential savings are unknown, so gather fleet memory telemetry once server drivers run real workloads and decide on evidence.
  4. Claude subscription sessions: keep spawning a visible terminal by default, or headless-terminal with attach-on-demand? Recommend: headless-terminal default for executor-role sessions (spawned detached under abduco, session-terminal attach on demand — the mechanism already exists), visible-by-default only for sessions a human opens themselves.
  5. Default memory budgets. Recommend: MemoryHigh soft at 1.5 GB, MemoryMax 3 GB per session scope, instance-slice cap at 70% of RAM, all configurable per machine; ship with telemetry before enforcing hard kills.
  6. Do superagent/steward move first or last onto the runtime? Recommend: after the opencode pilot proves the contract (phase 5), so the riskiest consumers migrate onto proven ground.
