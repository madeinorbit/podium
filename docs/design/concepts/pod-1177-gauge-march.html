The mission gauge marches smoothly

The flight-deck gauge's running band stuttered because it was built to. Same material, same gate, same density — the light just moves every frame now.

Before — and why it stuttered

before8 positions per 1.3s · 90% of frames unchanged
3 done 4 in progress 2 to go

The stutter was deliberate: the band advanced in steps(8, end), on the reasoning that a meter speaking the braille spinner's grammar should step as the spinner steps. That works for a glyph — each frame is a whole new character, so there is nothing to be smooth between. It does not work for a position: eight frames per cycle leaves 90% of rendered frames identical, then jerks the light a sixth of the band in one go. What reads is not cadence, it is dropped frames — and dropped frames are how this app says the machine is in trouble.

What changed — three things, none of them the material

1. Linear, not stepped. The light moves on every frame it is on screen.

2. A transform, not a background. Sliding a background is a repaint every frame; sliding a layer is a compositor transform and no paint at all. The gauge sits in a column that re-renders on every wire frame, so the motion has to survive a busy main thread — that is the half of the stutter a linear timing alone would not have fixed.

3. A repeating train, not one traversal. The old glow crossed the band once per cycle, so its speed was the band's width over 1.3s: a mission whose run band grew marched faster for no reason anyone could name, and every cycle ended with the light jumping from off the right edge back to off the left. The train repeats every 180px and translates exactly one period, so the loop is seamless — first frame and last are the same pixels — and the speed is a constant ~129px/s at every width.

The cells themselves do not move. The mask stays on the box and the light travels on its child, so segments stay pinned to the band and light up in place as the glow passes under them. That is what keeps this a meter with cells rather than a barber pole. The glow is the same 72px it always was; only the 108px of dark between glows is new, and that is what holds the band's density where it was set.

Sampled every animation frame for 1.5s on the production bundle's CSS. Under a deliberately jammed main thread (120ms long tasks) the before-case still froze and still leapt 116px; the after-case kept advancing in proportion to elapsed time.

Unchanged

The gate is still working — an agent computing right now, never a task merely parked in in_progress — so a stopped fleet still leaves the gauge completely still. The cells are still 6px on, 3px off, in the band's own --live blue at 42%, under the count rather than over it. Reduced motion still drops the march entirely.
