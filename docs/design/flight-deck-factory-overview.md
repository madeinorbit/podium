# Flight deck factory overview

Specification for POD-1975. Author deliverable tracked by POD-1982. Status: final author revision after Claude Opus 5.5 high's conditional pass, with the required entry correction and parent clarifications applied. The parent verifies those edits and owns implementation approval. This document changes no production behavior by itself.

The deck must answer who coordinates the work, what each task has achieved, what agents are doing, and whether the operator owes a response. Returning to an epic must restore the workspace the operator left. These are separate contracts with separate data sources.

## Scope and evidence

The approved references are `flight-deck-concept.html` and `flight-deck-audit-and-direction.md` in the POD-1975 checkout's `.design` directory. POD-1976, POD-1977 and POD-1978 each have their audit attached as artifact 1. The concept's sample data and simplified two-pane demonstration are illustrations, not production algorithms.

Source inspection used commit `a67097b15`. The POD-1979 branch `pod-1979-new-task-view` was inspected read-only at `87ee61699`. The parent reports its current tip as `006f56235`, adding only a dim, monospace treatment to the composer tip. Its behavior is unchanged: remove the unassigned-agent deck and fold Flightdeck on New task. The branch remains in review, separate from main. Integration must retain its behavior. The parent owns integration, implementation assignments and review.

This specification covers the web Flight Deck, mission entry and its device-local workspace state. Shared client projections may serve other clients, but this does not redesign their screens. The semantic issue-reference order remains stage glyph, issue reference, title, as defined in [Unified issue presentation](POD-458-unified-issue-presentation.md).

## Data contract

### Task identity, containment and counts

Use immutable issue IDs as keys. Resolve display references and titles from current issue records. `parentId` supplies formal task containment. Session `spawnedBy` supplies session ancestry; it never creates or reparents a task. Issue `startedBySession` is a separate recorded provenance field and continues to supply the existing display grafts. Use the existing mission-root and membership projections, with cycle protection, rather than title, branch, worktree or sequence-number guesses.

The formal task tree is the root plus recursive `parentId` descendants. The accepted deck tree also includes the existing provenance grafts from `missionIssueIds` and `buildFlightDeckRows`. Grafts show `Started by <session reference>` and retain the existing display parent, usually the task owning that starting session. They do not become formal children. Archived and deleted branches retain existing exclusion rules. The eligibility and placement of unaccepted work are defined in the final section.

Preserve `missionIssueIds` membership for sessions, tabs, pruning and operator focus. Do not substitute the formal progress set or the visible filtered rows. An agent-created issue with `startedBySession` can belong on the deck without a parent or discovery edge. An accepted backlog spin-off stays an existing uncounted graft until the existing `hasLeftMission` and departure rules move it. This work does not redefine departure lifecycle or unrelated mobile behavior.

Task completion uses the existing `missionProgress` unit set: eligible accepted formal descendants, or the eligible accepted root when there are no such descendants. Retain its exclusions for abandoned work, non-formal grafts and vacated continuation origins. The formal walk passes through proposed ancestors, so their accepted descendants remain units. A proposed root with no accepted formal descendants shows `No accepted tasks`, not 0 of 1. Count each unit once, including deeper descendants. A parent and its child can each be units because each is a recorded task. Label this number `Tasks done`, with an accessible description of its denominator. Do not call it percent effort or agent progress. For the audited PIPP-4 fixture it is 33 of 35 tasks, not the direct-child count of 27 of 29.

Successful closure contributes to done. Cancelled, superseded and duplicate dispositions retain their actual labels and the existing `issueAbandoned` exclusion; they do not become successful completion. Finished work may therefore contain rows that do not contribute to the done numerator. Filtering, folding, search, graph cross-references and staffing changes never change the unit set.

### Independent facts

Build one pure deck projection with independent fields for the following facts. Consumers must not use one winning `deckIssueState` word as a substitute for them.

| Fact | Source and exact interpretation |
| --- | --- |
| Task lifecycle | `stage` plus the shared closed and disposition predicates. `done` or a non-null close reason means closed. Show Backlog, Planning, In progress, In review, Shipping, Done, or the actual terminal disposition. |
| Assignment | Existing issue/session join and `sessionPresentOnTask`. Not archived and not exited means still assigned, including hibernated sessions. Count distinct Podium session IDs. Shells and headless records keep their existing agent-roster exclusions. |
| Process liveness | Session `status`. Live, starting, reconnecting, hibernated and exited remain distinguishable. A hibernated session is assigned and resumable, but its process is not running. |
| Current execution | Use the liveness-aware `isSessionWorking` verdict for eligible, nonarchived agent sessions. Working and compacting are execution; an issue's `in_progress` or `shipping` stage alone is not agent execution. Starting, reconnecting, hibernated and exited cannot count as running. |
| Agent error | `sessionErrored` and the existing error-class label. Show the known cause if available. Error is independent of requests and task lifecycle. |
| Human request | An open task's explicit `needsHuman`, or an attached nonarchived session's recorded request: current offer, `needs_user`, or an idle verdict for which `idleVerdictNeedsHuman` is true. Error alone, idle alone, unread and review stage alone are insufficient. |
| Dependency wait | The task is open and has an unresolved recorded `blocks` target. Closure always prevents an active task-wait label. Details below define unresolved versus unknown targets. |
| Unread | Existing issue/session read baselines. It means unseen output or issue changes, not work running or a response owed. |

The current `sessionNeedsHuman`, `issueNeedsHuman`, `attentionGroup` and `motionPhase` combine some of these facts. In particular, errors enter the human-attention bucket and review alone can imply a human request. The deck must use a narrower request projection and a separate error projection. Keep the broader legacy semantics outside this feature unless another approved change owns them. Do not change server offer retirement, notifications or task lifecycle to obtain the new display.

The current `issueErroredSession` suppresses errors on closed tasks. That helper cannot answer whether a still-assigned session on a closed task has errored. The new deck projection must retain that session fact while keeping task closure authoritative.

An offer and continued execution can coexist. Read execution independently of `motionPhase`, whose attention precedence otherwise hides work. A task with one running session and one errored session shows both counts. Current error counts include assigned parked sessions whose last observed phase is error, labeled as parked. Errors from archived or exited sessions remain readable in history and are excluded from current error totals.

Task closure retires its human obligation under the existing close contract. A stale offer or needs-user phase on a closed task does not add yellow Needs you or a current request count. Its session can state `Last recorded request; task closed`. This does not hide continued execution or an agent error and never reopens the task.

### Dependencies and unknown information

An issue's outgoing `{ id: B, type: 'blocks' }` means this issue depends on B. At storage level the dependent is `fromId` and the prerequisite is `toId`. Draw prerequisite to dependent in the dependency view. Only exact type `blocks` supplies a scheduling constraint. `related`, `tracks`, `validates`, `caused-by`, `supersedes`, arbitrary stored types and spawn ancestry must not create a wait or a scheduling arrow. Containment comes from `parentId`, even when consumers also expose a synthetic `parent-child` relation.

Deduplicate repeated blocking targets by ID and use the tree's stable comparator. A target is resolved-open when its record is known and the shared closed predicate is false. Closed, cancelled, superseded and duplicate targets are resolved-closed for blocking purposes. Do not infer that a closed prerequisite succeeded; show its disposition.

For an open task, show `Waiting on` with the reference, title and stage of every resolved-open target, visible by default. Wrap the list at narrow widths; never replace unresolved targets with a count, `and N more`, a tooltip or a disclosure. A task with three unresolved prerequisites names all three without another action, including when its agent roster is folded. Unknown targets likewise remain visible with the available identity and unavailable label. External targets carry `Outside this epic`. This is neutral information even when an agent is running on the waiting task.

A missing target is unknown, not automatically open or complete. Show `Dependency unavailable` with its known reference, or its ID when that is all the record supplies. Preserve the edge. Do not invent a title or force ready=true. If the wire says blocked but targets have not resolved, show `Dependency status unavailable`, alongside separately labeled authored notes. Likewise, disagreement between a resolved open edge and a false blocked flag must not remove the named edge. The shared closure rule still wins.

For a successfully closed task with a resolved-open target, show `Done` and `Recorded dependency still open`, followed by every such target's reference, title and stage, visible by default. Never show active `Blocked` or `Waiting on` on that task. Use the equivalent terminal label for abandoned work. Missing targets use `Recorded dependency unavailable`. Do not assert the dependency was open at closure: today's edge and target state do not establish that history.

`dependencyNote` and `blockedByNotes` are issue-wide authored prose. Display them as `Dependency note`, without attaching their text to an individual edge or converting names in prose to scheduling constraints. Historical events and current edges do not support a complete replay of former task parents or dependencies.

## Reading and navigation

### Coordinator and mission summary

The root's actual `coordinatorSessionId` identifies the main coordinator. Resolve it against that root's session membership. Do not substitute the newest member, a child task lead, a session whose title contains coordinator, or a guessed spawn ancestor. Child designated coordinators are labeled `Task lead`; the internal legacy role name `phase-lead` is not a workflow phase.

Place a distinct coordinator panel immediately below the mission title and task summary, above view controls and task content. It includes `Main coordinator`, session reference, title, process/activity, and `Open coordinator`. Do not dim the identity when idle, parked, ended or when its task is done. A compact sticky header retains the coordinator identity and open action while the deck's body scrolls. Folding the whole Flightdeck leaves an accessible `Open Flightdeck` rail; it does not require an always-open panel beside the new-task composer.

The panel is the coordinator's canonical session row. Do not repeat it in the root roster or count it twice. Other root agents remain in that roster; helpers spawned by the coordinator retain that parent association beneath the panel's crew disclosure.

Requests in this panel belong to that coordinator or the root issue. A child error or request appears in the mission summary and its own row, without falsely attributing it to the main coordinator. If the root has a task-level request without a session author, label it as a task request. Show available question/action text; otherwise say `Response requested` and open the recorded issue or session context. Never manufacture a question from idle state.

With a designated ID still resolving, show `Coordinator loading`. With no designation, show `No coordinator assigned`. With a known retired designation, show its known identity and `Coordinator unavailable`; allow an existing readable historical conversation to be opened explicitly, but do not silently designate someone else. A cross-task designation means the root's `coordinatorSessionId` resolves to a session now attached to another issue, including a child of this epic. It is unavailable as this root's coordinator even if `missionIssueIds` includes that issue. Show the recorded identity and owning task; an explicit `Open recorded session` follows its actual owner, but it is never the automatic root default. A missing identity cannot enable a working open action. No coordinator condition must produce a setup composer for an existing task.

The summary separates `Tasks done` from `Running agents`, agent errors and requests. Activity and attention cover the complete deck crew before filtering or folding, including the root, accepted formal tasks, provenance grafts and the proposals shown in the final section. These are mission crew totals, not accepted execution or formal progress. Accepted departure references do not add their external crew. Native workers are not Podium agents. Count each running, errored or requesting session once by session ID in its respective total. Count a task-level request flag once only when no requesting session already represents that task. Multiple origins or offers from one session cannot inflate its count. Error and running totals are independent of staffing and completion.

A summary request/error action reveals its owning row, including a proposal at the bottom. It switches to Overview if needed, clears an excluding search, writes explicit open folds for the necessary ancestors/roster and scrolls to the row. It does not open a tab. For a mission member it sets operator focus to that task; for an external proposal reference it keeps the current inspector until the operator opens that proposal's own mission. The reveal is a user edit; background attention updates never unfold or scroll.

### Task and session rows

Task rows show stage glyph, reference, title and literal lifecycle. A separate line shows execution/error/request summaries, then staffing or dependency detail as needed. Task rows and agent rows must have visibly different structure. Keep the reference/title treatment from the existing issue-reference component; issue tint is identity, not status.

| Situation | Required reading |
| --- | --- |
| Backlog or planning with no session history, ready=true | Recorded stage; `Not started`; `Ready to start`; `No agent assigned`. |
| Backlog or planning with no session history, named open blocker | Recorded stage; `Not started`; neutral named wait; `No agent assigned`. |
| Backlog or planning, no sessions, ready=false without a named blocker | Recorded stage; `Not started`; `No agent assigned`; show a known defer or eligibility reason. Do not invent a blocker or claim readiness. |
| In progress or review, no sessions | Recorded stage; `No agent assigned`. Do not claim it never started. |
| Open task with only archived/exited sessions | Recorded stage; `No active agent`; history remains available. |
| Open assigned session, idle | Recorded task stage; `Idle` on that session. No empty-seat claim. |
| Assigned hibernated session | `Parked` or `Saved session`, with last observed error/request if relevant. Never Running from a stale phase. |
| Live session whose turn ended | `Idle` or `Turn finished` on the session. Task completion remains independent. |
| Open task with running and errored agents | Recorded stage; `1 running` and `1 agent error` simultaneously. |
| Closed task with current execution | Done or actual disposition; `Agent still running`. Retain it as a current exception. |
| Closed task with assigned errored agent | Done or actual disposition; red agent error, with parked qualifier if applicable. |
| Unknown/uninstrumented agent activity | Process state and `Activity unavailable` where needed. Do not claim idle or finished without evidence. |

Ready means eligible under the existing domain predicate, not never started, and not automatic dispatch. The UI must never derive readiness from absence of agents. Shipping remains a task stage with system custody; it may say `Shipping` with no running agents.

Use red icon and text for errors, yellow question/action and `Needs you` for recorded requests, neutral text for dependency waiting, blue running mark with `Running`, and quiet green check with task `Done`. Unread has a separate quiet dot and accessible `Unread` label. Color is supplemental. A static running symbol plus text must work with reduced motion. Do not reuse a task completion check for a session merely waiting for its next turn.

### Hierarchy, grouping and folds

Overview is the full-tree view and the fallback when no valid saved preference exists. Keep Working and Needs you filters; Needs you now follows the explicit request rule above. Red errors remain visible in Overview and its summary. An error is not silently included in the yellow filter. Filters preserve ancestor context, including a done parent with an open descendant. The final section remains available independently of these filters.

Within each displayed sibling set, including existing provenance grafts, assign a branch one rank:

1. Open work with a current request or assigned-agent error on that branch.
2. Other open work, in the existing stable issue order.
3. Finished or cancelled work with no open accepted descendants.

A closed parent with an open accepted descendant is an open branch for grouping, while its own lifecycle stays closed. A closed leaf with live execution or an error stays among finished siblings with that exception prominent in its row and the mission summary. Execution starting or ending does not change rank. This keeps rows from moving on every agent turn.

Within each rank preserve the existing comparator: compare distinct nonempty `sortKey` values when both exist, otherwise `seq`, then ID as a final tie-break. Do not sort by last output time. Preserve recorded ownership and never duplicate a task into several operational groups. Only top-level sibling partitions need `Current work` and `Finished work` headings; nested completed siblings move to the end of their own sibling list. Closure or a changed request/error rank can move a row, but does not change folds, inspector selection, tab focus or scroll to it automatically. Preserve a visible scroll anchor by stable row ID where reordering affects the viewport.

Keep finished task titles visible by default and fold their historical agent rosters initially. Tasks with current exceptions start expanded only if the operator has no saved fold. Separate roster folds from branch folds so hiding old agents does not hide child task titles. Explicit folds always win, including after status changes. A collapsed branch still reports exact hidden running/error/request counts and unread state; icon previews capped at 12 do not become a census. The main coordinator has no branch fold.

Podium helpers nest under the session named by parsed `spawnedBy` only when parent and child are on the same task. Use `spawnedByParentSessionId`, not manual string heuristics. Show a cross-task spawn as `Spawned by <session reference>` with navigation, while leaving the helper under its actual task. Unknown parents retain a readable provenance label without a false link. Deduplicate session IDs, break spawn cycles and fall back to flat task ownership. Lead first; other session roots and sibling helpers sort by `createdAt`, then ID. Status changes do not reshuffle those siblings.

Native workers sit one tier below their owning Podium session in a separately labeled disclosure. Show each reported native ID and optional type. Deduplicate IDs within that parent; label missing type `Native worker`. The display count is the greater of the nonnegative reported count and number of distinct identified workers. If count exceeds identities, show `N additional workers, identities unavailable`, not fabricated worker IDs. Never imply these are separate Podium sessions or assigned tasks.

Every native group says `Individual activity unavailable`. A parked/exited parent qualifies the list as `Last reported native workers`. Parent `awaitingSubagents` can say `Parent waiting for native workers`, but does not establish which worker is active or done. A native row opens the owning session and existing native-detail context. Its accessible action is `Open owning agent`; no independent stop, completion, duration or transcript control is offered.

### Dependency view and existing views

Add ungated `Dependencies` beside Overview. For every accepted displayed task, including a provenance graft, with at least one recorded blocking edge, render one group keyed by the dependent task ID. The group lists all recorded prerequisites, their current stage and inside/outside-mission membership, then the dependent. Grafts retain their `Started by` label and exclusion from formal progress. Every unresolved prerequisite is visible by default. Closed prerequisites remain available and may use a separately labeled historical disclosure in this view; that disclosure must never contain unresolved or unknown targets. A task feeding several groups appears as a reference several times but never becomes another progress unit. Sort groups in Overview task order and targets by the stable comparator above.

Single-prerequisite tasks are included. Accepted displayed tasks with no recorded blocking edges appear once in `No recorded prerequisites`, the last group of dependency content, above archived sessions, departures and the final section. That wording does not promise independence. Cycles render finite named edge lists with `Dependency cycle recorded`; do not topologically sort them into invented phases. Unknown targets remain visible as unknown. This requires no phase, reviewer-role or gate schema. A title such as Quality gate A stays a title. Do not infer Research, Build or Review lanes from names, stage, plan prose or topological rank.

Keep Waterfall and Timeline with their existing availability gates and timing/history meaning. Their stored view IDs remain readable. They consume the same task-state distinctions and retain underlying mission membership. The final section's placement rule applies in every view; unaccepted tasks do not become duration bars or additional current task rows elsewhere. Historical event mentions may remain as specified there.

### Interaction and narrow widths

Selecting an epic in the sidebar or its workspace-entry header means enter the mission workspace. It does not imply opening a different agent. A sidebar non-root task is `enterMission(root)` plus `inspectTask(child)`: preserve an existing layout, or run the absent-layout root coordinator decision, then inspect the child. Never open the child's agent or a recent agent as a side effect. `selectPanelForIssue(issue, session)` remains an explicit session target. Selecting a specific task in the deck sets inspector focus and retains the existing explicit lead-preview behavior: designated task coordinator, then a single eligible agent, then the existing deterministic active-member fallback. A sessionless task changes inspector focus without opening another task's agent. Opening a named session, native owner, dependency target or departure is explicit navigation, with the precedence rules below.

Every explicit sidebar entry into an existing task writes the shell deck mode to `open` once, including clicking the current mission's own row. A later manual fold stays until the next such entry. This makes the coordinator visible after leaving New task. It is a gesture effect, not a subscription to selected issue or arriving data. Reload and background updates never reopen it. Shell folding is outside exact tab/pane restoration; New task still folds it and shows the composer.

Keep task chevrons as fold-only controls. Session single-click opens/replaces the preview; permanent-open gestures keep the tab. Nested dependency links, status controls and native disclosures must stop the containing row's navigation. Keyboard activation uses the same action as pointer activation. A dependency inside the current mission selects its task; an external task enters its own mission and selects that task without inventing an agent target. An explicit session link additionally opens that session.

Responsive behavior uses the deck container width, not the whole browser width. At 480 CSS pixels and above, identity and short state summaries may share a line. Below 480, put state, role and dependencies on wrapped lines. Below 370, keep dependency references visible, replacing the current rule that hides the chip. Use 20px indentation where it fits; below 370 reduce it to 12px, cap accumulated indentation at three levels and show an explicit parent-reference breadcrumb for deeper rows. Semantic hierarchy and parent navigation remain complete.

At 320px the title, reference, stage, coordinator action and all exceptional facts must be reachable without horizontal deck scrolling. Running/error/request counts and unread information must not exist only in `.deck-drop-payload` or `.deck-drop-crew`, which current CSS can hide at narrow widths. Put them in wrapping text that remains visible, or revise those hiding rules. All three dependencies in the three-blocker fixture remain named by default at this width. Long titles wrap; full session/native IDs are available through the row's accessible name and a keyboard/touch disclosure. View controls may wrap or use a labeled selector, preserving access to all available views. No essential explanation depends on hover. Controls retain visible focus and at least 24px targets; icon-only row actions expose their names. Text contrast follows the existing accessible semantic tokens, with a 4.5:1 normal-text target.

Keep existing responsive workspace behavior. This change adds no narrow pane switcher or pane-collapse mode. Preserve every saved leaf, axis and ratio, including three or more panes. CSS minimum sizes may constrain rendered pixels, but must not write new ratios unless the operator resizes.

## Exact workspace restoration

### Storage ownership and saved fields

Reuse principal-isolated device-local `podium.workspaces`, keyed by `mission:<root issue ID>`, and its file-tab records. Do not add replicated fields, a server workspace model or cross-device synchronization. Preserve existing shell layout ownership, including replicated dock position/visibility where applicable. The exact setup here means workspace tabs, panes and mission inspection/display state, not transcript scroll, text selection, open context menus or global shell geometry.

Persist the following in each mission's workspace entry:

| Field | Required retained value |
| --- | --- |
| `panes` | Pane IDs, ordered tab IDs and every pane's `activeTabId`, including inactive panes. |
| `root` | Recursive split nodes, every `axis`, ordered children and normalized relative `sizes`. No two-pane conversion. |
| `focusedPaneId` | Any valid leaf, including pane three or later. |
| `previewTabId` | The current preview ID or null, preserving its italic/replacement semantics. |
| Optional `deck` metadata | Operator `focusedIssueId` and preferred deck view. |

Keep the workspace envelope at `v: 1`. Add optional `deck.focusedIssueId: string | null` and `deck.view: 'overview' | 'working' | 'needs-you' | 'dependencies' | 'waterfall' | 'handoff'`. Normalize these independently of layout fields. A missing focus defaults to the root once resolved. A missing view reads the existing global preference and then falls back to Overview. Branch, roster and native disclosures continue in the separate issue-keyed device-local fold store, described below. Archived-session disclosure remains transient. These additions do not belong in replicated issue/session entities.

Keep file-tab records, scopes and their existing presentation state through the current UI-state layer. Layout storage holds IDs, not duplicate transcript content. The existing single-preview-per-workspace and one-pane-per-tab invariants remain. Empty panes in a saved tree remain empty; an intentional one-pane, zero-tab workspace is a valid saved layout.

An explicit inspector or view edit also materializes a saved mission entry, even with zero tabs, except for inspection that accompanies the first-entry coordinator decision. That child focus cannot create a zero-tab entry: if no coordinator is seeded, retain the focus only in memory for this runtime. Merely computing default display metadata also creates no entry. This distinction must bypass the current `workspaceWritePatch` suppression of a previously absent, one-pane empty layout only for an intentional user edit outside that first-entry exception. A fold-only edit writes its existing separate store and does not create or empty a tab workspace.

Persist operator `focusedIssueId` from `operator-focus.tsx`, not the task explorer's stack top. Its explicit writers are deck task/session selection, a session tab click retargeting to that session's owner, a sidebar task selection, and RightDock task selection. Preserve the existing file-tab owner retarget when the file names an issue. Those user actions persist the new focus subject to the first-entry exception above. Restore writes the saved operator focus directly, without replaying a tab click or session-open action.

The inspector task is independent of the focused session. An operator may inspect a child while keeping the coordinator conversation focused. Entering the mission restores both values without forcing them to agree. Resolve operator focus against the unchanged `missionIssueIds`, including provenance grafts. The task explorer's navigation stack/history stays transient and may reset from operator focus as today. Global right-panel choice, query text, archived-session disclosure, hover cards and pointer drag preview are outside this exact-setup contract. Existing durable display preferences such as Waterfall zoom remain with their current owners.

### Entry precedence and hydration

Implement one engine entry decision shared by the sidebar and epic entry points. Conceptually distinguish `enterMission(issueId)` from `openSpecificSession(sessionId)` and `inspectTask(issueId)`. These need not be the final exported names.

1. Record a navigation generation tied to the principal and requested destination. A newer user navigation or workspace edit cancels pending automatic work from an older generation, even if it selects the same root again.
2. Hydrate local UI state and file-tab records before deciding absence. Resolve the selected issue's complete ancestor chain to the mission root. A missing ancestor is unresolved, not permission to make `issue:<id>` the final workspace key.
3. If a normalized stored or current in-memory entry exists for that key, restore it exactly. Mirror legacy A/B scalars from it for compatibility. Do not call `setPane('A', ...)`, retire a preview, reset inspector focus or open a recent session as a side effect of entry.
4. If an explicit session/deep-link/launch target accompanies this navigation, restore the destination first and then open that target. If already in a pane, activate it there and focus that pane; otherwise open it in the requested valid pane or the saved focused pane. Preserve all other tabs and split nodes except the established replacement of a preview. A permanent explicit open remains permanent. The target wins over any automatic coordinator default.
5. With no saved entry and no explicit session target, resolve the root's designated coordinator after the relevant issue and session data arrives. Seed one permanent coordinator tab if the session belongs to the actual root, is not archived/exited, and is an eligible agent session. Hibernation is allowed: opening its conversation is not spawning a replacement. Plain entry defaults the inspector to the root. A sidebar child-task entry restores an existing entry and inspects the child without opening a tab. With no saved entry, it runs the same plain-entry coordinator decision, then sets operator focus to the child. It never opens the child's agent or a recent one. If no coordinator is seeded, the child focus stays in memory for this runtime and creates no saved entry.
6. If no usable coordinator exists, show an empty existing-task workspace with the appropriate coordinator message and an explicit session picker. Do not choose a recent child, create a session, or enter the new-task composer. An automatic empty placeholder does not create a saved entry. Any user workspace choice cancels pending seeding; a user choosing or closing tabs records the resulting layout, including zero tabs.

Cached entity seeds are sufficient for positive identity resolution after local hydration. Absence from a partial seed is not an authoritative missing result. An unresolved entry waits through the existing bounded entity-resolution interval of 20 seconds; a positively resolved coordinator may seed during that interval only if the navigation generation still matches. At timeout show `Coordinator unavailable` or `Task data unavailable` as appropriate, leave the entry absent and stop that automatic attempt. A later arrival cannot steal focus. Re-entry or an explicit open retries resolution.

A route mirrored by the app is not a new navigation command. In the web router, mirror the actual focused leaf's active tab, not legacy pane A, and add a small mirror marker to the existing browser history state while preserving its other fields. Record the mission key and mirrored worktree/tab values; only a marker matching the current route counts. Reload or return to that marked entry restores the workspace without issuing a tab-open gesture. A copied URL, bookmark or deliberately changed URL without a matching marker is an explicit target and wins. In-app explicit session actions remain explicit regardless of the current marker. Do not add a generic host navigation adapter framework.

The marker protects more than which ID is active. Replaying even an apparently idempotent permanent open can promote a preview, and replaying a tab click can retarget an independently saved inspector task. Restore must perform neither. Mirror replacements do not feed back as opens. A focused empty pane mirrors no tab and cannot fall back to pane A.

For the initial legacy web reload without a marker, treat an initial pane parameter equal to the hydrated legacy `paneA` as the old mirror only when the browser reports reload and the saved destination is the same mission. Restore its actual saved focus, then write the new mirror. Ordinary incoming navigation still honors that parameter as a link. Test this bounded compatibility case because a third-pane workspace otherwise reloads onto pane A. An explicit link to a missing session gets a loading/unavailable target, not a coordinator substitution. Sidebar task entry must not call the recency-based `pickPaneSession` path in `use-unified-work.ts`.

No session activity, updated title, stage change, offer, unread event, roster reorder or newly arrived agent selects a tab or inspector task. Preserve the focused-conversation rehome exception in `sessionIssueFollow`, described below. Deck active-session highlighting must use `focusedPaneSession` or the actual `focusedPaneId`, never pane A followed by pane B.

### Preview semantics

Current serialization and deserialization call `releasePreview`, dropping the tab and sometimes collapsing its pane. Remove that release from both persistence directions. This intentionally reverses POD-1247's persistence decision to honor exact tab restoration. Save and restore the preview as it was, including when it is the only tab in a nested pane. Do not promote it to permanent during restore.

An actual user tab-selection or replacement gesture retains the existing preview retirement behavior. Leaving a mission, re-entering it, reload, hydration, background activity and a persisted layout write are not such gestures. A hover card or press-and-hold peek that never creates a workspace tab can remain ephemeral. Any interaction that creates an actual tab is covered by exact restoration, even if the tab is called a preview.

### Migration and invalid data

Keep `{ v: 1, workspaces: ... }` at the existing `podium.workspaces` key with additive optional `deck` fields. Do not introduce a v2 envelope or dual-version reader. An older v1 reader may drop the new metadata and release a preview when it writes, but it still reads every valid sibling workspace. That older-bundle limitation must not turn into loss of all other missions.

Normalize the tree with the current structural rules and retain every tab still present, including any legacy preview. Tabs already removed by the old serializer cannot be recovered and must not be reconstructed from recency. Preserve valid sizes, focus and active IDs. Initialize missing operator focus to the root once resolved. A mission without a stored view reads `podium.flightDeck.mode` as its fallback; if that value is absent or invalid, use Overview. Only an explicit view choice writes that mission's preference. Do not delete or rewrite the legacy global mode key or eagerly copy it into every mission.

Map legacy `full` to Overview and `active` to Working; retain `working`, `needs-you`, `waterfall` and `handoff` semantics. `handoff` remains the stored Timeline choice. A disabled Waterfall/Timeline feature displays Overview while retaining the dormant preferred value. Dependencies has no feature gate. Invalid new metadata falls back field by field and must not invalidate valid tabs or panes.

Adopt a legacy `issue:<id>` layout into `mission:<root>` only after root resolution and only if the mission key is absent. Prefer the root's legacy issue key, then the requested issue's legacy key; do not merge tab sets from several layouts. Give the adopted copy its mission key and reconcile against `missionIssueIds`. Legacy issue-key entries are never deleted by this work. If a mission entry already exists it wins unchanged. A write refusal keeps the adopted result in memory and leaves durable old data available. Repeating adoption is safe because a saved mission entry always wins.

For malformed JSON or unsupported envelope versions, render a fresh in-memory workspace rather than crashing or partly trusting fields. A corrupt workspace is rejected independently of valid siblings. Do not overwrite an unreadable blob merely by mounting or resolving rows; an explicit user workspace edit may replace it with supported state. Normalization alone does not require a storage rewrite.

Keep current structural normalization: each leaf claims one pane, duplicate tab IDs keep their first occurrence in tree order, invalid active IDs choose the first surviving tab, invalid focus chooses the first leaf, invalid preview becomes null, and each invalid size becomes weight 1 before normalizing the full sibling array. Remove unusable nodes; collapse structurally invalid single-child splits. Valid nested trees and valid proportions are unchanged. This structural repair is distinct from removing an unknown entity ID.

### Existing fold store

Keep device-local `podium.flightDeck.folds`, independent of workspace layouts. Extend its issue-keyed semantics with `branch` and `roster` maps of issue ID to `open` or `closed`, and a `native` map keyed first by issue ID and then owning session ID. Missing entries mean use the row default. A native disclosure is not a fabricated worker lifecycle record.

Read legacy closed-ID arrays and the current `{ open, closed }` form. Once a legacy issue's topology is resolved, map a leaf value to its roster and a branch value to its branch, never both. Apply the same rule to open and closed values. Once either persisted new map contains that issue, ignore its legacy value in both categories; explicit new entries win. Defer interpretation when topology is unresolved; absence from a partial slice is not proof of a leaf. Retain legacy entries so a later resolved topology can be handled. Do not copy folds into mission workspaces, prune them on a grace timer, or discard them on reparenting.

Migration reads do not delete or rewrite legacy keys. Before an explicit fold write, reads may interpret legacy values against the currently resolved topology. The first explicit fold write after topology resolves stores every legacy placement resolved at that moment in the new maps alongside the requested edit, which wins for its target. Preserve unresolved legacy values and the historical `open`/`closed` entries. Once a placement is durable in a new map, subsequent topology changes never reinterpret its legacy value. Later explicit writes likewise include any newly resolved legacy placements. No eager write on read is required. Archived disclosure stays transient and the final triage section has no fold.

### Unknown, retired and rehomed IDs

Retain the existing 20-second continuous unresolved-ID grace through `Reactions.pruneWorkspaces`, starting only after local workspace/file-record hydration. During that interval preserve tab positions, active IDs, unresolved operator focus and pane focus. Render a loading target with a close action where a selected tab does not yet resolve. Arrival or explicit removal resets its timer. Pending spawn IDs count as known. Fold IDs have no grace-based pruning.

After grace, an ID still unavailable to this principal can be pruned without claiming the entity was deleted. This is the existing bounded availability policy, not proof of deletion. Pruning keeps all split leaves, axes, sizes and focused pane; if an active tab goes away, choose the surviving neighbor using the existing prune reducer, or null if none remain. Do not seed the coordinator into the resulting empty saved workspace. Remove an unusable persisted session-scoped file record with its tab; retain resolvable file tabs and their scope records.

A known session outside the resolved `missionIssueIds` membership is rehomed and is removed from the old layout without waiting for the unknown-ID timer. Never apply that rule while the root/ancestor chain is unresolved, or because a provenance graft is absent from formal progress. Background rehomes only reconcile membership: they do not add a destination tab or navigate.

Preserve `sessionIssueFollow` when its existing source-selection preconditions hold and the changed session is the conversation in the actual currently focused leaf. The guard requires a known previous nonempty issue ID, a different new issue ID, and selection of the previous issue or null; do not broaden it as part of this work. Follow that same session to its destination workspace and open it permanently. This is the exception to automatic rehome navigation. A session in pane A when another pane is focused, an inactive tab, or another background pane cannot trigger it. Resolve the destination mission before writing its workspace. Test both the focused-session follow and background-only reconciliation.

Known exited or archived sessions still belonging to the mission remain readable in saved tabs. Retirement alone does not remove an open tab or erase its split. They are excluded from automatic first-entry seeding. Archived/deleted inspector tasks or tasks definitively outside `missionIssueIds` fall back to the root without changing tabs; unresolved inspector IDs get the same grace first. Keep stored folds even when their owners are temporarily absent or have moved.

### Storage refusal

The side cache is best effort and currently swallows UI-state quota failures. A refused write must not roll back in-memory tab edits, erase panes, reseed the coordinator or retry on every activity frame. Keep the most recent in-memory layout for re-entry in that runtime. Retry on a later actual layout edit through the normal persistence path.

Do not display a promise that a refused layout is saved. Where the existing storage adapter exposes failure, a quiet `Layout could not be saved on this device` notice may explain the limitation. This feature does not require a new replicated error field or a new blocking dialog. After reload, only the last successful durable write can be guaranteed. Principal changes cancel waits and discard the former principal's in-memory navigation context; no layout leaks across that boundary.

## Proposals

This is the single product section for unaccepted work, and it is the final section in every Flight Deck view. It also contains the complete proposal-placement contract for this specification. Nothing follows it.

1. **Eligibility.** A proposal is a nonarchived, nondeleted, open issue whose recorded stage is exactly `proposed`. A `discovered-from` edge, no agent, no branch or no recent activity does not make an accepted issue a proposal. Closure/disposition takes precedence over a stale proposed stage. Backlog is accepted work, even with no agent.
2. **Mission scope.** Before view filters and folds, union eligible proposed members of the unchanged `missionIssueIds`, eligible proposed issues with a recorded `discovered-from` target in the root's formal tree, and eligible proposed destinations already exposed by existing continuation/spin-off projections. This includes an agent-created proposal with `startedBySession` and no parent or discovery edge. Do not widen session/tab/focus membership to this display candidate set. Do not traverse unrelated edges or extend the collection through accepted departures: a proposal discovered from a departed task belongs to that task's own mission. The selected root may itself be proposed; its title remains the page identity, with its one actionable proposal row here.
3. **One collection.** Union candidates by issue ID. An issue reached through containment, started-by provenance, several origin edges, departure projection and continuation projection still has exactly one proposal row. Keep all known origin references on that row. Compute this collection in one shared projection; do not render separate internal and external proposal groups. Use the same stable comparator as accepted rows. Do not sort by session activity.
4. **Placement.** Render exactly one `Proposals` section when the collection is nonempty. It is after accepted task content, history/archived sessions, accepted departures and continuation content. It is outside their branch folds and mode filters, and has no fold of its own. Working and Needs you do not hide this collection. Search may narrow its rows; the header then states `X of N` and retains the section with `No matching proposals` when X is zero. A summary attention reveal clears an excluding search and scrolls to its proposal row. With zero proposals, omit the section rather than show an empty second group.
5. **No other proposal rows.** Remove the leaf-only extraction exception, Waterfall's inline proposed rows and proposed destinations from departure/continuation rows. Remove the separate `proposed` section passed into `FlightDeckHandoff`; all view modes use the same final section outside their mode-specific content. Timeline may retain recorded events mentioning an issue as historical text, but cannot render a second current proposal card, roster or work unit. Dependency groups may name a proposed prerequisite as an edge reference pointing to its sole row here; they cannot present it as accepted work or add another proposal group.
6. **Proposed parents.** A proposed issue with children still goes here. Proposed descendants receive their own unique rows in this same collection, with parent references. An accepted issue whose immediate formal parent is proposed renders under the nearest accepted formal ancestor, or directly under the root container if none exists. Its depth is one greater than that displayed parent, and it ranks in that parent's displayed sibling set. On the accepted child's own row show `Parent POD-N · proposed · see Proposals`, identifying its actual immediate parent. This is ancestry text, not a second proposed task row. Its own accepted children stay beneath it and do not falsely label that accepted parent proposed. Preserve `parentId` and its formal progress unit. Apply exactly the same placement in Waterfall. If a provenance graft's existing display parent is omitted as proposed, attach the graft to the nearest retained display ancestor/root and retain Started by, without claiming formal parenthood. A proposed root with zero accepted formal descendants reads `No accepted tasks` in progress.
7. **Row content.** Show reference, title, Proposed label, known author session and origin references. Show recorded placement as `Within this epic` when formal containment establishes it, otherwise `Independent follow-up`; retain `Started by` provenance where known. Unknown authors remain unknown; do not guess from the nearest agent. Preserve existing explicit triage/start/dismiss actions and issue context menu. A proposal may already have a session. Show its actual activity, requests and errors, and count genuine signals once in mission crew/attention totals, never in formal task progress. For a proposal outside `missionIssueIds`, explicit row/task opening enters its own mission; a summary reveal merely reveals its bottom row and does not write invalid operator focus into the origin workspace.
8. **Accepted grafts and departures.** Acceptance alone does not make an issue a departure. Accepted non-formal `missionIssueIds` members remain in the accepted tree with Started by, excluded from formal progress. In particular, the existing accepted backlog spin-off without agents remains a graft until existing lifecycle rules say otherwise. Issues already exposed as accepted departures remain in `Where the work went` or continuation treatment with stage, origin and navigation. They never appear under Proposals. Deduplicate a continuation destination against other accepted departure rows, retaining existing live-tip and finished-departure rules. When an existing projection also exposes a member as a departure reference, that reference adds neither another accepted task row nor a second crew count. External departure references contribute no crew or progress to the origin. A proposed continuation target has no actionable continuation card above this section; its origin information belongs on its sole proposal row here.
9. **Transitions.** On acceptance, a contained proposal moves into the accepted tree once and joins the eligible formal progress set. An independent proposal leaves this section and follows the existing membership/departure projections: a remaining graft is shown uncounted in the accepted tree; a qualifying departure is shown as such; an external issue without either qualification remains an external relation. Do not change stage, `hasLeftMission` or staffing merely to force a placement. Dismissal, archival or deletion removes the proposal according to the domain operation. Reparenting recomputes display placement without duplicates. These updates preserve tabs, inspector selection and folds except for normal invalid-membership reconciliation, an explicit navigation action or the specified focused-conversation rehome follow.
10. **Required fixture.** Include a contained proposal, an external proposed discovery, a startedBySession-only proposal without parent/discovery edges, a proposal reached by multiple origins, a proposed parent with proposed and accepted children, a proposed root with no accepted formal descendants, an accepted non-formal graft without a discovery edge, an accepted backlog spin-off without agents, an accepted running departure and a proposed continuation destination. Add a proposal discovered from that departure in its own mission, and a genuine proposal request/error session. Across Overview, filters, Dependencies, Waterfall and Timeline there is at most one Proposals section, it is last and unfolded, and every eligible issue has exactly one actionable row in it. Accepted grafts and departures stay outside it; formal progress excludes proposals and non-formal discoveries; crew attention includes genuine proposal signals once and reveals the correct bottom row.
