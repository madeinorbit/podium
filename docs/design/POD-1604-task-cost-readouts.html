What a task cost

Every issue on this machine already has a price — the transcripts are on disk and the price table has shipped since POD-596. v1 offered three approaches; A+C was chosen, with one correction: no prices on the flight deck. This version carries that decision through four surfaces and answers the two questions left open.

Figures and task refs are real, read off this machine over the last seven days. Tracker read 24 Aug 2026; stages move, so a row may have advanced since.

What was decided
  • A+C. A settled figure (the ledger) as the spine, with C's comparative multiple as a second reading. B — the live burn alarm — is not built.
  • No price on any deck row. The spine stays about attention and progress. One price on the mission header, for the epic the column is showing, opening a breakdown or the task in the explorer.
  • A cost section in the explorer's task detail and in the task detail page, designed around the fact that neither surface lists settled sessions.
  • High-level cost stats on the usage sheet, above the ranked table.
  • Rollup: yes, and it has to be legible rather than a hover tooltip.

01 · The correctionWhy cost was wrong on the deck rows

The instruction was “keep it away from the flight deck”, and working through the surface afterwards, the deck's own commentary had been saying the same thing. Worth writing down, because it is the rule that keeps the figure from creeping back:

  • The spine is one question. Every column in a deck row answers “what needs me, and what is moving”. Cost answers neither. The state column's comment is explicit that it spends its width on the one word that says something the marks cannot — a dollar figure is a second axis smuggled into a list built for one.
  • It would have had to fight for room it cannot win. The meta cluster already holds the relation chip, the seat chip, the fold payload and the crew census, with a drop ladder retiring them at 370, 350 and 310px. Cost joins that queue at the bottom, which means the number is missing exactly when the column is narrow — a figure you cannot rely on seeing is worse than one you never expected.
  • At the median it says nothing. Half of all costed tasks are under $7.03. A spine of thirty strips would carry thirty small change figures to surface the two that matter.

So the deck keeps one price, at the level where the question is actually asked: the mission you are looking at, in its header, once.

v1 marked a rolled-up figure with a left tick and put the split on hover. That was too quiet for a number whose meaning changes completely depending on whether it includes children — so the split is drawn, not hidden.

05 · Explorer & task detailThe section that accounts for what the roster hides

The structural fact this design turns on

IssuePanelView holds every session for the task in all, then renders activeSessions = all.filter(isOpenSession). So the roster is deliberately live-only — which is exactly why the cost section has to exist and has to be self-contained. The five-row cap and its “N more active” toggle come out as part of this work: the explorer shows every active session. It is not a summary of the list above it; it is the accounting for the sessions that list will never show. The data is already in scope, so nothing about the roster has to change.

07 · What is unchanged from v1The rules that survive the correction

  • Rounding is the provenance. ≈$226 outside, cents only where the full sentence fits. Three significant figures, no cents above $10.
  • The hedge sentence is reused verbatim — “at list price for the same tokens — not what you were billed” — never paraphrased into a second wording.
  • Attribution is stated once, in the sheet's provenance bar. The floor mark keys off harness: a task with any Claude session is fully counted; only wholly-Codex or mixed tasks print ≥. Re-measured 31 Aug and the rule holds, though the figure moves: of files touched in the last 7 days, 0 of 117 Claude transcripts lack a segment row and 137 of 299 Codex rollouts do — 284.9M tokens, 4.4% of Codex tokens, unattributable to any task. Do not quote a fixed percentage anywhere in the UI; the provenance cell should report the measured share, not a constant.
  • Never a confident $0. A task with no sessions reads No sessions, never $0.00 — POD-1608 is the live proof, with 126 files changed and a truthful zero, because the agent that did the work was bound to another issue.
  • Pruned transcripts read Not recorded, which is a different fact from zero.
  • POD-1571 composition is settled, and it shipped. The reset ledger is implemented and green, and it complies with the closed-masthead rule: it renders no masthead figure at all, and its three readings sit inside its own section at the sheet's 13px mono reading size. Both features touch the provenance bar and nothing else, one cell each.
  • Do not borrow a tone ramp for the percentile view. The live quota meter escalates amber at 75% and red past 90%; in a history chart that mapping inverts, which is why the ledger went monochrome. Ours inverts the other way again — high spend is the thing worth a second look — so the safe answer is the one already chosen: ink steps, never hue, following the Composition ramp.

08 · Build order

Integration notes from the shipped ledger — read before touching the sheet
  • The provenance bar is ours to edit. POD-1571 deliberately left UsageProvenance untouched so there is no race. Land the Attribution cell whenever; the ledger's Collecting cell goes on top of our change rather than beside it.
  • Its cadence is 15 minutes, not 5 — the daemon memoises each provider read for 120s, so faster polling returns identical payloads. Do not repeat the 5-minute figure from its proposal artifact.

10 · PerformanceMeasured, and it rules out the obvious build

v2 said the feature was “one query over data that already exists”. That was wrong, and it is the kind of wrong that only shows up after something ships. Measured on this machine:

CaseCorpusTimeVerdict
One task — POD-1574, task-detail panel10 transcripts · 45MB856msToo slow to open a panel with.
Every task — the usage sheet1,397 transcripts · 4.15GB69.9sNot viable at all.

And the naive fix — “scan it in the daemon” — is the worst available option, because apps/daemon/src/control/exec.ts already says so in its own comment: the existing usage scan “runs on the DAEMON's event loop, which is the loop carrying PTY traffic”, is memoised for 120s, and serves stale while rescanning precisely to keep that walk off the critical path. A second full walk would land on the loop that carries every agent's keystrokes.

The architecture that follows
  1. Attribute the walk that already happens; do not add one. The daemon already parses every usage-bearing line of every transcript touched in the last 7 days, and then throws away which session each record came from. Carrying the segment path through and bucketing by issue as well as by hour×model makes the sheet's by-task section nearly free — one DB lookup per file, not per record.
  2. Persist per-session cost for the all-time figures. The 7-day walk cannot answer “what did this task cost” for a task that closed months ago, and the task-detail panel needs exactly that. One row per session, written by the same walk.
  3. Make the rescan incremental. Transcripts are append-only, so store a byte offset per file and read only what is new. That turns a 70-second cold walk into a bounded steady-state cost, and it is exact rather than heuristic.
  4. Never block a render. Every surface takes the sheet's existing cold-state treatment — Unfilled slots in a layout drawn in full from the first frame — rather than a spinner or a late-arriving reflow.

Pricing stays client-side. The read path returns per-model TOKEN aggregates, not dollars — apps/server does not depend on client-core and should not grow that edge to duplicate a price table. Every surface prices with the existing bucketCostUsd, so the product has exactly one pricing implementation. It follows that the rate and its cohort median must also be computed client-side, after pricing: cost-per-reply and tokens-per-reply are not the same ranking and not a monotonic transform of each other, because models differ in price per token. A server-side token-based median would look plausible and rank tasks wrongly — the worst failure for a number whose only job is comparison.

09 · Still open

The mission header chip on a mission with no cost. A brand-new mission shows no chip at all, so the header row is gauge + Add agent as it is today — the chip appears when there is something to report. That means the header's shape changes once, early in a mission's life. The alternative is a permanent chip reading —, which is a slot held open for a number rather than a fact. Recommending the first; say if the shifting row bothers you more than the empty one would.
