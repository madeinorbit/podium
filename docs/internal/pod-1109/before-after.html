Web maskable icon — before and after

The installed web app’s Android adaptive icon, under the mask shapes a launcher may pick.

Beforeon main today

The generator feeds icon.svg — the full-bleed cut — into the maskable slot at padding: 0.15 over flat #131417. That padding is total, not per-side, so the art lands at 85% of the frame. icon.svg owns a gradient ground, so the inset does not read as padding: the tile’s straight edges cut visibly across the circle, with a flat ring outside them.

Afterthis change

The 9a set already draws a safe-zone cut for exactly this slot — the ocre plane raised and the letter stepped down, rather than the whole tile shrunk into the crop. The web build now renders that cut, full bleed. The ground reaches the frame edge, so there is no second colour for a mask to expose.

What changed

  • The maskable leaves the generator: its sizes is now empty, which is how a slot is switched off.
  • apps/web/public/icon-maskable.svg is web’s copy of the shared 9a cut, byte-identical to apps/mobile/assets/icon-maskable.svg.
  • scripts/generate-maskable-icon.ts rasterises it to a committed PNG — a straight resize, no canvas, no padding.
  • vite.config.ts declares manifest.icons by hand, which is what stops the plugin overwriting the maskable entry. The transparent entries are unchanged.

The letter and plane run off the frame on purpose — the crop is meant to slice them, which is why the tests do not assert a safe-zone box. They guard the two ways this actually regresses: the copy drifting from the shared master (which happened once already during this issue), and the renderer insetting the art again.
