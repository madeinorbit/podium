Specification · POD-4414 · rev 2 · 2026-09-20 · after independent review

Harness Adapter Spec

How Podium organises everything it knows about, and everything it does with, a coding harness. Written for an independent reviewer with no prior context: background first, then the goal, the design, the rules, how we get there, and what is still open. Companion pages: Terminal Layers in Code (the runtime object stack) and Daemon Link Planes (the network link, parked).

0. Background for a cold reader

Podium runs coding agents ("harnesses": Claude Code, Codex, OpenCode, Grok, Cursor, Pi) on one or more machines and lets a person drive them from a browser or phone. A server is the control plane: it holds the session records, the issue tracker, the user's transcripts and policy. A daemon runs on each machine and owns the processes. They talk over a WebSocket. A harness runs either headed, as a terminal program in a pseudo-terminal, or headless, as a server process Podium talks to over a protocol.

Harness knowledge today is spread across the codebase: an inventory on 2026-09-16 found harness names in 257 non-test files across 20 directories, outside the driver implementations themselves. Consequences: the same credential file layout retyped in six places; model catalogs duplicated between web and mobile; a Codex terminal heuristic living in the browser terminal client; the server parsing harness transcript files with its own copy of the grammar; and, until this epic's Phase 0, two different ways for the server to talk to a harness, one of which typed keystrokes and polled for echoes.

Two earlier documents shape this one. POD-3190's Design from scratch set the runtime object stack (host, durable process, terminal, session, driver). POD-4104's spec rev 2 set the harness-adapter invariant (one adapter per harness; the driver contract is the only runtime path; nobody else names a harness). This spec reconciles the two, names the mechanisms that consume an adapter, and fixes the package layout. Revision 2 applies an independent architecture review of rev 1 (see §11): it separates implemented support from effective capability, replaces two absolute rules with composition rules, distinguishes bundled client code from wire data, states the identity invariant precisely, specifies construction and failure ownership, and qualifies the extensibility promise.

1. Goal

Every fact about a harness lives in exactly one place, and every use of a harness goes through one of three generic mechanisms, or the projection served to clients. Adding a harness on existing mechanisms means adding one directory. No vendor-specific behaviour lives outside that directory and the driver families, and a lint proves it.

Measured by:

  • A harness that uses existing driver families and store kinds is one directory under adapters/ plus a registry entry; the compiler lists every missing section and no application code changes. A harness with a genuinely new protocol or store kind adds an implementation inside the harness package and still changes no application consumer.
  • The boundary lint passes with an empty allow-list for the daemon, the server, the web and mobile apps, and the shared packages.
  • "How does Podium talk to a harness" has one answer readable from imports: the Driver. "How does Podium read a transcript" has one answer: the Store. The server's transcript lake and a live session read with the same code, and the same logical record receives the same identity whether read live, mirrored, relocated or replayed.
  • The codebase is smaller: three packages dissolve into one, and eight daemon files that each knew one harness disappear.

2. Why

  • Cost of change. Every harness update today is a hunt across twenty directories. With one directory per harness, the diff for "Codex changed its transcript format" is one file.
  • Correctness. Duplicated knowledge drifts. The server's own transcript grammar disagreed with the daemon's; the two Codex credential lists in the daemon disagreed with each other. One copy cannot drift from itself.
  • Confusion. Every engineer and every agent working on sessions met two paths and three packages with overlapping purposes. The single most common failure in this codebase's history is an implementer picking the wrong one.
  • Completeness. With knowledge spread out, "is this harness fully supported" has no answer. With required sections and declared declines, it is a generated table.
  • Clients that outlive their build. A phone app built last month must render a harness added this week: its name, icon, model choices and supported controls, inside a presentation schema the app already knows. That needs the harness's display facts served as versioned data. It does not give an old client a new interaction model; that needs a new client.

3. Principles

  1. Knowledge and mechanism are different kinds of code and never mix. Knowledge is data plus pure functions, varies per harness, and is written by the person adding a harness. Mechanism is behaviour, varies per way-of-using, and is written once.
  2. Factor along the real axes of variation. Harness varies the knowledge. Mechanism varies how we use it. Store kind varies how we read. Side (server, daemon, client) varies where it runs. Every object varies along exactly one axis; the cross products are data.
  3. Absence is a value. A harness that lacks a capability declares it declined with a reason. It never omits the section. Completeness is then a typecheck.
  4. One authoritative definition per concern, with a clearly responsible implementation. Ownership is not readership: a definition may have several narrow readers. Consumers depend on narrow typed interfaces or immutable projections; application code never inspects adapter internals.
  5. Mechanisms do not own or instantiate each other. Dependencies between them are explicit, narrow and acyclic, passed as ports. Application code (the daemon's session object) owns lifecycle and workflow composition.
  6. Implemented support, machine availability and session capability are three different facts. The adapter says what is implemented; inventory and admission say what this machine can provide; the selected driver and current conditions say what this session can do. Callers get the capability at the scope of their operation.
  7. Vendor behaviour stays behind the boundary; the style of its expression is free. Prefer data and pure strategies where they make an integration simpler; allow a small harness-local strategy implementation where forcing it into declarations would build an interpreter.
  8. The server never holds a process or a socket to a harness. It decides; the daemon executes. This is inherited from the layers design and is what makes server and daemon restarts independent events.

4. The design

4.1 The Adapter

One TypeScript type, the composition of sixteen section types, with no optional fields. One directory per harness under packages/harness/src/adapters/, one file per section. Each section is either supported(value) or declined(reason). Sections split into host-only (anything naming a path, a process or a file) and browser-safe (descriptor, catalog, composer rules), and the browser entry may import only the second group.

The type is today's AgentManifest, renamed. It grows sections; it does not get a rival. Capabilities are not a section. The adapter's support matrix (which sections are supported, which declined and why) is one input to capability; see §4.7 for the other two. Item identity is not a section: each grammar produces record and sub-item identity, and the Store combines it with conversation namespace and file incarnation under the invariant in §5.

A Driver is not handed the whole Adapter. It receives a typed subset, the sections it owns, so the read restriction is a type rather than a rule. The same holds for the Store and Inventory.

4.2 The four mechanisms

Three mechanisms and one projection. Each mechanism holds one kind of thing and consumes the sections designed for it; each is harness-free and could serve a harness that did not exist when it was written. The Descriptor holds nothing and is not a mechanism: it is the browser-safe projection of an adapter.

4.6 The runtime stack it plugs into

From Terminal Layers in Code, restated so this document stands alone. The server's ServerSession is the record and the lifetime policy. The daemon's DaemonSession owns, per session, its processes, its Terminal if any, and its Driver if any. A Terminal is a surface (attachment, screen, applied size) over one process it does not own. A DurableProcess is the door to one podium-host, the small C process that holds the child and outlives daemon and server. Ownership flows one way and nothing changes hands on park, resume, shell-to-agent upgrade or native attach. The Driver is constructed by DaemonSession with the Adapter and either a Terminal (headed) or an engine address (headless), and owns nothing below itself.

4.8 Construction sequence and failure ownership

The Driver receives a Terminal or an engine address and owns nothing below itself. Launch, environment and instrumentation are its sections. Those statements coexist only with an explicit sequence, owned by DaemonSession:

StepWho actsReadsOn failure, who cleans up
1 prepareDriver family (pure)launch, environment, instrumentationnothing to clean; spawn is refused with the reason
2 create or adopt processDaemonSession via DurableProcessthe prepared specDaemonSession: if instrumentation was installed and spawn fails, remove it; report spawnError
3 attach surfaceDaemonSession builds a Terminal over the process (headed) or records the engine address (headless)—DaemonSession: process stays owned; a failed attach reports and may retry; nothing is killed
4 bind driverDaemonSession hands the Driver its typed sections and the Terminal or addressruntime, stateDaemonSession: an unbuildable driver is spawnError (fresh) or reattachFailed (adopt); the process is kept for an operator decision, never silently orphaned
5 observeDriverstate, instrumentation (decode)Driver reports degraded observation; the session stays live
6 detach or terminateDaemonSession, per ServerSession policy—park = drop the Terminal, keep the process; kill = dispose the process, then the Terminal

Process survival is not session recovery. After an adopt, the Driver must restore or explicitly invalidate pending deliveries, protocol subscriptions, open interactions and acceptance evidence. A surviving process with unrecoverable protocol state is reported as such, not presented as live.

5. Rules

  1. Every section is required. Absence is declined(reason), and an empty reason fails the registry check.
  2. One authoritative definition per concern. Readers depend on narrow typed interfaces or projections, never on the whole Adapter; a mechanism receives only the sections it owns as a typed subset. Additional narrow readers (the registry's family selection reading runtime, a bundled client reading pure composer rules) are legitimate, not defects.
  3. No vendor-specific operational behaviour outside adapters/ and driver/families/. The mechanical gate is the identifier lint, kept because a stated invariant without a check has already failed in this codebase; its allow-list requires a category per entry: leak (may only shrink) or policy (product preference such as the superagent's harness order in harness-defaults.ts, which is Podium policy and must not move into an adapter; points at a policy module). Comments, fixtures and historical migrations are excluded. Closed sets of harness names live only in the registry.
  4. Nothing inside adapters/ imports a mechanism. Nothing in a mechanism imports a specific adapter, only the Adapter type.
  5. Mechanisms do not own or instantiate each other; dependencies are explicit ports, narrow and acyclic. A live Driver reads history through an injected Store port. Login: Inventory owns the probe and the login command; DaemonSession opens a Terminal running it; Inventory re-probes on exit.
  6. The contract entries (/driver, /store, the root) import no host code: no child_process, net, http, no @podium/process. The server may import them. An import check enforces it.
  7. The Store is both-sides for file-chain and mirror sources. The SQLite source is host-only; the lake serves OpenCode only while its machine is reachable until its database is mirrored.
  8. Bundled browser code and the wire descriptor are different things. The wire descriptor is versioned, serialisable data (label, brand, icon, catalog, capability flags, supported controls) an older client renders inside a schema it already knows; consumers ignore unknown fields and the schema widens the parser first. Composer interpretation is authoritative on the daemon, which serves the resulting state; the bundled pure rules in the browser entry are a fallback for harnesses that client build knows. No remote rule interpreter. An older server likewise does not parse a newer harness's mirrored transcript: it reports the session as unreadable at its version rather than guessing.
  9. Identity invariant: the same logical native record and sub-item receive the same identity whether the bytes are read live, mirrored, relocated or replayed. This requires agreement on conversation namespace, logical file incarnation, record identity or position, and sub-item mapping, not only a shared parser. The Store owns that agreement; the search indexer consumes normalised items and never a harness's records.
  10. "Adapter" is a declarative record, not a ports-and-adapters implementation; the mechanisms are the port implementations. The package readme says so.

7. Acceptance for the whole design

  • The boundary lint passes with an empty allow-list for apps/daemon, apps/server, apps/web, apps/mobile, packages/client-core, packages/model, packages/protocol, packages/runtime.
  • Adding a harness on existing mechanisms touches adapters/<name>/ and one registry line. A test adds a fixture harness this way with meaningful supported behaviour (not a column of declines) and every mechanism serves it through the real server-to-daemon route.
  • The driver conformance suite runs every family. The Store golden tests run every declared grammar live and mirrored with identical ids, and cover truncation, archived incarnations, partial records, relocation and reconnect replay. The Inventory probe fixture runs per harness.
  • Behavioural guarantees are exercised through the application-to-daemon route, not only against a driver: receipts, typed refusals, configure timing, attachment semantics, capability resolution at all three scopes.
  • Recovery under failure is tested at the points that matter: restart or disconnect after delivery but before acknowledgement, during an open interaction, while a native terminal holds control, and during transcript mirroring; each asserts honest recovery or explicit uncertainty.
  • Cross-version: an older client renders a new descriptor inside its schema and unsupported operations fail explicitly; an older server refuses rather than misparses a newer harness's transcript.
  • Removal is proven by consumption, not by grep alone: the lake, the indexer, discovery, credentials, composer and runtime selection are shown to consume the new boundaries.
  • The generated support matrix (harness by section, supported or declined with reason) exists and is the first of the three capability inputs; it is not presented as the session's capability.
  • grep for AgentSession, the legacy delivery symbols, child_process under driver/families, and the two env switches returns nothing.

8. Risks

  • Boilerplate declines. Sixteen sections by six harnesses invites declined('n/a'). The registry refuses an empty reason; the matrix makes declines visible.
  • Bundle leakage. The root entry of the harness package must not pull driver families into the server or clients. The contract-entry import check covers the root.
  • Package merge size. Three packages into one is a large diff. It is directory moves and import rewrites with no behaviour change, landed in one issue with the lint on.
  • OpenCode's SQLite store is not mirrored and needs a native module the server lacks. The design states the limitation rather than hiding it.
  • Rigidity. Rev 1 elevated defaults into laws (exactly four mechanisms, one reader, no calls, a directory per harness for any harness). Rev 2 replaces them with composition rules; the residual risk is implementers reintroducing them as lint.
  • Sixteen files per harness is organisation, not a criterion. Sixteen typed sections are the requirement; trivial declarations may share a file.
  • Overlap with POD-4104, which owns the packaging. This spec proposes an amendment (one package, four mechanisms, adapter naming, state as a section); the two epics must agree before step 2.

9. Open points, after review

The five rev 1 questions were answered by the independent review and folded in: narrow readers instead of a split composer section; exec through the one-shot override, not a fifth mechanism; Descriptor is a projection; families per protocol; one package with tested entry points. What remains open:

  1. OpenCode's SQLite store: mirror it, or accept that the lake serves OpenCode only while the machine is reachable. POD-4104's open point; a decision is needed before POD-4082.
  2. The exact wire schema of the served descriptor and its version policy, to be fixed in POD-4118 with the widen-first rule.
  3. Which allow-list entries are policy: an inventory pass in POD-4120 decides each one with a one-line reason.

10. Decision history

  • A shared "EngineLink" abstraction over the three headless protocols was proposed and retracted: they share a process mechanism and nothing else.
  • "Reader" as the name for the transcript mechanism was retracted: it implied the whole read side. The mechanism is the Store, and it covers discovery too.
  • Terminal owning its process was retracted: parking would destroy the owner and keep the owned. The session owns processes; the Terminal is a surface.
  • Two packages (knowledge and mechanism) were proposed and retracted in favour of one: the lint enforces the direction, and a reader needs a one-word answer to "where is the harness code".
  • Alternative names (Archive, Installation, Profile) were considered and rejected in favour of Store, Inventory, Descriptor.
  • Rev 2, after independent review: "one owning mechanism per section" became "one authoritative definition, narrow readers"; "mechanisms never call" became "never own or instantiate, explicit acyclic ports"; capability split into implemented, available, effective; bundled client code separated from the wire descriptor; identity invariant stated and the indexer put in scope; construction and failure ownership specified; extensibility promise qualified; exec via the one-shot override; Descriptor named a projection; handoff assigned to the Store; policy references (superagent harness order) kept out of adapters and out of the leak count.

11. Review input

Rev 1 was reviewed independently on 2026-09-20 against main at 692d8c8e8 (a static architecture review; the reviewer did not run tests and noted that some "done" labels refer to the integration branch). Verdict: approve the direction, request targeted revisions, roughly 8/10. The review's three most important amendments, all applied here: separate static support from effective capability; distinguish bundled browser code from wire descriptors; replace absolute one-reader and no-call rules with explicit narrow composition. One recommendation was taken with a modification: the identifier lint stays as the mechanical gate, with a policy category, rather than being replaced by a behavioural definition that no check can verify. The review is attached to this issue as review_outcome.md.
