Daemon Link Planes

Every link between server, supervisor, daemon and the processes on a machine, the three kinds of traffic on them, and what splitting the server-to-daemon link would cost. Parked until the layer work is done; kept so the discussion is not lost.

1. The planes on the server-to-daemon link

Every link in the system, network and local, drawn once so the plane discussion is about real sockets. Then the planes, then what a split would cost.

The update grant, confirmed

The updateGrant frame is a member of the /daemon control union and the daemon has a handler for it. That handler is a three-way switch, read from the daemon's boot environment. If the supervisor owns updates, the daemon forwards the grant to the supervisor over the local update-control socket. If the daemon has no parent server, it applies the grant itself, which is the pre-supervisor installation still being migrated. In an all-in-one process it answers with an update status of rejected, naming the duplicate route. The server, for its part, sends grants to whichever of the supervisor or the compatibility participant it has for that machine, and a supervisor always wins. So the machine plane is one link with a migration-window second inlet, not a missing plane.

What the split costs, honestly

  • Two handshakes and two auth exchanges per daemon instead of one. The peer dialer is shared code, so this is one more call site, but it is one more thing that can be half up.
  • Two connection state machines with independent reconnect timers. "Daemon online" becomes "control up, stream up", and the UI has to say which one is missing.
  • Cross-plane ordering is no longer free. A kill on control and bytes on stream can arrive in either order. The epoch fence handles the dangerous direction: bytes for a Terminal that no longer exists are dropped. The benign direction, bytes arriving before the bind, is handled by the stream not opening until bind has answered.
  • The in-process local link for all-in-one deployments must model two channels too, or it silently keeps head-of-line blocking on the one topology that hides it.
  • Proxies and per-host connection limits. Two sockets per daemon doubles the count a tunnel or a corporate proxy sees. Small numbers, but it is a new line in the deployment notes.
  • Observability doubles. Each plane needs its own liveness, lag and window-size metrics, or a stall on one is misread as a stall on the other.

The alternatives, side by side

OptionWhat changesFixes head-of-line?Fixes loss and duplicates?Complexity added
A. One socket, channels in the envelopeEvery frame tagged with a channel; stream channel gets seq and ackNo. One TCP stream, one event loop, a slow handler still blocks the readerYesLowest
B. Two sockets: control and streamStream traffic moves to its own connection with its own readerYes at the transport; not yet at the event loopYesModerate, listed above
C. B plus a worker for the stream planeThe stream reader and Terminal I/O run on a worker thread in the daemon (and the fan-out on the server)Yes, fullyYesHighest: shared state between threads, message passing for every byte
D. Worker only, one socketHandlers move off the loop, socket stays sharedPartly: the loop is free but frames still queue behind each other on the wireNo, unless A is done tooModerate, and it does not fix the wire

Recommendation: B now, C only when measured. A and B share the same envelope work, so B is A plus one connection. B makes each plane observable on its own, which is what turns "the terminal feels laggy" into a number. C is the right answer to a specific symptom, a stalled frames bucket in the daemon's loop profile, and should wait for that symptom to show up on B rather than be built on suspicion.

The machine plane does not change. It is already a separate link and a separate process; the work is to say so and stop routing inventory and update traffic through the session socket.

What stays the same regardless of option

  • The daemon dials out; the server never connects in. NAT and tunnels do not care how many sockets that is.
  • Idempotency lives in handlers, not in the framing. A REST endpoint would need the same request ids and keys; it would only lose the push direction.
  • Durability lives in podium-host, not in any connection. Every link can drop and the process, its ring and its lease stay where they are.

2. The server and daemon seam today

Where the six objects sit relative to the network, and where the code that crosses it lives. Verified on the integration base, 2026-09-20.

Is it one clean seam?

AspectWhereVerdict
Frame shapespackages/protocol/src/messages/: one zod union per direction, plus terminal, binary envelope and the in-process local linkclean. Nothing crosses the network that is not declared here.
Server inboundapps/server/src/gateway/daemon-frame-routing.ts: a total table from frame type to owning port (sessions, machines, hosts, conversations, rpc, headless, agentRelay, approvals, updates, logs) and the plane and class of each frameclean. One place to ask "who handles this frame".
Daemon inboundapps/daemon/src/control/registry.ts: one dispatcher over 17 handler families (sessions, runtime, discovery, transcripts, files, exec, headless, handoff, workspace, approvals, credentials, inventory, logs, updates, server transfer, server endpoint, shipping)clean. The families are the honest list of what the daemon does for the server.
Request correlationapps/server/src/modules/daemon-request.ts: one broker minting request ids with timeouts and no retry, used by machines/rpc.ts and the runtime gatewaypartial. Spawn, kill, reattach and resize are fire-and-forget with out-of-band replies matched by session id. The planes page lists this as the control-plane fix.
Server outbound24 files call the machine port directly: relay.ts, most of modules/sessions/session-*.ts, hosts, issues, approvals, logs, superagentspread. There is no single "daemon client" on the server. Phase 0 removes the worst caller (the inbox loop); the rest is a Phase 3 consolidation if the planes work happens.
Daemon outbound24 files call ctx.send; the outbox for durable runtime events lives in connection-state.tsspread, but bounded: every send goes through one send on the connection state, so a stream-plane envelope can be added in one place.

Where the six objects sit: Session and the viewer surface are server code and never hold a process or a socket. RuntimeDriver, Terminal, DurableProcess and podium-host are machine code and never know the server exists beyond the connection state that dispatches to them. The seam between is the protocol package for shapes and one router per side for inbound frames. That is the part this epic must keep clean, and POD-4437 pins it. Consolidating outbound sends into one daemon client per side is the first concrete item if this page is picked up: it is where a stream-plane envelope and a control-plane idempotency key would be added once instead of in two dozen files.
