# POD-4819 — Harness receipt proof (Phase B of POD-4720)

Status: design for review, 2026-09-29. Read on `issue/4720-acknowledged-message-delivery-chain`
at `124f91387`. Evidence: code (cited `path:line`), the installed Claude Code 2.1.284 binary
(read, not run), and the protocol types generated by codex-cli 0.155.0
(`codex app-server generate-ts`). **Measure** marks a claim that POD-4834 must confirm on the
real CLIs before anything relies on it.

**Run, not read.** A fact about an agent program counts only when it was observed on the real
CLI: the fake model server logs what reached the model, hooks and protocol frames are logged,
the history file is read in file order. Reading code, a binary or docs gives a candidate, marked
**read**. Every cell in §4 is either *run* (with its evidence under
`docs/measurements/pod-4834-receipt-proof/`) or *read*, and nothing is implemented on a *read*
cell. POD-4834 turns every *read* cell into a *run* cell.

## 1. Goal and scope

Know, for every message and every agent program, whether the message reached the agent's
conversation. End with a yes or a no in almost every case, and with `unknown` only when neither
can be known. Never a false yes, never a false no.

Not in this phase:

- how a message is typed into a terminal, and never leaving text in the input box — Phase D
  (POD-4821);
- which delivery modes exist and their time limits — Phase C (POD-4820);
- the daemon's own durable storage — POD-4766 / POD-4777. The operator designs it; §10 lists
  only what this phase needs from it.

## 2. Words used here

- **Delivery mode** — when a message is typed: `when-ready`, `queue`, `interrupt`, `steer`,
  `at-boundary` (`packages/harness/src/driver/turns.ts:21`). The stored message path uses
  `when-ready` and `interrupt` today (`packages/harness/src/driver/delivery-queue.ts`).
- **Sender** — a person (chat), an agent (mail), or the system (steward, automations,
  auto-continue, notices). The sender is not a mode: agent mail is typed `when-ready` like chat.
- **Wrapped message** — every message not written by a person is typed inside
  `[podium message <id> …] … [end podium message <id>]`
  (`apps/server/src/modules/messages/render.ts:135`), so our id lands in the agent's own history.
  A person's chat is typed as is, without our id (a deliberate decision, `render.ts:187-211`).
- **Agent program** — the harness: Claude Code, Codex, Grok, OpenCode, Cursor, Pi, driven either
  through a terminal (PTY) or through a protocol (Claude SDK stream-json, Codex app-server,
  OpenCode HTTP v1/v2, Grok ACP).
- **Delivered** — the message is in the agent's conversation history: the model reads it at its
  next step, and it survives a restart of the agent program. What the model then does with it
  ("answered") is not a delivery status; the transcript shows it.

## 3. Statuses

One list, used by the server, the daemon and the drivers. A message only moves forward
(`packages/model/src/entities/message-delivery.ts`). A status may be skipped when its signal
does not exist for an agent program (§4); the message then moves straight to the strongest
status that is known.

| Status | Meaning | Set by |
|---|---|---|
| `stored` | The server has it. | server |
| `dispatched` | The server sent it toward the agent's machine. | server |
| `reached-machine` | The daemon saved it on its disk. | daemon (POD-4777) |
| `typing` | The daemon saved "about to hand it over" on disk, just before the first keystroke or request. A retract loses from here. | daemon (POD-4777) |
| `typed` | Handed over: the text and Enter were written, or the request was sent. | driver |
| **`accepted`** (new) | The agent program took it, but it may still wait inside the agent program (Claude's own queue, a steer waiting for the next model step, OpenCode's queue). | driver, from the agent program's own signal (§4) |
| `confirmed` | In the agent's conversation history. **This is "delivered".** | driver or server, from the history (§4, §5) |
| `cancelled` | Retracted before `typing`. | daemon |
| `failed` + cause | Definitely not in the conversation (§7). Safe to resend. | daemon or server |
| `expired` | Never handed over within its time limit (only from `stored`). | server |
| `unknown` | Handed over, and no yes or no can be expected any more (§9). Late proof still moves it to `confirmed` (§6). | daemon or server |

New moves: `typed → accepted`, `accepted → confirmed | failed | unknown`, and every move that
today enters `confirmed` from before `typed` may also enter `accepted`. `unknown → confirmed`
already exists.

**Details kept with the message, not statuses:**

- *proof* — what set `accepted` / `confirmed`: the agent program's reply, a submit hook, or a
  history entry;
- *matched by* — our id, the agent program's id, or order plus text (§5); plus *merged* when our
  text was inside a larger entry (§5.5);
- *ids* — the transcript entry (POD-4774) and the agent program's own ids (POD-4841);
- *failure cause* (§7);
- *mode facts* — the mode actually used (`deliveredAs`), whether an interrupt stopped the running
  turn, whether a steer joined the running turn or became the next one (Phase C).

**The driver speaks the same words.** Today `send()` answers `accepted` / `queued` / `refused` /
`unverified` (`turns.ts`), and "accepted" means anything from "we started trying" (Claude SDK,
Grok ACP) to "recorded" (OpenCode v2). After this phase a driver reports, by message id:
`typed`, `accepted` (with proof and ids), `confirmed` (with entry and ids), `refused` (becomes
`failed`, §7), or `unverified` (the message stays `typed` or `accepted`; §6 and §9 decide what
follows). Each report may arrive after `send()` returned.

**What readers of "delivered" keep.** The chat bubble, retract, sender notices (POD-4778) and
`podium mail status` all mean "the agent has it", which is `confirmed`. They keep that meaning;
only the drivers that set it too early change (§4). A reader that should also treat `accepted`
as "on its way" says so explicitly. Cost: `accepted` is a new value of the status column, which
needs a migration of its allowed values (the expand-only route POD-4765 used).

## 5. Matching a signal to our message

Strongest first. A driver uses the strongest one its agent program allows and records which.

### 5.1 Our id goes in and comes back

The agent program stores our id with the message: OpenCode v1/v2 and Codex (POD-4835) today;
Claude SDK (POD-4836) planned; every wrapped message on every agent program, because the id is in
the text. Exact, survives a restart, and is found even when the text was merged with other text.

### 5.2 The agent program returns its own id for our call

Codex `turn/start` returns a turn id; its user item belongs to that turn. Exact while we keep
the id (POD-4841).

### 5.3 Order plus text (a person's chat on a terminal agent)

The only case with no id anywhere. Today it is matched by an exact hash of the text, so any
change fails (a draft merged in, whitespace, a harness rewrite), and two identical short texts
("yes", "yes") cannot be told apart.

**Idea.** The first *prompt* entry after our saved position (§5.4) is ours, as long as nobody
else submitted anything in between. The text then only has to agree.

**Can the daemon know nobody else submitted? Not today** (read in code, 2026-09-29):

- On sessions run by podium-host, only the daemon may write to the terminal
  (`packages/pty/vendor/podium-host/host.c:405-408, 486-491`: one writer lease, held by the daemon). A
  person's keystrokes from the web, mobile or desktop terminal also reach the terminal through
  the daemon (`input` / `ptyInput` frames, `apps/daemon/src/control/native-terminal-input.ts:33-36`).
  So every write passes through one process.
- But the daemon records them nowhere in one place. The message delivery queue types one
  message at a time (`delivery-queue.ts`, single-flight), while Draft Sync
  (`apps/daemon/src/composer-sync.ts:275-279`), answers to menus (`terminal-driver.ts:2209`),
  interrupt keys, the Ctrl-U clear after an interrupt (`apps/daemon/src/session-observers.ts:607-615`), the
  Ctrl-L redraw and a person's keystrokes all write around it. Draft Sync can type while a
  message's paste is in flight: its "someone is typing" signal (`composer-sync.ts:252`) is fed
  only by input frames, never by the driver's own writes. Only the server keeps a timestamp of a
  person's input (`apps/server/src/modules/sessions/terminal.ts:659-722`).
- Sessions on the abduco fallback can be typed into by anyone running `abduco -a`
  (`packages/pty/src/durable-process.ts:198-215`), unseen by the daemon.
- The history readers emit some entries nobody typed as `role: 'user'`: Claude compaction
  summaries and slash-command records (`packages/harness/src/adapters/claude-code/transcript.ts:320-332`),
  interrupt markers (Claude, Codex `turn_aborted`, OpenCode), empty image or file markers. A
  "first user entry after our position" can therefore be one of these.

**What makes it knowable (the core — it only observes, it never blocks anything):**

1. **Input log.** One ordered, per-session log on the daemon, directly under the terminal write
   call, recording every write with its origin (message id, draft, answer, key, person) and every
   Enter. It only has to cover the time a message is open.
2. **Draft Sync is gone** (POD-4851, operator decision 2026-09-29), so no second Podium writer
   types into the input box.
3. **Entry kinds.** The history readers mark entries nobody typed (compaction summary, slash
   command, interrupt marker, empty marker, a queued prompt of kind task-notification), and
   matching looks only at *prompt* entries.
4. **Abduco sessions** never use order, only text.

**Rule.** When message M is typed, the daemon saves the position and time (§5.4) and the input
log's index. For the first prompt entry E after the position ("between M and E" runs up to the
moment the daemon reads E, which errs toward the text-only row; M's own Enter and retries do not
count as another Enter):

| Other Enter in the log between M and E? | E's text | Result |
|---|---|---|
| No | equals M (whitespace collapsed) | `confirmed`, matched by order |
| No | contains M | `confirmed`, matched by order, *merged* |
| No | neither | Not ours: something submitted that the log did not see. Nothing is credited; the watch closes as `unknown`, and the self-check alarm (§9) records the log gap. |
| Yes | — | Order is not used. Text only: the first prompt entry after the position that equals M (or contains it, *merged*). If two open messages have the same text, none is credited. |

Where the program has a submit hook (Claude), the same rule is applied to the hook for
`accepted`, and the hook's `prompt_id` then names the record exactly.

**What order adds over text alone:** identical short texts are told apart; the text check can
tolerate what the program changes (whitespace, placeholders) because it only has to agree, not
identify; a merged draft is reported as *merged* instead of `unverified`. **Why text is still
checked:** it is what catches a gap in the log or in the entry kinds. Order alone would credit
the wrong entry silently.

**Optional optimization: a typing lock.** Because every write passes through the daemon (above),
the daemon can hold other writes to a session while one message is pasted and submitted, so a
person's keystrokes can never land inside it. It is an optimization only: the core above decides
correctly without it, and it can never stop anything from working.

- It is a lease with a hard expiry (about 1–2 s, measured per program), released by its own timer,
  never by the typing finishing; a hung typing still releases it.
- Held writes (a person's keystrokes, answers, keys) are buffered with a size cap and written in
  order at release; an overflow releases early.
- It covers only the paste, the Enter and a short settle, never the wait for proof.
- A switch turns it off; with it off, or on the abduco fallback, the core still applies.
- Tests: a typing call that never settles still releases the lease at its expiry and flushes the
  held input; the next message is typed after that.

One more thing seen while reading, **to verify** before anything is filed: Claude's origin list
(`packages/harness/src/adapters/claude-code/state-provider.ts:389-393, 540-543`) is fed only by
input frames containing an Enter, while every `UserPromptSubmit` takes its oldest entry, so a
prompt the driver typed might take a person's origin. The input log would replace that list.

### 5.4 Only entries written after the send count

POD-4838. When a watch is armed, before the first byte, the daemon saves the transcript
position (segment and byte offset) and the time. An entry counts only if it lies after that
position in the same history file, or — in a different file (resume, rotation, full re-read) —
its own timestamp is at or after the saved time. Today no such floor exists, and a full re-read
can let an older identical prompt confirm a new send
(`apps/daemon/src/runtime/terminal-driver.ts:1137-1146`). The position is exact within one file;
the time covers the cases where the position cannot, and the order (§5.3) separates two messages
sent close together, which time alone cannot.

### 5.5 Merged text

When the entry contains our exact text inside a larger text, the message is `confirmed` with
*merged* set. It reached the agent, but someone else's words went with it; that is a Phase D
failure (POD-4821) and is reported as one. For wrapped messages the id is found either way.

## 6. Late proof

POD-4840. A time window decides only when the user is shown "not confirmed yet". It never
decides the final answer. A watch stays open after the window, bounded as §9 says, and proof
that arrives later moves the message forward (`typed`/`accepted`/`unknown` → `confirmed`).
Wrapped messages already work this way through the server's id match
(`apps/server/src/modules/messages/service.ts:2269-2299`); the issue covers chat and the agent
programs' own ids.

## 7. A proven "no"

`failed` is final, and the sender is told it is safe to resend. So a "no" needs direct evidence
from the agent program or from what is on its screen. Never from a status reading (§8).

### 7.1 What counts

| # | Evidence | Applies to | Cause |
|---|---|---|---|
| N1 | The driver refused before writing anything. A refusal is by contract a reply that nothing was written (`turns.ts`, `RefusalReason`); POD-4839 audits every refusal path and turns any that can follow a write into `unverified`. | every driver | `refused` + reason |
| N2 | The agent program rejected the request in an explicit reply: a JSON-RPC error reply, an HTTP 4xx. A timeout or a dropped connection is not a reply. | protocol drivers | `rejected-by-agent` + reason |
| N3 | The agent program keeps our id or gave us its own, answers through its own protocol that it has no turn open (its answer, not our reading of its phase), and its history has no item with that id. | Codex (by `clientId`, `thread/read`), OpenCode v1/v2 (by message id), Claude SDK (by uuid) | `not-recorded` |
| N4 | The agent program's process exited, and its history, read to the end after the exit, has no entry for the message after the saved position (§5.4). Whatever it held in memory (Claude's queue, the input box) died with it. | every agent program | `agent-exited` |
| N5 | Terminal: after Enter and the existing submit retries (`packages/harness/src/driver/families/terminal/injection.ts:436-465`), the input box shows exactly our text; the history has no entry for it after the saved position; the input log shows nobody else typed since (§5.3, so N5 needs the input log); the daemon then clears the box with the program's clear keys and a second screen read shows it empty. | programs with an input-box reader: Claude Code and Codex CLI today (`packages/harness/src/adapters/claude-code/composer.ts:31-95`, used by Draft Sync) | `not-submitted` |

N5 needs the clear. Text left in the box can still be submitted later by anyone pressing Enter, so
a "no" without the verified clear would be false. If the clear cannot be verified, the message
stays open and the user sees "left in the agent's input box". Clearing and never leaving text
behind is Phase D's job (POD-4821); this phase only uses the verified result as evidence. A box
that holds our text plus other text is not N5: it is someone else's draft and is never cleared.

These add to the causes that already exist for a message that was never handed over (the
agent never became ready, the session or issue is gone, the delivery failed before typing —
POD-4778). The existing `unconfirmed` cause is not a "no": it is what `unknown` is made of today.

### 7.2 What is not a "no"

These leave the message open (`typed` or `accepted`), and later `unknown` (§9):

- the proof window passed;
- the agent looks idle and the history has nothing new — the entry may still come, or our reader
  may lag;
- the input box is empty and the history has nothing — the text may have been taken and not yet
  written, or swallowed;
- a later prompt entry that is not ours — it closes the watch as `unknown` (§9), not `failed`;
- a timeout or a dropped connection on a protocol request;
- anything read only from an agent state (§8).

## 8. Using agent states that are not fully reliable

Agent phases (idle, working, needs input) and composer readings are still being made reliable
elsewhere. This design never lets them decide an answer:

- A **yes** comes only from the agent program's own record: its reply, its hook, its history
  entry, our id or its id.
- A **no** comes only from the direct evidence listed in §7.
- A state decides only **when to look**: when to read the screen, when to re-read the history,
  when to stop nudging. A wrong state therefore costs time (we look too early, and look again),
  never a wrong status.

One finding for the state work: Claude fires `UserPromptSubmit` at Enter also for a prompt that
waits in its queue (2.1.284 binary), and our state tracking opens a new turn on every such hook
(`packages/harness/src/adapters/claude-code/state-provider.ts`, `turnEpoch += 1`). A person
typing in an attached terminal during a turn may make us believe a second turn started.
POD-4834 confirms it; a bug is filed if so. A second one from the same binary read: a prompt
that waited in Claude's queue and runs after the turn ends gets a new `prompt_id`, but no
`UserPromptSubmit` fires for it, so a hook-driven turn start is missed there.

## 9. When `unknown` is final, and what the user sees

- After the proof window with neither a yes nor a no, the user sees "typed, not confirmed yet".
- The message becomes `unknown` when the watch closes without an answer: the agent program
  recorded a later *prompt* entry (§5.3) after our position that is not ours and our text is not
  in the input box, or a maximum wait passed (POD-4840 chooses and justifies the number), or the
  history was rewritten (compaction, `/clear`) across the window.
- A message that reached `accepted` stays `accepted` when its watch closes without a history
  entry: the agent program's own signal said it took the message, so it is not `unknown`. Only a
  `typed` message becomes `unknown`.
- `unknown` shows "check before resending" with the nearest transcript entries, as POD-4778
  decided for agent senders.
- **Self-check alarm:** the daemon logs an alarm, and the server records it, when a message
  marked `failed` later appears in the agent's history (the rules in §7 did not hold), or when
  order matching finds a prompt entry the input log did not see (§5.3). `unknown → confirmed` is
  expected and not an alarm.

## 10. Restart — what this phase needs from daemon storage

The daemon storage design is the operator's (POD-4766, POD-4777). This phase only needs these
facts per message to be on disk before the first byte, and kept until the message is settled:

- our message id and the exact typed text (after the paste boundary);
- the transcript position and time from §5.4;
- the agent program's ids once known (POD-4841);
- the last status reached (`typing`, `typed`, `accepted`).

With them, recovery needs no new driver call: after a restart the daemon opens a watch again for
every stored message still `typing`, `typed` or `accepted`, and the normal history re-read
matches them with §5. Without them, a message typed before a crash stays `unknown`.

## 11. Facts found during this design

- **Claude's own queue** (*run* on 2.1.284, see §4): a prompt entered while a turn runs waits in
  Claude's queue; `UserPromptSubmit` runs at Enter with the running turn's `prompt_id`; a
  `queue-operation` `enqueue` is written then, and a `queued_command` attachment when the running
  turn takes it in at a tool boundary. *Read* only, not yet run: `ctrl+x ctrl+s` /
  `ctrl+enter` ("send now") moves running tools to the background and delivers without stopping
  the turn, and Escape can pull queued prompts back into the input box. This is native steer for Claude (Phase C).
- **System sends** were typed without a message record (steward nudges, automations,
  auto-continue, some superagent sends, the old issue-mail nudge). POD-4846 is moving them onto
  messages; its first part (steward nudges) landed at `124f91387`.
- **A failed system send landed in the person's input box** — POD-4844.
- **Low-priority issue mail under 6000 characters** is typed in full but stops at `typed` —
  POD-4845.
- **A refusal ends as `unknown`** although nothing was written — POD-4839.
- **An acknowledged Codex steer can be lost** when the turn is interrupted before Codex's next
  model call, while we report it accepted — POD-4849. It is the clearest case for `accepted`
  being separate from `confirmed`: the steer rests at `accepted`, and N3 (§7) turns it into
  `failed` once the turn is over and `thread/read` has no item with our id.
