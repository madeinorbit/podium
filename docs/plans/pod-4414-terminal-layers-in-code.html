Terminal Layers in Code

Which of the ten conceptual layers deserve to be separate objects in code, judged by which user-visible paths pass through them; who owns whom and who may call whom in the three driver shapes; and the code structure this epic ends with. The server-to-daemon link is a separate page.

Refreshed at 33820c7de for Phase 2 (POD-4434, POD-4505, POD-4499, POD-4490, POD-4476, POD-4478). Every path and symbol below was checked against that tree with ls, rg and file reads; machinery Phase 2 deleted is marked deleted, not silently dropped.

1. Where each user-visible path enters the stack

Six things a user can open, drawn as lanes falling through the ten layers. A filled dot means the path instantiates that layer. A hollow dot means the layer is absent for that path. The bracket on the right marks layers that never appear without each other, which is the test for collapsing them.

The per-turn helper (child-turn, claude-sdk-host, host-protocol and their tests) is deleted, and @anthropic-ai/claude-agent-sdk is no longer a dependency of the harness package.

1b. Who owns whom, who talks to whom

Four shapes, one structure. A diamond-tailed arrow is ownership: the owner creates, holds and disposes. A dashed arrow is a reference: the pointer may use the target and never owns it. A dashed red slot is a part that this shape does not have. If the four columns look the same, the model is right.

Beside the stack: the Adapter and the Reader

The six objects are the runtime stack. One more thing sits beside it and is not a runtime object: harness knowledge, the Adapter (AgentManifest in @podium/harness, one manifest per harness in packages/harness/src/adapters/ with the exhaustive Record<BuiltinHarnessKind, AgentManifest> in packages/harness/src/registry.ts): transcript paths and record grammars, login probes, discovery layouts, model catalogs, hook payloads. It has consumers that never touch a process. The server's transcript lake mirrors harness files by a guarded byte read and parses them with the Adapter's grammar, for sessions Podium never launched, with no Driver and no DaemonSession. Discovery, inventory and every client that renders a harness are the same shape. POD-4104 names the offline half the Reader: Adapter grammar over a record store, no process.

Since POD-4476 (4.2) the closed set of harness names is derived from the manifests themselves (Object.keys over the total record, defined at L0 as BuiltinHarnessKind in @podium/model), so adding a harness grows the set with no second list to update; since POD-4478 (4.4) CLI installs and quota labels resolve through the machine Inventory (packages/harness/src/inventory/, surfaced as @podium/harness/inventory). The vendor-boundary allow-list ratcheted 491 -> 468 -> 432 with those two moves (HARNESS_BASELINE_TOTAL in scripts/harness-boundary-allowlist.ts).

The rule this adds: the Driver is the only way to act on a harness; the Adapter is the only place that knows about one. Driver and Reader both consume the Adapter and never each other. For the boundary lint that means the server may import @podium/harness/driver and @podium/harness/store and never @podium/harness/driver/host (the entries POD-4469 landed, checked by audit:harness-entries), rather than a flat ban on the package.

Three transitions the model has to survive, and does: park is "drop the Terminal", the process stays owned, and resume rebuilds a Terminal over it from the host's replay cursor. Upgrade a shell is "give a headed Driver the existing Terminal"; a headless Driver cannot take a shell, because it uses an address, not a surface. Native attach on a headless session is "add a second process and a Terminal over it", with the Driver unaware. A fourth since POD-4490: bind failure is "keep the engine, record it, invalidate pending turns" — DaemonSession.bindFailed on EngineBindUnrecoverable, with the adopt and resume arms deliberately skipping the reap so the survivor stays for an operator decision. The one constraint the model states rather than hides: one Terminal per Session at a time, because the terminal stream is keyed by session id.

3. Where the objects sit relative to the network

Session and the viewer surface are server code and hold no process and no socket. RuntimeDriver, Terminal, DurableProcess and podium-host are machine code and know nothing of the server beyond the daemon's connection state that dispatches to them. Frame shapes live in one package and inbound routing is one table per side; outbound sends are spread. The seam itself, with the diagram and the verdict per aspect, is on the Daemon Link Planes page, since cleaning it up is planes work, not object work.
