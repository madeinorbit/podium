# MobX entity model rules

Status: the rules are in `docs/agents/frontend-data.md` (adopted 2026-10-06/07, linked from AGENTS.md). This document is their rationale, the work they cause, and the history of the POD-5708 design talk.
Rule numbers below follow the discussion; the guide numbers them differently (its rule 5 = "one field, one question", 6 = "live by default", 7 = "working set").
Scope: the whole client (desktop via Tauri, web, phone) on the MobX pool (`packages/client-graph`).
Evidence: the measurements and quotes in the appendices (MobX docs, mobx-utils, mobx-state-tree, the Linear talks, experiments under `docs/plans/mobx-entity-model-rules-evidence/`, and a code audit of `integrate/4286-pilot` at 8d30f0da9b).
Engines: the desktop app runs in Tauri's system web view, so WebKit/JavaScriptCore on macOS and Linux and Chromium/V8 only on Windows. Our memory figures are measured in Bun (JavaScriptCore), so they are the representative ones.

Labels: **[MobX docs]** = stated by the MobX docs; **[house rule]** = our own reasoning; **[deviation]** = we knowingly differ from the docs' default, with the reason given.

## Open questions

- Later, only after measuring in the app: the keep list for recently closed values (designed in Appendix A), the working-set machinery (principles are in the rules).

## Appendix A: discussion notes and measurements (2026-10-06, as recorded during the talk; superseded wording kept for the numbers)
- Rule 4: where exactly is the line between an entity fact and a screen rule (for example "asking", "progress", a draft issue's display title)?
- Rule 2 follow-up: the screen layer (not entity models): plain MobX default there (`makeObservable`/plain getters), as the docs recommend for few objects? (Proposed, not decided.)
- Keeping VALUES after a screen closes. Neither ours nor MobX's `@computed` does this: both drop the value and recompute on reopen (`dec-reopen.ts`); `@computed` only keeps an empty container. MobX's own way to keep values is `keepAlive`: value kept, no background work while closed (marked stale, recomputed once on the next read), but never released while the object lives, with no public way to release it; the docs call it a memory-leak risk. A capped middle ground with public API only (`hold-cache.ts`, 14/14 checks): a holder keeps the value of recently closed fields up to a cap or time limit; its price is one background recompute per data change while kept (an observer makes MobX confirm the change), unlike `keepAlive`. Not decided; not measured in the app.
  - Option 3, measured (`keep-modes.ts`, 15/15 checks over drop/warm/keep): a `keepAlive` holder that reads `inner` through a public on/off switch keeps the value with NO background work (data changes only mark it stale; reopen is free if unchanged, one recompute if changed) and is released by flipping the switch (its inputs stop being watched). 20,000 fields closed, all inputs then changed: drop 9-14 ms, warm (option 2) 118-147 ms, keep (option 3) 16 ms (two runs); kept memory per field in that harness: drop 0.3 KB, warm 5.6 KB, keep 6.2 KB. Operator prefers option 3 (2026-10-06).
  - Proposed (operator, 2026-10-06: no per-field declaration, no cost measuring): every closed `@lazy` field goes into one least-recently-used list with one global count cap (a JS Map in insertion order: O(1) to touch and to evict), held the option-3 way; everything kept is dropped when the phone warns about memory or the app goes to the background. Precedent: Relay keeps a fixed-size buffer of recently released queries (`gcReleaseBufferSize`), React Query keeps unused queries for a time (`gcTime`); neither measures compute cost. Memory: ~6 KB per kept field measured in `keep-modes.ts` (small values, includes the holder), so the cap sets the overhead directly (1,000 kept fields ~ 6 MB). Only levers on a field: `equals` and a rare `keep: 'never'`. DECIDED by the operator 2026-10-06, starting cap ~2,000 fields. Bookkeeping cost of the first public-API build (`evict-overhead.ts`, 20,000 small fields, three runs; CPU on a busy box, ratios only): memory while shown 5.2 KB vs 3.5 KB per field today (+49%, the extra outer layer); per kept field 6.3 KB vs 3.0 KB for the cached value alone (bookkeeping about equals the value); CPU: first show and re-read +10-15%, closing 2-3x today (~2-4 µs per field), reopening a kept field ~2.4x faster than today. At cap 2,000: ~6.5 MB of bookkeeping. Where it went (`parts.ts`): an empty MobX computed is ~514 B, one with live dependency links ~1.7 KB, two listeners ~580 B, a box ~146 B, a Map entry ~88 B; the first build added a second computed per field (outer), a third (holder), a box and listeners. SLIM build (chosen shape): ONE `keepAlive` computed per field whose function reads a per-field off switch; `onBecomeUnobserved` puts it in the LRU; eviction flips the switch and reads it once, which drops its dependencies and value; untracked reads compute directly and cache nothing (as `keyedComputed`). 7/7 behaviour checks (`slim-check.ts`). Measured vs today: memory while shown 3.77 vs 3.47 KB per field (+9%); kept field 3.94 KB, i.e. the cached field itself, bookkeeping ~0.3 KB (switch + LRU entry); closing 3x faster than today, reopening a kept field ~5x faster; evicting costs ~5 µs per field.

## Appendix B: verification report (2026-10-06)

### Verdict
Correct, with caveats. A computed nobody reads never runs; one nothing observes drops its dependencies and its value. MobX's docs say one class per domain entity, one instance per entity, derived values as computeds, many small `observer` components reading late. Linear does the same: one decorated model class per entity in an object pool, read directly by `observer` views. Caveats: (1) "costs nothing" holds for CPU, not memory, with the docs' default declaration; (2) unobserved computeds are never cached, so imperative reads recompute every time; (3) a wide observed computed re-runs O(n) and with default equality re-renders on equal results; (4) screen rules on the entity model make a god object even if lazy.

### What a MobX cache object costs (`prealloc.ts`, `array-trim-v8.mjs`)
One `ComputedValue` (the same class whether made by `makeObservable`, `@computed`, `computedFn` or our `keyedComputed`) holds its function, last value, the list of what it read, the set of who reads it, state flags and its equality function: ~520 B unread (Bun/JSC). Watched, each dependency is recorded both ways (its list + a Set entry on the data), ~320 B for one dependency. On its first run MobX preallocates room for 100 dependencies and trims the length afterwards (mobx PR #3833); JSC keeps that ~830 B until the field runs a second time, V8 frees it at once (100-slot array trimmed to 1: 894 B in Bun, 64 B in Node 22). So every KB figure in this report is measured in Bun/JSC and overstates Chrome (V8) by up to ~0.8 KB per watched field; the phone's engine (Hermes) is not measured. The desktop app runs in Tauri's system web view: WebKit/JavaScriptCore on macOS and Linux (WebKitGTK), Chromium/V8 only on Windows (WebView2). So the Bun/JSC figures are the representative ones for most users, and MobX's ~830 B first-run reservation per watched field is real for them (possible fix: a small MobX patch or an upstream report; not decided). Our `keyedComputed` adds ~0.7 KB per watched field on top (lookup entry, one listener, two small functions).

## Appendix C: reviews during the discussion (2026-10-06)

### mobx-state-tree (MST) compared (2026-10-06; docs, source and issues, research report)
- Model = runtime type = schema = TypeScript type (`types.model({...})`, `Instance<typeof T>`); fields visible. Ours: the client schema is plain data and the class gets the fields at runtime; same single-source idea, less visible.
- Lazy only in part: each row still gets a full node subtree at load (`ObjectNode` constructor, `initializeChildNodes`); the observable object and per-instance views/actions are created on first access (RFC #810). Ours is lazier: nothing per field until a screen reads it.
- Views are per-instance MobX computeds made with `makeObservable` on first access; no eviction; parameterised views are not memoised. Same cost profile as `@computed`.
- References resolve through one identifier cache per tree; `safeReference` clears links to removed targets. Ours: the pool's identity map and relation index do the same.
- FAQ: not all state belongs in MST; plain MobX for local/UI state; volatile state for non-persistable things. Matches our three kinds of objects.
- Scale: the FAQ itself says performance-critical apps with "a huge amount of mutable data" are "better off by using 'raw' MobX"; issue #1683 ("2MB of data becomes ~600MB", "never intended to handle hundreds of thousands of nodes"), #440 (100,000-item array replace ~5 s vs 0.02 s in MobX), #2128 (applySnapshot slow on large stores).
- Worth taking: keep object identity on server updates (reconcile by id): our pool already does; one declared schema as the single source: decided; a link to a removed target becomes null (`safeReference`): our relation getters already answer null for a known target with no row (`models.ts` header comment). Nothing new to build. Not worth taking: the library itself or its eager per-node trees, for our target of tens of thousands of rows.

### Simplicity review (2026-10-06)
Simple and idiomatic as designed: components and UI stores are textbook MobX; `@lazy get x()` reads like `@computed get x()`; one field per question is MobX's one computed per derived value; three homes for three kinds of question.
Not yet simple or idiomatic:
1. (Schema kept: DECIDED 2026-10-06, the server shares the field definitions.) Stored fields are not written in the class: `installFields` adds `title`, `stage`, ... to the prototype at runtime from the client schema (`shared/schema.ts`, plain data: fields, relations with inverses, residency, editability). The server shares the field definitions through the zod schemas in `@podium/model` (each schema field cites one, checked by `schema.test.ts`), not this file. Weighed: the schema is the right single source (the pool needs the same metadata to maintain both directions of every link; Linear's decorators are also metadata, just written in the class). Cost: a reader of the class does not see the fields. Proposed: keep the schema; optionally add `declare readonly title: string` lines checked against the schema at compile time, for readability only. Not decided.
2. Companions: DECIDED 2026-10-06 (one screen model per screen; a companion class only when a screen has its own per-entity rules): each screen has ONE screen model class that holds its UI state (`@observable accessor`) and hands out its own companions (`readonly row = companion(issue => new SidebarIssue(issue, this))`, kept in a WeakMap so a companion dies with its issue); `Mission` hands out `MissionIssue` the same way, in the mission module. Then: a component's prop type says what it needs. A screen that needs screen rules hands out its own companion (sidebar rows get `SidebarIssue`, a mission card could get `MissionIssue`); a screen or shared component that needs only entity facts takes the bare `IssueModel` (a companion exposes `.issue` for those). Companions belong to one screen and never wrap another screen's companion. components receive the companion, not the issue: the sidebar model hands out `SidebarIssue` rows (`sidebar.roots`, `row.children`), a row component reads `row.label` and `row.issue.title`; `companion(SidebarIssue)` is called only inside the screen model. Earlier sketch for reference ( `export const sidebarIssue = companion(SidebarIssue)`; in a row component `const row = sidebarIssue(issue); return <div>{row.label}</div>`; the companion is ~50 B, stays with its issue, its `@lazy` fields are kept and dropped like any other): a decorator cannot take an argument, so "the sidebar's companion for this issue" needs one small helper, e.g. `const sidebarIssue = companion(SidebarIssue)`; `sidebarIssue(issue)` returns the one instance, created on first call, stored on the issue's hidden slot holder. That is the second and last API next to `@lazy`.
3. Today there are several cache entry points (`keyedComputed` called directly in ~19 files, `cachedGroup` 73 calls, `cachedKey` 25 calls); the target is `@lazy` + `companion` only. Filed as POD-5746 (Cache helper consolidation).
4. `@lazy` is simple to use, not simple inside (keepAlive + off switch + list): acceptable only with a small dedicated test suite, including "a dropped field stops watching its data".
5. One private MobX call (`_getGlobalState`, to tell a read inside a screen from one outside) is confined to one helper file by `lint:mobx-private`. CHECKED replaceable with public API (`public-tracked.ts`, `public-tracked-slim.ts`, 4/4 each): on a cache miss create the computed, listen with `onBecomeObserved` during the read, keep it only if that fired; otherwise release it at once, with the switch flip and the release read inside ONE action (outside an action MobX defers the unhooking to the next batch end). The same applies to eviction. Cost: a read outside a screen allocates a short-lived computed.
6. Write-path indexes, if allowed, are a mechanism outside MobX; keep them rare and declared.

### Self-review (2026-10-06, after the decisions so far)
Sound: three kinds of objects with one home per question; `@lazy` reads like `@computed`; public MobX API only; the schema as single source; every claim measured or quoted.
Doubts:
1. Order of work: we tuned the cost per field (keep list, switches) while the NUMBER of objects is still unbounded. The working set bounds objects, counts and the keep list at once; its definition should come first.
2. `@lazy` is becoming a small framework (lazy creation, screen detection, keep list, end-of-task release, memory-pressure drop). The keep list is the one part not yet shown to pay off in the app. Build order DECIDED 2026-10-06 (keep it simple): `@lazy` core only = create on the first watched read, store on the object, drop when no screen watches, reads outside a screen compute directly, public MobX API only. The keep list, end-of-task caching of outside reads and the memory-pressure drop come later, inside `@lazy`, only once measured in the app.
3. Companions and screen models are two new concepts; they are only worth it on screens with per-entity rules (the sidebar today). Rule: no companion class until a screen has such a rule.
4. Not yet verified on the phone: decorators through Metro/Babel, and memory under Hermes.
5. `@lazy` caches reads outside a screen until the end of the current task, which `@computed` does not; harmless, but documented so nobody is surprised.
