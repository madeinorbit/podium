Podium, from first principles

A redesign built from a fresh, full read of the codebase: what the product actually is, which complexity is essential, and the architecture that fits it — plus what it deletes and how we could get there.

2026-07-10 ~124k LOC surveyed · 6 apps · 11 packages 5 parallel deep-read reports synthesized

TL;DR — five moves

The bones are right. The product concept, the local-first sync direction, the harness-adapter seam, the command-registry idea — all worth keeping. What's wrong is that the codebase contains three half-finished unifications (branded IDs, generic mutations, the delta wire), several god objects that grew where module seams should be, and the same concepts defined 3–8 times. The redesign finishes the unifications and makes the latent architecture the actual one:

MOVE 1

One model

Every entity defined once, with branded IDs, in a single model package. All projections derived, never re-declared. Sync provenance moves to an envelope, out of entity schemas.

MOVE 2

One replication engine

Authority / Replica / Outbox — one engine used identically at browser↔server, mobile↔server, and node↔hub. The funnel, ledger, upstream sync, forwarder, and client replica are today five bespoke implementations of it.

MOVE 3

Commands everywhere

The issue command registry pattern — schema + authz + handler, transports derived — becomes the write surface for all mutations. One access path replaces tRPC-vs-registry-vs-store spaghetti.

MOVE 4

Three planes, explicit

Control (durable, replicated) / Stream (live, lossy) / Bulk (paged). The wire taxonomy already knows this; the module structure doesn't. Make plane the top-level organizing axis.

MOVE 5

Variance at the edge

Everything CLI-specific lives in one harness manifest per agent (today: 3 capability tables, 6 identity aliases, state logic in 3 modules). One SessionBinding owns a session's identities.

1 · What Podium actually is

Strip away the implementation and the product is one sentence:

Podium is a control plane for a fleet of third-party coding agents: it runs them on any of your machines, shows you all of them from anywhere (offline-capable), tells you which one needs you, and organizes the work around them.

Everything shipped today falls into eight capability clusters:

See agentsTerminal panes (xterm), structured chat view of the same session, controller/spectator roles, mobile key toolbar, live titles, drafts synced across devices.

What is genuinely good keep

  • The local-first replica. Oplog deltas + durable outbox + optimistic overlay is the right read/write model for this product, and it works.
  • The harness-adapter seam. Per-CLI variance (launch flags, resume models, transcript formats, MCP dialects) is irreducible; isolating it in adapters is correct.
  • The message-class taxonomy. durable / live / command / bulk, total over every union — a compile error if you forget to classify. This is the seed of the whole redesign.
  • The issue command registry. One definition → tRPC + MCP + CLI + relay, with authz attached. The best pattern in the repo; it just never spread.
  • Domain as a tiny pure leaf (461 LOC, zero deps), the sqlite runtime shim, the signed-update pipeline, boundary linting as code.

3 · First principles

Five invariants fall directly out of the problem. Everything in §4 is derived from them.

P1

Agents are opaque and hostile to abstraction

Third-party TUIs you don't control: no uniform state API, divergent resume models, on-disk formats that drift per release. Adapters, hooks, and heuristics are essential — so confine 100% of that variance to one module per CLI, and let nothing else know an agent's name.

P2

Replication is the product, not a feature

Phone offline, laptop asleep, VPS authoritative — every surface is a replica of somebody. There must be exactly one replication mechanism, used at every hop, or every hop grows its own bugs.

P3

Three traffic classes, three contracts

Durable state (small, must survive reconnect), live streams (high-rate, loss is fine), bulk data (transcripts — paged, never fanned out). They already have different guarantees on the wire; they should have different owners in the code.

P4

Every write is a command

Named, schema'd, authorized, idempotent. Whether it arrives via UI, CLI, MCP, an agent's relay, or a downstream node's outbox — same definition, same authz, same envelope. Transports are derived, never hand-written.

P5

Podium mints identity; artifacts are evidence

Already the stated doctrine (“agent artifacts are evidence, never identity”) — apply it totally: one branded ID per entity, minted once, with all native aliases (rollout files, thread ids, abduco labels, scopes) recorded on the entity, never used as it.

4 · The design

4.1 One peer model

Today there are four bespoke kinds of process (server, hub, daemon, client) with four handshakes and three identity schemes. Reduce to one concept: a peer that dials an authority, authenticates once, declares capabilities, and then speaks the three planes it cares about.

  ┌─────────┐   ┌─────────┐   ┌──────────┐        ┌──────────────┐
  │ web PWA │   │ mobile  │   │ desktop  │        │ another node │
  │ replica │   │ replica │   │ (full    │        │ (its own     │
  └────┬────┘   └────┬────┘   │  node)   │        │  authority)  │
       │             │        └────┬─────┘        └──────┬───────┘
       │  control+stream+bulk      │                     │  control (replica)
       ▼             ▼             ▼                     ▼  + command forwarding
  ╔═══════════════════════════════════════════════════════════════╗
  ║  NODE (authority)     model · commands · sync · services      ║
  ║  roles: [core] [+hub: accepts peers below] [+cloud: plugins]  ║
  ╚═══════════════╤═══════════════════════════════╤═══════════════╝
                  │ stream + command planes       │
           ┌──────┴──────┐                 ┌──────┴──────┐
           │ machine host│                 │ machine host│   ← daemon role:
           │ (this box)  │                 │ (remote box)│     PTYs, harnesses,
           └─────────────┘                 └─────────────┘     discovery, hooks
One handshake, one pairing story, one token model. “Hub” stops being a different thing — it's a node that accepts other nodes as replica peers. The local daemon pairs exactly like a remote one (no more 'local'/'__local__' placeholder identities).

4.2 Three planes as the top-level axis

CONTROL — durable

Entities + commands + replication. The only plane with persistence.

  • read: change feed (seq cursor, gap-heal)
  • write: command envelopes (idempotent)
  • sessions, issues, conversations, machines, repos, settings, threads

STREAM — live, lossy

Never persisted, never replayed, coalesced under pressure.

  • PTY frames, titles, agent state
  • host metrics, quotas, presence
  • attention events

BULK — paged

Large payloads, cursor-anchored, never fanned out.

  • transcript windows + tails
  • file read/write, uploads
  • lake mirror pulls
Today this exists as a wire-side classification (message-class.ts) bolted onto module code that freely mixes planes. In the redesign each plane has one owner in the gateway, one backpressure policy, one test harness — and a module declares which planes it touches.

4.3 One sync engine (Move 2)

The heart of the redesign. Define the replication engine once, with three roles, and instantiate it at every hop:

  AUTHORITY                      REPLICA                      OUTBOX
  owns the ledger                holds rows + cursor          durable command queue
  commit(cmd) → write            applies deltas               client-minted mutationIds
  + change append (one txn)      heals gaps via changesSince  optimistic overlay derived
  emits seq-ordered deltas       snapshot only on cold start  poison-drop, FIFO drain

  instantiated at every hop, same code:
    browser/mobile  ──replica+outbox──▶  node        (today: client-core replica + outbox)
    node            ──replica+outbox──▶  hub         (today: UpstreamSync + UpstreamForwarder)
    server modules  ──commit()───────▶  own ledger   (today: funnel + Ledger)
Five implementations become one. The engine owns its DDL and migrations (today sync writes SQL against tables whose schema lives in apps/server). The legacy full-snapshot fan-out is deleted; delta is the only wire.
  • Entity envelope: every replicated row is {id, rev, origin, payload}. Mirror provenance (viaHub, upstreamStale, pendingSync — today hand-copied onto each entity schema) becomes envelope metadata computed by the replica, invisible to entity definitions.
  • Conflict policy stays: writer-authority for daemon-observed fields, per-field LWW for user-authored fields — but declared once per field in the model, not re-implemented per hop.
  • Idempotency stays: mutationId as the universal dedup key — but there is exactly one applied_mutations concept, owned by the engine.

4.4 Commands as the only write surface (Move 3)

Generalize the issue registry to everything. A command is:

defineCommand('session.rename', {
  input:  z.object({ sessionId: SessionId, title: z.string() }),
  authz:  { action: 'write', target: 'session', scope: 'subtree' },
  handler: (ctx, input) => ctx.sessions.rename(input),
})

From that single definition the framework derives: the tRPC procedure, the MCP tool, the CLI subcommand, the daemon-relay gate, the outbox envelope for offline clients, the idempotency wrapping, and the audit/event-log entry. Consequences:

  • The 1,026-line hand-written router disappears into generated surface + a handful of genuine queries.
  • The three ways to reach state (mods(ctx) / ctx.registry.modules / ctx.registry.sessionStore) collapse to one.
  • Duplicate procs (superagent send ≡ sendTurn) become impossible to re-introduce unnoticed.
  • Issue authz (capability + scope-subtree) becomes the authz model for all writes, including sessions — agents get exactly the same gate everywhere.

4.5 The node, decomposed

Replace the constructor-as-wiring composition root and the 2.2k-line session god-object with services that each own one plane-scoped concern, communicating through commands (writes), the change feed (reactions), and typed queries (reads). Where today's graph is cyclic (sessions↔issues↔conversations), the cycle is broken by reacting to changes instead of calling back:

4.6 The machine host (daemon), tightened

  • One SessionBinding record per session owns all six aliases (podium id ↔ durable label ↔ systemd scope ↔ harness-native id ↔ resume ref ↔ transcript path) with explicit bind events on spawn / reattach / hook-repin / headless-allocation. Binding logic leaves session-observers.ts / control/session.ts / adapters and lives in one state machine.
  • One harness manifest per CLI — the existing adapter interface plus the capability matrix, MCP-support table, and transcript mapper registration folded in (today three separate tables in three packages). Nothing outside harness/ may branch on agent kind — lint-enforced, like today's boundaries.
  • Async-only host API — delete the sync/async twins of every abduco/tmux op.
  • State detection stays hooks-first; the regex transcript classifier survives but is quarantined as one adapter-private fallback with a confidence field, so the LLM escape hatch and future replacement are localized.

What deliberately does not disappear: the incident scar tissue. The abduco scope gymnastics, ConPTY quirks, codex trust hashing, redeploy gates — each encodes a real production incident. They get relocated and labeled (each behind its owning seam), not rewritten.

7 · Getting there — two routes

Route A — Strangler, in place (recommended)

Six phases, each independently shippable, live system stays up throughout. Order chosen so every phase makes the next one mechanically easier:

  1. Model extraction. Move every entity schema + domain predicate into model; flip z.string() ids to the existing branded ids; delete duplicate shapes by re-deriving them. Mechanical, huge blast radius, near-zero behavior change — the compiler drives it.
  2. Sync unification. Make funnel/ledger the Authority role; port client replica to the Replica role; delete the legacy snapshot fan-out; move DDL into sync. Then re-instantiate for node↔hub and delete Upstream*.
  3. Command generalization. Lift the registry framework out of issues; migrate session/settings/superagent mutations onto it; shrink the router.
  4. Node decomposition. Split SessionService along lifecycle/inbox/presence; recompose IssueService; replace thunk-wiring with change-feed reactions. (Only safe after 1–3: the seams then already exist.)
  5. Host tightening. SessionBinding state machine; async-only hosts; fold the three capability tables into harness manifests.
  6. Client split + UI slimming. Engine into five modules; viewmodel slices; retire the mobile wrapper; declarative menus.

Why recommended: ~6 apps × 3 OSes × 5 agent CLIs of incident-hardened edge cases live in this code. A rewrite re-discovers them one outage at a time; a strangler carries them across. The boundary linter and the message-class totality checks make each phase verifiable.

Route B — Clean-room rebuild (“throw it all away”)

Scaffold the L0–L4 skeleton empty, port feature clusters in product-priority order (run/see agents → state/attention → tracker → sync/fleet → orchestrator → ops), treating today's repo as a reference implementation and test oracle (the e2e suite ports first).

Honest cost: months of dual maintenance, and the highest-risk code (abduco/ConPTY/harness quirks) is exactly the code that can't be redesigned — it would be transplanted verbatim anyway. Route B buys a cleaner git history and absolute freedom on the store schema; it does not buy a better architecture than Route A ends at. Worth it only if we also want to change something Route A can't reach (e.g., a different persistence substrate end-to-end).

8 · Open decisions — where I need you

Each of these changes the design or the plan. My recommendation is marked, but these are yours to call:

Route A (strangler) or Route B (rebuild)?

Recommend A. The incident scar tissue is the most valuable code in the repo; A carries it, B re-earns it.

Delta-only wire — drop legacy snapshot clients?

Recommend yes. Removes the dual fan-out permanently. Cost: one forced client update at cutover (the 426 self-update path already exists).

All-in-one: one process or keep the server/daemon split?

Recommend keep two processes, one peer protocol. The split isolates PTY storms from the API and is why redeploys don't kill sessions. The redesign removes the split's complexity (one handshake, no placeholder identities) without giving up its isolation.

Replica store: keep TanStack DB, or a minimal purpose-built replica?

Slight lean: purpose-built. The sync engine defines the semantics anyway; TanStack DB has already bitten (delete-tracking) and mostly adds an adapter layer. But keeping it is cheap if you value the ecosystem.

Agent state: invest in hooks-first everywhere and demote the regex classifier?

Recommend yes. Hooks are ground truth where they exist; the classifier becomes a labeled, confidence-scored fallback inside the claude manifest only.

Keep tRPC, or go fully command-registry + plain HTTP queries?

Recommend keep tRPC as a derived transport (typed client for free), but no hand-written procedures — everything flows from command defs. Full removal is possible later since nothing but the derivation layer would touch it.

Nothing has been changed in the repo. When you've picked directions on the questions above, the natural next step is a phase-1 plan (model extraction) with concrete file moves.
